Tenant notification templates (LawDocsComply PR-LDC-27; R1-plan M58; R1-D-90). `TenantTemplateStore` keeps versioned tenant overrides per class, channel and locale in `notify.tenant_template` (migration `notify/0004`, expand-only, forced RLS) behind wave 2's `TemplateResolver`: pass `store.resolver.resolve` as `templates`. An email override is a subject, a required plain-text part and an optional HTML part with `{{var}}` placeholders, linted by `lintEmailTemplate` (the class's variable whitelist, `templateVariables`; field limits; a strict HTML allow-list with no script, style, iframe, form or embedded content, no event handlers, https, mailto and tel links only, no remote images and no variables in attributes) and rendered by `renderEmailTemplate` with every HTML value escaped; security classes keep the catalogue's email. SMS and WhatsApp overrides only select a template the product's `TemplateRegistry` has registered for the tenant (DLT template with its sender and entity ids; an approved WhatsApp template by name and language), never free text, and a selection no longer registered fails the delivery closed. Every change is the R3 maker-checker request `notify.template.change` (`requestChange`, tenant owner, admin or maker; `registerApprovals`, tenant checkers only), whose executor checks the content digest and the base version, supersedes the previous version and ledgers `notify.template.activate` in the approving transaction; `history`, `get` and `resolvedOf` read the versions. `NotifyService.previewTemplate(ctx, class, channel, locale, vars)` returns the message delivery would hand the port, built by the same code. The email channel sends tenant content as `EmailMessage.content` and refuses an adapter without the `content` capability. Catalogue classes may declare `variables`; the platform classes now do where their variables are known, and the catalogue lint checks them against the SMS and WhatsApp template variables.
