PAdES verification is now usable against CCA India (owner answer #178; R1-D-272). `CCA_INDIA_TRUST` pins the two existing CCA India roots, CCA India 2022 and CCA India 2022 SPL, by the SHA-256 of their DER (checked at load); the expired 2014 and 2015 SPL roots are not pinned. Only roots are pinned: an intermediate carried in the signature's CMS certificate set (or in a timestamp token's, for the TSA) is accepted when the whole path validates to a pinned root (names chain, each signature verifies, every CA has cA TRUE and keyCertSign, with keyUsage required on a carried intermediate, path length constraints, at most 6 certificates, no unknown critical extension, all valid at the signing time). The search is bounded against a hostile certificate set (`PADES_LIMITS.maxChainCandidates` 16, `maxChainSignatureChecks` 32, `maxChainSearchSteps` 128; running out is `chain_untrusted`). Each signature result gains `chainSha256` (the path's certificate fingerprints, signer first, root last; null without a path) and `timestampChainSha256` (the TSA's path when the timestamp is valid). New option `requireTimestamp` (default false) refuses a signature without a verified B-T timestamp with the new outcome `timestamp_required`, reported only when no other refusal applies. Pinned intermediates in a `customTrustStore` work as before. `@infrabyx/crypto/pades-test` gains `criticalOids` on `testCertificate`.
