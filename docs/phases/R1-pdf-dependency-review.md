# PDF export: dependency review (PR-LDC-28, wave 7; R1-D-95)

**Question.** LawDocsComply asked for PDF beside XLSX and DOCX (PR-LDC-28). Wave 6 shipped XLSX and DOCX over the package's own ZIP writer and deferred PDF to a dependency review (R1-D-87).

## Options

| Option                                                                         | What it brings                                                                                                                                                              | Cost and risk                                                                                                                                                                                                                                                                       |
| ------------------------------------------------------------------------------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| A. A PDF library with font embedding (for example PDFKit with its font engine) | Embedded TrueType or OpenType fonts, so any script, the rupee sign and Indic text with shaping                                                                              | A dependency tree of several packages, with font parsing of untrusted inputs in the export path; each added to the 7-day update policy (PL2-D-32), the SBOM, the licence check and the threat model; complex-script shaping still needs care; a font file to ship and keep licensed |
| B. A low-level PDF object library                                              | Object-level writing and editing                                                                                                                                            | Still a dependency; text layout, wrapping and tables are ours to write anyway; no shaping                                                                                                                                                                                           |
| C. Our own writer over the 14 standard fonts (chosen)                          | PDF 1.7, the block model DOCX already uses, Helvetica with WinAnsiEncoding, no font embedded, Flate-compressed content (Node's zlib), link annotations, deterministic bytes | Text limited to WinAnsi (Latin-1 plus the euro sign, dashes, curly quotes, bullet); no rupee sign, no Indic scripts; widths from the Helvetica metrics, bold measured wider so lines break early, never late                                                                        |

## Decision

C, as for XLSX and DOCX: no new dependency, no font parsing, no untrusted content beyond text the caller passes, and no JavaScript, forms, attachments or actions other than https links. A character outside WinAnsi is refused (`char_unsupported`), never replaced, so a report never silently changes an amount or a name. `[ASSUMED – owner review]` (OWNER-QUESTIONS #117): if a product needs the rupee sign or Indic text in PDF, option A comes back as its own review, with the font and its licence named.

## Tests

`packages/export/src/pdf.test.ts`: the cross-reference table points at every object; A4 pages; the table header repeats on every page a table spans; WinAnsi bytes for the euro sign, dashes and quotes; escaping; link annotations (https only) and none of JavaScript, AcroForm, embedded files, Launch or OpenAction; the same bytes for the same input; refusal of the rupee sign and Devanagari; bad blocks; the size cap. A sample was also checked with poppler (`pdfinfo`, `pdftotext`) and `pypdf` in strict mode.

## Update, wave 8 (OWNER-QUESTIONS #117, R1-D-96, R1-D-97)

The owner said no to Latin-only PDF: Indian lending and compliance documents need the rupee sign and the borrower's language. Two changes, still without a run-time dependency:

1. **The rupee sign.** `toPdf` now embeds Noto Sans (Regular, Bold, Italic, Bold Italic; SIL OFL 1.1) in place of the standard Helvetica: subset once, at build time, with fontTools 4.55.3 to Latin, Latin Extended-A, the WinAnsi punctuation, the euro and the rupee sign, about 22 KB per style, shipped in `packages/export/fonts/` with the upstream commit, the upstream and subset SHA-256 and the licence (`FONTS.md`, `OFL.txt`). fontTools is a one-off tool, not a dependency of any package. The fonts are embedded whole as CIDFontType2 with Identity-H and a ToUnicode map; `ttf.ts` reads only their metrics and character maps.
2. **Indic scripts.** Shaping (conjuncts, matras, reordering) is not done in process; such documents are refused with `shaping_required` and routed by `renderPdf` to the DOCGEN port (Gotenberg's Chromium) as self-contained HTML. Doing the shaping in process (a HarfBuzz build, or an OpenType layout engine) would be its own dependency review and is not proposed.
