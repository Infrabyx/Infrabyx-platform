## A. PR-UDF-048 — the STATEMENT_ANALYSIS port (`contracts`, `config`, `fakes`, `testing`, `connectors` minors)

Udofin's Phase 6 step 6.6 analyses a borrower's bank statements (FI data fetched under an AA consent, AA_FIU, or a statement the borrower uploads) before an RE's credit decision. Today it would call an analyser directly from the product. The port puts it behind IPB-01's registration process (§01.4.4.0): an interface, a contract suite, a reference adapter, an alternative, a fake, a catalogue entry, config keys and an ADR (ADR-0012).

**Interface** (`packages/contracts/src/ports/statement-analysis.ts`, `StatementAnalysisPort`):

- `analyse({ subjectRef, inputs: [{ fiType, storageKey, sha256 }], reportPrefix }, call?) → StatementAnalysis`, where `StatementAnalysis` is `{ analysisId, state: "COMPLETED" | "PENDING" | "FAILED", report?: { storageKey, sha256 }, failureReason?, adapter, method, vendorRef, checkedAt }`. `analysisId` is the platform's own id (`sta_<ULID>`, a new `ID_PREFIXES` entry), never the vendor's; `vendorRef` is the vendor's (the analysis id for the in-platform adapter); `method` names the analyser and its version; `report` only when COMPLETED, `failureReason` (`STATEMENT_ANALYSIS_FAILURES`: `unreadable_input`, `unsupported_input`, `vendor_failed`) only when FAILED.
- `status(analysisId, call?) → StatementAnalysis` (an optional `PortCall`, as PR-UDF-045 did for `vcipStatus`; read under `call.tenantId`, else the tenancy context). A final state is answered from the record without asking the vendor again; a PENDING one asks the vendor.
- `handleWebhook(rawBody, headers, meta?) → { analysisId, analysis }` for a pending analysis: the signature is verified first, then the analysis is read back with `status`; the notification's own state is never trusted.
- **Request schema** (Zod, strict): `fiType` from AA_FIU's `FI_TYPES`; `storageKey` a STORAGE key (`isValidStorageKey`, IPB-01-27); `sha256` 64 lower-case hex; 1 to 24 inputs, each key once; `reportPrefix` a `tenant/<tenant>/<module>/` prefix; every input in the report prefix's tenant; `subjectRef` 3 to 200 characters with no Aadhaar-like number (`findAadhaarLike`). Every field is classed REGULATED.
- **References only:** inputs and the report are STORAGE references with their SHA-256; no statement content, account number or transaction ever crosses the port, and the result's keys are a fixed set (`statementAnalysisResultOnly`).

**Residency and class (REGULATED, kept in India), enforced the way the other REGULATED ports are:**

- `PORT_DEFAULT_DATA_CLASS.STATEMENT_ANALYSIS = "REGULATED"` (and the ESLint plugin's mirror), and the router's method table (`core/specs.ts`) names `analyse`'s payload and `PortCall` and `status`'s `PortCall`, so the router refuses an adapter instance whose residency cannot carry REGULATED (`IPB-PORT-003`, `ResidencyViolationBlocked`) before any I/O, and a routing file that names an adapter with another residency at boot (`IPB-PORT-005`).
- Each adapter declares `residency: "IN"`, `maxDataClass: "REGULATED"`, and checks the call itself (as the EMAIL adapters do for attachments): a `call.dataClass` below REGULATED or above it, or an input that is not in the REGULATED bucket class (the India-resident class), is refused `IPB-PORT-003` (`meta.reason: "residency"`) before any vendor call. An input that is missing is `IPB-PORT-001` `input_missing`; one whose bytes do not match its SHA-256 is `IPB-PORT-001` `hash_mismatch` (as the KYC adapters, PR-UDF-039). The report is written to the REGULATED class under `reportPrefix` with its SHA-256.

**Idempotency** on `call.idempotencyKey` for `analyse`: the same key with the same request answers the same analysis with one vendor call; the key with another request is `IPB-PORT-004` (`idempotency_conflict`) before any vendor call. The KYC store pattern (`kyc/bank-account.ts`): `StatementAnalysisStore` with `MemoryStatementAnalysisStore` (tests, one process) and `PgStatementAnalysisStore` (production) on a new table. The key is kept as SHA-256; the request as a SHA-256 of its canonical form (JCS): it binds the inputs' own SHA-256 digests, so it cannot be tested against guesses without the statements, and no HMAC (no new key) is needed. Every analysis has a record, keyed or not, because `status` needs the report prefix and the vendor's reference of a pending one. A keyed retry whose first call did not finish asks again with the same `analysisId` as the vendor's reference (the in-platform analyser is deterministic; the HTTP vendor is expected to de-duplicate on it `[VERIFY]`).

**Adapters** (both against stubs, both off by default; no vendor is chosen: the repository names no statement-analysis vendor, so neither adapter is named after one, and the vendor is owner question #152):

- **Reference, `platform-statement`** (`PlatformStatementAnalyser`): an in-platform, deterministic analyser with no vendor and no egress. It reads each input from STORAGE, checks its class and SHA-256, recognises its format (ReBIT JSON from AA_FIU, or PDF by its signature) and writes a checksum summary report (per input: FI type, SHA-256, byte length, format; method `checksum-summary-v1`) and nothing from the statement's content. An input in neither format is FAILED `unreadable_input`. It never answers PENDING, so `handleWebhook` is `unsupported`. Off behind `int.statement_analysis.platform.enabled` (default false). It proves the plumbing (references, residency, idempotency, the report's shape) until the owner chooses an analyser; it is not a credit analysis.
- **Alternative, `http-statement`** (`HttpStatementAnalyser`): a vendor-neutral HTTP adapter over the egress client (no SDK; IPB-02-43), every vendor shape `[VERIFY]` and kept in small mapping functions: `POST /v1/analyses` with `{ referenceId, documents: [{ fiType, sha256, contentType, content (base64) }] }` (never `subjectRef`), answered `{ id, status: COMPLETED | PROCESSING | FAILED, method, report? }`; `GET /v1/analyses/<id>` for status; bearer key from SECRETS (`secrets/<env>/statement_analysis/http/api_key`). The report is written to STORAGE as received, with its SHA-256. Off behind `int.statement_analysis.http.enabled` (default false); its host is `int.statement_analysis.http.host` (default empty: refused `adapter_unconfigured`), on the egress allow-list alone. `unproven` until a vendor's sandbox exists.
- **Fake, `fake-statement-analysis`** (`FakeStatementAnalysis`, in `@infrabyx/fakes`, re-exported by `@infrabyx/testing`): deterministic by input bytes (a marker answers PENDING until `settle`), counts its analyses, and implements the signed webhook.

**Webhook decision: no new cryptography.** Standard Webhooks verification is not approved for platform use yet (#150, on another branch). HMAC-SHA-256 is approved for named vendors' webhooks only (C-13: Razorpay, Cashfree, Meta), so it is not extended to an unnamed vendor here. The real adapters therefore refuse `handleWebhook` `IPB-PORT-001` `unsupported` (declared in their capabilities), and a product follows a PENDING analysis with `status`. The fake implements it with the C-22 profile already approved for regulated messages (`signRegulatedMessage` / `verifyRegulatedMessage`, ES256 through a `LocalKms` development key, a replay store), as the V-CIP hand-off fake does (PR-UDF-045): a bad or replayed signature is `IPB-API-018` with no read-back. The vendor's scheme is chosen with the vendor (#152).

**Data model and migration:** `connectors/0014_statement_analysis.sql`, `connectors.statement_analysis`: `id` (`sta_` ULID, the analysis id), `tenant_id`, `adapter`, `key_hash` (null when unkeyed; unique per tenant and adapter when set), `request_hash`, `report_prefix`, `state` (`requested`, `pending`, `completed`, `failed`), `vendor_ref`, `result` (the port's answer: references, hashes, evidence; REGULATED), `created_at`, `updated_at`, `expires_at`. Expand-only; forced RLS by tenant; every column data-class tagged; granted as its peers; a guard trigger keeps the binding and moves the state forward only (`requested` → any, `pending` → `pending`, `completed` or `failed`; final states final; the vendor reference set once). Every write through the kernel with a ledger entry (`connectors.statement_analysis.*`: the row, the adapter, the key's hash and the state; never the request). A record lives 24 hours (IPB-10-07's window, as #144): after that a retry with the key is a new analysis and `status` answers `unknown_analysis`, so a product keeps the result in its own records. `purgeExpired` deletes expired rows (ledgered).

**Registration** (everywhere a port appears): `PORT_CATALOGUE.STATEMENT_ANALYSIS` (tier 2, `int.statement_analysis.`, owner ADR-0012) and `R1_PORTS`; the `ports` index; the router's method table; three settings in `packages/config/settings-tree.yaml` (regenerated registry); `@infrabyx/connectors/statement-analysis` (a subpath export) with `src/statement-analysis/` (so `pnpm --filter @infrabyx/connectors test:contract -- --port STATEMENT_ANALYSIS` runs its leg); `scripts/port-matrix.mjs` `PORTS` (and its path test); `PORT_EXIT` (`platform-statement` → `http-statement`) and `docs/exit/EXIT_RUNBOOK.md` regenerated; ADR-0012; threat model §3.144; product guide §7cy.

**Tests by IPB ID:**

- `@IPB-01-15` contract cases (`statementAnalysisContractCases`, in `testing`) on the fake, `platform-statement` and `http-statement` (its stub): completed (a REGULATED report under the prefix whose bytes match its SHA-256; `status` answers the same); pending then `status` (fake and HTTP stub); failed (a reason, no report); residency refusal (an input outside the REGULATED class, a call class below or above REGULATED: `IPB-PORT-003` with no vendor call); a missing or altered input refused before any vendor call; idempotent retry with one vendor call; conflict `IPB-PORT-004` with no vendor call; `status` of an unknown analysis; references only (the result's exact keys, no input bytes); a `findAadhaarLike` sweep (`@infrabyx/contracts/aadhaar`, letters joined) over every answer and error; the webhook (verified and read back on the fake, `unsupported` on the real adapters).
- `@IPB-01-16` the router refuses a GLOBAL instance for the port (`IPB-PORT-003`) and a routing entry that disagrees with the descriptor (`IPB-PORT-005`).
- `contracts` unit: the schema (strict, bounds, tenant, Aadhaar-like `subjectRef`), every field REGULATED, the port default, the catalogue and `R1_PORTS`, the result filter.
- Adapter tests: off until the flag (nothing read or sent, health down), the HTTP host unset, the body without `subjectRef`, a report answered by the vendor stored by hash, a vendor `FAILED`.
- Integration (PostgreSQL, `statement-analysis.int.test.ts`): forced RLS, grants, every column classed; keyed record, replay and conflict; no key, no request, no input key in any row or ledger entry; another tenant neither reads nor collides; the guard trigger; expiry and purge; the HTTP adapter's keyed retry on another instance with one vendor call.

**Stubs:** `startStatementAnalysisStub()` in `@infrabyx/testing` (`/v1/analyses` create and read, bearer key, a PENDING marker and a `complete(id)` hook, a FAILED marker), stub-shaped `[VERIFY]`.

**Exit-gate checklist:** each changed package's unit suite, lint and typecheck; the new contract leg; the integration test; `pnpm migration:lint`; `pnpm ipb:check`; `pnpm aadhaar:scan`; `pnpm scripts:test`; `pnpm test:policy` (port matrix); `pnpm registry:check`; `npx prettier --check .`; the exit runbook regenerated and checked; a Changeset per changed package; DECISIONS row; threat model; product guide; the request's row marked built.

**Owner decisions needed** (#152, none blocking): which analyser the reference should be (a vendor, or a deeper in-platform analysis), and its webhook scheme; the defaults taken: no vendor name, the checksum-only reference, the HTTP shapes `[VERIFY]`, `handleWebhook` `unsupported` on the real adapters, 24-hour records, a plain SHA-256 request binding, and up to 24 inputs.
