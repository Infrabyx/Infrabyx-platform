# R1 plan: Udofin PR-UDF-059, a verify-only PAdES/CMS signature verifier (not built until the owner approves)

Owner's addendum, 20 Nov 2026: "a cryptography item: plan it and raise it as an owner question before building (C-list)". Decision R1-D-218 (7); owner question #162. Related: PR-020 (ESIGN `verifySignature` planning, PL3-D-25).

## A. What Udofin asked for

A local PAdES/CMS signature verifier in `@infrabyx/crypto`: verify only, against the CCA India root and its published intermediates; no signing, no new primitive beyond X.509/CMS verification; so a product checks a PDF's embedded signature without a paid ESP call.

## B. Proposed scope (for approval)

- **Input:** the PDF bytes (from STORAGE, by key and SHA-256). Find each signature dictionary (`/Type /Sig`, `/SubFilter` `ETSI.CAdES.detached` or `adbe.pkcs7.detached`), its `/ByteRange` and `/Contents`.
- **Checks:** the `ByteRange` covers the whole file except `/Contents` (else `incremental_update_after_signature` is reported); the CMS SignedData (RFC 5652) parses; `messageDigest` equals the hash of the covered bytes; the signed attributes verify with the signer certificate's key; the chain builds to a pinned CCA India root through published intermediates; each certificate is valid at the signing time (`signingTime` or a timestamp token's time, B-T); key usage allows digital signature or non-repudiation.
- **Algorithms (verification only, already used elsewhere for verification):** RSA PKCS#1 v1.5 and PSS with SHA-256/384/512; ECDSA P-256/P-384 with SHA-256/384. SHA-1 and MD5 refused (`weak_algorithm`).
- **Trust store:** the CCA root(s) and intermediates as DER files in the repository with their SHA-256 fingerprints in a manifest, changed only by PR; no trust taken from the PDF beyond its chain.
- **Revocation:** CRL/OCSP need egress to the CAs. Default: reported `not_checked` unless the caller passes CRLs or OCSP responses it fetched; an online mode is a separate owner question.
- **Output:** `{ signatures: [{ signer: { subject, serial, issuer, certSha256 }, signedAt, coversWholeDocument, chain: "trusted" | "untrusted", revocation: "good" | "revoked" | "not_checked", algorithm, valid }], valid }`; no personal data is logged.
- **Library:** `node:crypto` (`X509Certificate`, `verify`) with a minimal ASN.1/CMS reader, or `pkijs`/`asn1js` after a licence and supply-chain review; no native code.

## C. Tests (when approved)

Fixture PDFs signed by a test CA (generated in the test, never a real certificate), plus a published sample chain: valid, tampered byte, appended incremental update, wrong root, expired at signing time, SHA-1 signature, missing `ByteRange` coverage; `@IPB-02` crypto registry entry (verify-only); CBOM updated.

## D. Owner decision needed

#162: approve the verify-only scope (with revocation as caller-supplied evidence) as a C-item. Nothing is built until then.

## E. Build design (owner approval #162, R1-D-228; built under R1-D-246, C-28)

The owner approved section B exactly (#162, 20 Nov 2026). This section records how it is built; nothing here widens B.

1. **Library: a minimal reader, no new dependency.** `pkijs` and `asn1js` would add a general ASN.1 engine, a schema layer, a WebCrypto engine and their transitive packages (`pvtsutils`, `pvutils`, `bytestreamjs`, `tslib`, `@noble/hashes`) to a package that has had no third-party runtime dependency since PL1 (C-09), all on untrusted input. The approved scope needs a few fixed structures only, so `@infrabyx/crypto` gets its own strict DER reader (`der.ts`: definite lengths only, minimal length and integer encodings, low tag numbers, bounded element counts, no recursion over arbitrary input) and schema-driven readers for exactly: ContentInfo → SignedData → SignerInfo (sid, digestAlgorithm, signedAttrs `contentType`, `messageDigest`, `signingTime`, ESS `signingCertificateV2`, signatureAlgorithm, signature, the `signatureTimeStampToken` unsigned attribute), the certificate fields `node:crypto`'s `X509Certificate` does not expose (issuer and subject DER, serial, signature algorithm, extensions), TSTInfo (RFC 3161), CertificateList (RFC 5280 §5) and BasicOCSPResponse (RFC 6960). Signatures and certificate signatures are checked by `node:crypto` (`X509Certificate.verify`, `checkIssued`, `crypto.verify`). BER (indefinite lengths) is refused (`cms_malformed`). The `pkijs`/`asn1js` review is therefore not needed; the C-27 precedent (App Attest's DER reader) is followed.
2. **PDF side, no object model.** The file is at most 64 MiB (`maxBytes`, default 32 MiB) and starts with `%PDF-`. Every `/ByteRange` key is located; its enclosing indirect object is tokenised by a bounded PDF tokeniser (depth 16, strings, names, hex strings, arrays, dictionaries) and the dictionary holding that key is read: `/ByteRange` (four non-negative integers, `[0 b c d]`), `/Contents` (a hex string exactly filling the gap `b..c`, at most 1 MiB of DER, zero padding after the DER only), `/SubFilter` (`/ETSI.CAdES.detached` or `/adbe.pkcs7.detached`; anything else `unsupported_subfilter`) and `/M` (the claimed signing time when no other time is signed). A `/ByteRange` that cannot be read is a `malformed` signature, so an unreadable signature never disappears silently. Signature dictionaries inside compressed object streams are not found (the result is `no_signature` if there is none other); recorded as a limit.
3. **Coverage.** `c + d` equal to the file length is `coversWholeDocument: true`; less is an incremental update after that signature. The document is `valid` only if every signature found is valid and at least one covers the whole file; if all are valid but none covers it, the document outcome is `incremental_update_after_signature`.
4. **Algorithms (registry, verify only, C-28):** digests SHA-256/384/512 (`sha-384` and `sha-512` registered for this use only); RSA PKCS#1 v1.5 and PSS with SHA-256/384/512 (RSA ≥ 2048 bits; PSS with MGF1 of the same hash and trailer 1); ECDSA P-256 with SHA-256 and P-384 with SHA-384. SHA-1 and MD5 anywhere (digest, signature, certificate, CRL, OCSP, timestamp imprint) are `weak_algorithm`; anything else `unsupported_algorithm`. The signature algorithm's hash must match the digest algorithm.
5. **Trust.** `CCA_INDIA_TRUST` holds the pinned CCA India root(s) and published intermediates as PEM in `cca-india-trust.ts`, each with its SHA-256 fingerprint checked when the module loads, changed only by PR. Every CA certificate on the path must be one of them (an intermediate carried only in the PDF is not trusted). The path is at most 6 certificates; CA certificates need `cA` and, when key usage is present, `keyCertSign`; `pathLenConstraint` is honoured; an unknown critical extension, or a critical name-constraints or policy extension (not processed), fails the path. A `customTrustStore()` exists for tests and is reported as `trustStore: "custom"`, never `"cca-india"`.
6. **Signer certificate.** Found in the CMS `certificates` by `sid` (issuer and serial, or subject key identifier); ESS `signingCertificateV2`, when present, must hash to it (SHA-256/384/512); key usage must be present with `digitalSignature` or `nonRepudiation`; an extended key usage, when present, must include document signing, email protection, Adobe's authentic-documents usage, Microsoft document signing or any usage.
7. **Time.** The signing time is, in order: the genTime of a verified signature timestamp (B-T), the signed `signingTime` attribute, the dictionary's `/M`, else the verification time. Every certificate on the path must be valid at that time; a time more than 5 minutes after the verification time is `signing_time_in_future`. A timestamp token is verified fully (its CMS, `messageDigest` over TSTInfo, the imprint over the signature value, the TSA certificate with critical `timeStamping` usage chained to the same pinned trust and valid at genTime); a token that fails is `timestamp_invalid`; one whose TSA does not chain is reported `timestamp: "untrusted"` and its time is not used.
8. **Revocation (caller-supplied only, never fetched).** `revocation: { crls?, ocsp? }` (DER). A CRL counts when its signature verifies with the issuing CA's key (with `cRLSign` when key usage is present), the issuer name matches, it is current at the verification time and it has no critical extension (an issuing-distribution-point or delta CRL is not processed, so it is ignored, not trusted). An OCSP response counts when it is `successful`, basic, signed by the issuing CA or by a responder certificate that CA issued with `OCSPSigning`, current, and its CertID serial matches (with SHA-256/384/512 CertIDs the name and key hashes are also compared; a SHA-1 CertID is matched by serial under the issuer's signature, and no SHA-1 is computed). Each non-root certificate on the path: listed as revoked by any counting evidence is `certificate_revoked`; `good` needs counting evidence for every one; otherwise `not_checked`. A revocation is treated as fatal whatever its date `[ASSUMED – owner review]` (#178).
9. **Output.** Fixed labels only (`PADES_OUTCOMES`, `PADES_DOCUMENT_OUTCOMES`), never a string from the document; the signer block (subject, serial, issuer, certificate SHA-256) comes from the certificate, as section B lists. Nothing is logged.
10. **Tests.** `@infrabyx/crypto/pades-test` (tests only): a throwaway root, intermediate, TSA and signer (RSA or P-256), made at test time; it signs a PDF (a minimal one, or any classic-xref PDF such as `pdfFixture`'s) as an incremental update with a CAdES detached signature, and makes timestamps, CRLs and OCSP responses. Cases: valid RSA and ECDSA, B-T, tampered byte, appended update, wrong root, intermediate not pinned, expired at signing time, SHA-1, MD5 and unknown algorithms, missing `/Contents` coverage, malformed CMS and DER fuzzing (truncations and byte flips never throw), revocation good/revoked/stale/wrong issuer, OCSP good/revoked/unknown, and the empty CCA pin set refusing everything.
11. **Pins.** cca.gov.in is not reachable from the build environment, so `CCA_INDIA_TRUST` ships with **no pinned certificate** and refuses every chain (`chain_untrusted`) until the owner supplies the CCA India root and intermediates from CCA's published repository; owner question #178.
