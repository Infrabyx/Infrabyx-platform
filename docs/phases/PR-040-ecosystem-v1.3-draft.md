# PR-040: draft amendment to the Ecosystem Specification, v1.3

**Status:** draft for the owner's sign-off. The owner approved PR-040 for v1.3 on 4 Nov 2026 (R1-D-65). The repository never edits `docs/ecosystem/` (CLAUDE.md), so the text below is what the owner (or the spec's editor) would paste into the specification once it is signed off. Nothing here binds a product until v1.3 is published. **Raised by:** LawDocsComply PR-LDC-11, through the platform (R1-D-63).

## 1. What changes and why

v1.2 covers the Operations Hub's half of provisioning: OH4 approves a request and emits the signed `TenantProvisioned` (§6.29), and the product reports `ACCEPTED`, `READY` or `FAILED` by `PUT /v1/provisioning-requests/{id}`. v1.2 does not cover a product that starts provisioning itself (a self-serve trial or sign-up), or the Hub telling a product that a request it raised was refused. Today LawDocsComply publishes its own `ProvisioningRequested` from its outbox, and has no defined way to hear a refusal. v1.3 adds two events to §6.29, and makes no other change:

- **`ProvisioningRequested`**: product → OH, asking OH4 to provision a tenant for a provisional id the product already holds;
- **`ProvisioningFailed`**: OH → product, saying OH4 will not provision that request, and why.

`TenantProvisioned`, the status API and its rules are unchanged. A request that OH4 approves still ends in `TenantProvisioned`, which now names the request it answers.

## 3. Rules (paste as bullets under §6.29)

- **One request, one outcome.** Each `provisioning_request_id` ends in exactly one of `TenantProvisioned` or `ProvisioningFailed`. A consumer that has seen one of them ignores the other for the same id (and logs it as a conflict); OH never emits both.
- **Idempotency.** Both events are idempotent on `provisioning_request_id`. A product resending `ProvisioningRequested` with the same id and a different payload is refused by OH with `idempotency-conflict`; the product mints a new id for a new request. A product holds at most one live provisional id per `(org_ref or work-email domain, product, environment)`.
- **PRODUCTION.** A `ProvisioningRequested` for PRODUCTION is accepted by OH only as a request; OH4's maker-checker and the MSA, DPA and OUT clause-matrix refs are still required before `TenantProvisioned` (the §6.29 rule on `regulatory-guard` is unchanged).
- **Data.** `ProvisioningRequested` carries business contact data only (`dataclass` at most `INTERNAL` apart from the work email, which needs `legalbasis = CONTRACT_PERFORMANCE_VENDOR`); `ProvisioningFailed.detail` carries none. Neither carries borrower, member, customer or loan data (Operations Hub subjects accept at most `INTERNAL` from product sources, §4.6).
- **Code table `provisioning_failure_reason`** _(v1.3)_: `DUPLICATE_ORG` (a live tenant exists for the org, product and environment), `KYB_FAILED`, `PLAN_UNAVAILABLE`, `RESIDENCY_UNAVAILABLE`, `CONTRACT_MISSING` (MSA, DPA or OUT refs absent for PRODUCTION), `REJECTED_BY_CHECKER` (OH4's checker declined), `EXPIRED` (no decision within the request's validity), `PRODUCT_FAILED` (the product reported `FAILED` through the status API), `OTHER`. `retryable` is true only for `PLAN_UNAVAILABLE`, `RESIDENCY_UNAVAILABLE`, `EXPIRED` and `PRODUCT_FAILED`.

## 4. Signatures

Both events are **regulated messages** (§3.6), as `TenantProvisioned` is: RFC 9421 in transit and a detached JWS over the CloudEvent, stored with it so the proof can be re-verified after the HTTP exchange. Add `ProvisioningRequested` and `ProvisioningFailed` to the list of regulated messages added in v1.3. The JWS is made with the producer's ecosystem signing key (for `ProvisioningRequested`, the product's; for `ProvisioningFailed`, the Operations Hub's), and the consumer checks it against the key set it already pins for that producer. A consumer refuses an unsigned or wrongly signed event with `signature-invalid` and never acts on it.

## 5. Versioning

- **Event types:** `in.infrabyx.ops.ProvisioningRequested.v1` and `in.infrabyx.ops.ProvisioningFailed.v1` (§3.2; domain `ops` as for `TenantProvisioned`). `source` is `urn:infrabyx:[product]:[provisional_tenant_id]` for `ProvisioningRequested` and `urn:infrabyx:oh:[legalentityid]` for `ProvisioningFailed`; `subject` is the `provisioning_request_id`; `tenantid` is the provisional tenant id; `reid` is `none`; `productfamily` is `na`.
- **Schemas:** `[registry-base]/schemas/ops/ProvisioningRequested/1.0.0.json` and `…/ProvisioningFailed/1.0.0.json`; `TenantProvisioned` moves to a minor schema version for its optional `provisional_tenant_id` (additive; v1.2 consumers ignore the field).
- **Tag:** (N13) is the canonical-name tag for names adopted in v1.3. The change is additive: a v1.2 consumer that does not subscribe to the new types is unaffected, and no existing event, field or code changes meaning.
- **Specification history:** "v1.3: `ProvisioningRequested` and `ProvisioningFailed` (§6.29); `provisional_tenant_id` on `TenantProvisioned`; code table `provisioning_failure_reason`. Raised as platform request PR-040 from LawDocsComply PR-LDC-11."

## 7. What the platform builds once this is signed off

The request half and the failure path of the Operations Hub provisioning adapter (R1-plan M38; PR-LDC-11): publishing `ProvisioningRequested` from the product's outbox with its JWS, consuming `ProvisioningFailed` once per `provisioning_request_id` through the ecosystem inbox and calling the product's failure hook, and binding `TenantProvisioned.provisional_tenant_id` to the tenant `bootstrapTenant` created (M37). Until then the adapter consumes `TenantProvisioned` only.
