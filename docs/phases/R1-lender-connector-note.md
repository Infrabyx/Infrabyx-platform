# PR-UDF-004: does `LENDER_CONNECTOR` belong in the platform? (design note, no code)

**Date:** 2026-10-28 · **Request:** Udofin `docs/platform-requests.md` PR-UDF-004, items G1 to G7 of Udofin's `docs/architecture/connector-contract.md` §6 · **Status:** for the owner's decision (OWNER-QUESTIONS #82); nothing is built here · **Sources:** Ecosystem Spec v1.2 §3.3, §3.5, §3.6, §3.11, §10.1, §10.2, §14.3; IPB-01 §01.4.4.0, §01.4.4.2; IPB-14 §14.2; CLAUDE.md (the platform holds what every product needs; domain ports are proposed first, ADR-0005 of Udofin).

## 1. The question

Udofin asks for a `LENDER_CONNECTOR` port with the twelve capabilities of its Part 5.3, a contract suite and three adapters (Finbyx native, generic REST/webhook with mapping packs, SFTP/file), plus six supporting pieces (G2 to G7). Udofin is building product-local shims meanwhile, each named in its table, so nothing is blocked.

## 2. What the specs already decide

- **The connector SPI is an Ecosystem artefact, not an IPB-01 port.** Ecosystem §10.1: "Every connector implements `@infrabyx/connector-sdk` and runs out of process with APIs and events only", with the `Connector` interface (`manifest`, `capabilities`, `healthCheck`, `send`, `receive`, `call`, `reconcile`). §3.3 and §10.2 put schemas, code tables, mapping packs and the certification suite in `infrabyx-contracts`, and the Ecosystem Spec prevails over the IPB for cross-product contracts (CLAUDE.md precedence). A lender connector is that SPI applied to a lender.
- **IPB-01 ports are for external capabilities.** §01.4.4.2 names product domain ports as products' own (FBX `BUREAU`, `AA_FIU`; EQ `COURT_DATA`; LD `ECOURTS`), added through §01.4.4.0 by the product. A lender is a counterparty of Udofin (and Finbyx is the lender side), so `LENDER_CONNECTOR` is a domain port of the lending products.
- **Who needs it today:** Udofin only. Finbyx is the counterparty (it implements the RE side of the same events, not a lender connector of its own); no other product connects to lenders.

## 4. Recommendation

1. **Keep `LENDER_CONNECTOR` out of the platform** (G1, G3, G4, G6, G7 stay product-local now), and ask Udofin to shape its port as the §10.1 `Connector` interface so it can move into `@infrabyx/connector-sdk` unchanged.
2. **Take G2 (the Ecosystem inbox) into the platform** as the next maintenance minor, with its own plan, because all six products need it and half of it exists.
3. **Take G5 (JWS for regulated messages) into `@infrabyx/crypto`** only after the owner's cryptography decision.
4. **Decide where `infrabyx-contracts` and `@infrabyx/connector-sdk` live.** The Spec names them but no repository holds them yet. Creating one is an owner action (a new repository); hosting `connector-sdk` as a package in this monorepo is the other option and would reverse item 1 for the SPI only (not for the lender adapters).

## 5. Cost of each answer

- **As recommended:** Udofin keeps its shims behind the §10.1 shape; the platform plans G2 next; no new package here.
- **`LENDER_CONNECTOR` in the platform instead:** a new port under §01.4.4.0 (interface in `contracts`, contract suite in `testing`, three adapters in `connectors`, config keys, ADR, threat-model section), maintained for one product; the SPI would exist twice once `connector-sdk` appears.
- **`connector-sdk` hosted here:** a new package `@infrabyx/connector-sdk` (a minor, not a break), its certification suite in `testing`; lender adapters still product-side.
