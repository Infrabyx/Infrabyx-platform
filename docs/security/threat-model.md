# Threat model — infrabyx-platform

**Status:** living document (PL2-D-43). Updated by every PR that adds a port, adapter, package or data flow; the PR checklist points here. **Last updated:** 2026-11-12 (R1-D-139, §3.122: projection rule sets; R1-D-137, §3.121: the TallyPrime agent design; R1-D-136, §3.120: ordered approval levels; R1-D-135, §3.119: the product MFA floor; R1-D-126, §3.118: the CALENDAR interface; R1-D-122, §3.117: the ACCOUNTING sink interface; R1-D-128, §3.116: workbook forms; R1-D-125, §3.115: business ids on ledger entries; R1-D-120, §3.114: `cancelIn`; R1-D-117, §3.113 and §4: the AV port and the ClamAV adapter; R1-D-69, §3.73: per-tenant templates and delivery reports by vendor reference; R1-D-68, §3.72: the Operations Hub provisioning adapter; R1-D-67, §3.71: tenant creation for a provisional id; R1-D-66, §3.69: the approvals engine consumes each mandate approval; R1-D-64, §3.70: CI runs on pull requests only with the `ci:run` label; R1-D-62, §3.68: the Digio mandate adapter and NeSL DDE; R1-D-61, §3.67: the CIBIL bureau and Setu AA adapters against stubs, owner answer #97). Earlier sections carry their own decision references.

**Method:** STRIDE (Spoofing, Tampering, Repudiation, Information disclosure, Denial of service, Elevation of privilege) per package and per IPB-01 port, against the IPB-02 controls. Each control links to where it is specified (plan section, decision ID) and how it is proven (test tag). "Built" means merged on `main`; "planned" means specified in a phase plan and not yet built.

## 1. Scope, assets and trust boundaries

**In scope:** the `@infrabyx/*` packages, the reference routing files, CI workflows and the test infrastructure in this repository. **Out of scope here:** product code (each product keeps its own model), the cloud accounts themselves (PL6 Terraform and runbooks), and vendor internals (Vendor Assurance Room, IPB-D-09).

**Data classes** (IPB-02 §02.4.3.1): `PUBLIC` < `INTERNAL` < `CONFIDENTIAL` < `REGULATED` < `SECRET`. A class follows the content, not its protection (PL2 plan §6.9). A caller may only raise the class of a port call, never lower it below the port default (PL2-D-03).

| Asset                                                         | Class                   | Where it lives                                              |
| ------------------------------------------------------------- | ----------------------- | ----------------------------------------------------------- |
| Tenant business records                                       | CONFIDENTIAL–REGULATED  | Product schemas (RLS), field-encrypted where REGULATED      |
| REGULATED fields (PAN, Aadhaar, bank account, card last four) | REGULATED               | Field envelope (PL1 C-04), masked everywhere else           |
| Audit ledger                                                  | INTERNAL (digests only) | `audit.ledger`, hash-chained, append-only; signed anchors   |
| Secrets, keys, tokens                                         | SECRET                  | SECRETS / KMS ports only; never env in production           |
| Idempotency results                                           | as the call             | `connectors.idempotency_record`, sealed ≥ CONFIDENTIAL      |
| Telemetry                                                     | INTERNAL (scrubbed)     | OTLP → Collector → Grafana stack, `IN`                      |
| Flag state                                                    | INTERNAL                | Unleash or `config.flag_value`; snapshot in `config`        |
| Seed credentials                                              | SECRET                  | Generated per run, `SEED_CREDENTIALS.md` never committed    |
| Published packages                                            | PUBLIC (to the org)     | GitHub Packages; provenance through `release.yml` on `main` |

**Trust boundaries:**

1. **Caller → kernel.** Every mutation runs in `PgKernel.mutate` with a verified tenant context; RLS is the last line (IPB-02-12).
2. **Kernel → port (router).** The router enforces data class, residency, recipient delivery and idempotency before any I/O (PL2 plan §3.1, §3.5, §3.12).
3. **Adapter → vendor (egress).** HTTPS only, host allow-list, no redirects (IPB-02-43, plan §3.7).
4. **Vendor → platform (webhooks).** Signature verified, de-duplicated, ledgered (IPB-10-27, plan §3.8).
5. **CI and supply chain → `main` → registry.** SHA-pinned actions, 7-day dependency age, publish only from `main` (IPB-02-33, PL2-D-32).

## 3. Packages

### 3.1 `@infrabyx/contracts` (built)

Types, schemas and error codes only; no I/O.

- **T:** a schema too loose lets bad data through every product. Control: Zod strict schemas, payload data-class annotations, and `ipb/port-data-class` lint (an unannotated field fails).
- **I:** an error leaks internal detail. Control: RFC 9457 errors with code and help key; adapters put vendor detail in `meta`, never in `detail` shown to users (IPB-10).

### 3.2 `@infrabyx/crypto` (built)

- **I:** key material logged or serialised. Control: `SecretKey` is opaque (`toJSON`, `toString` and `inspect` print the ID only); material lives in a `WeakMap`.
- **T/S:** wrong algorithm or weak parameters. Control: the algorithm registry and CBOM (PL1), `assertApproved`, and the approved C-items only (plan §9). A new primitive is a stop-and-ask (CLAUDE.md working mode, item 1).
- **I:** joinable pseudonyms across purposes. Control: per-purpose HKDF sub-keys; telemetry hashes use `ipb/telemetry-id/v1` (PL2-D-36).
- **S:** forged or confused tokens. Control: C-11 verifier (X-16); `jose` only as a test devDependency, refused at runtime by `ipb:check`.
- **S:** forged vendor callbacks. Control: C-13 verifiers (X-17); webhook secrets we generate are 32 random bytes (C-19).
- **I (blind indexes above staging, PR-FBX-25, R1-D-37):** a dictionary attack on a searchable index, or indexes joined across tenants. Control: one root HMAC-SHA-256 key per product and environment, at least 32 random bytes, read through the SECRETS port (`secrets/<env>/kms/blind-index/<product>`) and used only inside `@infrabyx/crypto` (the C-23 pattern); each tenant and scope gets an HKDF-SHA-256 sub-key labelled `<product>/<scope>/v<n>/<tenant>`, so values of two tenants or scopes never match; the public local key is refused when read from SECRETS. Rotation writes a new secret version: writes move to it at once, lookups try both versions and a batched re-index rewrites old rows (`needsReindex`). Residual: the root key is in application memory while the process runs (a KMS-held MAC key would avoid that at one KMS call per index; OWNER-QUESTIONS #94); a value with few possible inputs (a date of birth, a pincode) stays guessable by anyone holding the key, so products index only high-entropy identifiers.

### 3.3 `@infrabyx/config` (built)

- **T:** a setting read before registration, or a production secret in env. Control: settings registry, env guard (exit 78) and the `process.env` lint (IPB-01-19).
- **E:** a flag flipped without governance. Control: `FlagAdmin` (kill switches by PLT_RELEASE_MANAGER/PLT_SECURITY_OFFICER, `fut.*` through R3 maker-checker) with a ledger entry (PL1-D-11).
- **D:** flag provider down. Control: last-known-good snapshot ≤ 24 h, then registry defaults; unknown `kill.*` evaluates on (X-10).

### 3.4 `@infrabyx/tenancy` (built)

- **S:** forged tenant or actor. Control: context only from verified claims; RLS insert policies bind `app.tenant_id` and `app.actor_id`.
- **E:** impersonation or break-glass abuse. Control: time-boxed, reason-required, ledgered; impersonated sessions cannot approve (`IPB-SEC-003`).
- **I:** REGULATED fields in plaintext. Control: field envelope encryption with per-tenant keys (PL1 C-04, C-15) and server-side masking; format v2 binds each data key to its tenant and purpose (X-18).
- **T:** a shipped migration edited. Control: checksums in `meta.migration_checksums`; migration-lint `--record-checksums`; CLAUDE.md "never edit a migration that has shipped".

- **E (named functions, PR-FBX-20, R1-D-39):** a person claiming a statutory function, or approving their own appointment. Control: `FN:` roles come only from `tenancy.function_assignment` (token claims are dropped by `withFunctions`), written only by the executor of an approved R3 request whose approver is not the assignee (also a table check); rows are never edited or deleted, revocation is immediate and ledgered. Residual: a product that skips `withFunctions` leaves function-gated actions undecidable, never wider.
- **E/R (officer functions per legal entity, PR-FBX-31, R1-D-46):** two people acting as the one CCO of an entity, an officer's function counted in another entity, or an officer removed by one person to clear the way for a friendlier one. Control: under a function's policy an assignment names the entity and the product's officer-register row; a unique partial index (`tenancy/0014`) allows one active single-holder row per tenant, function and entity, checked again before the request and at execution; `withFunctions` adds a per-entity function only when the context's `entityId` is that entity, and `authzAttributes` gives AUTHZ the entities per function; with `checkedRevocation` an assignment ends only by the executor of an approved R3 `tenancy.function.revoke` request (a different ORG_OWNER or ORG_ADMIN), recorded with its request id; the entity, register row and holder flag are immutable after the write (trigger). Residual: with checked revocation, removing a compromised officer at once means suspending the person's sign-in (IdP) while the request waits; a person can hold a function for one entity at a time in a tenant (the 0011 index), so one officer serving two entities of a group needs a later contract migration.

- **E/I (external grants from a product's approvals, PR-FBX-22, R1-D-40):** a product opening a wider grant than its approval allowed. Control: `fromApproved` runs only in a tenant transaction of a non-agent, non-external principal, refuses an identical maker and checker and more than 90 days, keeps the product's approval id once per tenant, and ledgers every field; the PII and export levels default to the most restrictive; reads still go only through `ExternalReads` as `app_external`. Residual: the platform trusts the product's own maker-checker for these grants; its approval record is the product's.

### 3.5 `@infrabyx/audit` (built)

- **R:** an action without a trace. Control: ledger-required commit (X-02); trigger-computed chain so no application path writes an unchained row.
- **T:** history rewritten. Control: append-only for every role (X-03); weekly verifier emits `LedgerChainBroken`; signed daily anchors on write-once storage (PL1 C-03).
- **I:** payloads in the ledger. Control: before/after stored only as canonical digests; IP and user agent as keyed pseudonyms (PL1 C-02).

- **R/T (batches and units, PR-FBX-30, R1-D-41):** a failed item's changes surviving, or a step's member list altered. Control: savepoints only through the kernel's `unit` (callers' `SAVEPOINT`/`RELEASE` stay refused); a rolled-back unit's entries do not satisfy the commit check; the batch entry's digest covers every member id and `audit.batch_member` is append-only for every role, checked by `verifyBatch`. Residual: a batch entry names resources, not their before and after states; a product that needs per-resource evidence keeps per-resource entries.

### 3.6 `@infrabyx/seed` (built)

- **E/I:** seeds or seed credentials in production. Control: refusal first in `prod`, `dr`, `pre-prod` (`SEED_REFUSED_ENVS`, PL1-D-06); generated passwords; `SEED_CREDENTIALS.md` ignored and checked by `ipb:check`; forced rotation and MFA on first production login (IPB-D-04).

### 3.7 `@infrabyx/testing` (built)

- **T (supply chain):** a test image swapped. Control: images pinned by digest from Docker Hub, kept equal to `infra/docker/TEST_IMAGES.md` by a unit test; images from session 2 on were at least 7 days old when pinned (PL2-D-37).
- **I:** sandbox credentials printed. Control: the sandbox-leg gate prints missing variable names only, never values.

### 3.8 `@infrabyx/connectors` core (built)

- **S:** a forged vendor webhook. Control: signature verification before any processing, 401 on failure, inbox de-duplication, ledger entry `connectors.webhook.received` (plan §3.8; C-13 for per-vendor rules, session 3 onwards).
- **T:** a replayed or altered idempotent request. Control: request hash (C-20) compared on replay, mismatch is `IPB-PORT-004`; keys stored as SHA-256 hashes.
- **R:** idempotency outcomes untraceable. Control: each state change is ledgered (PL2-D-35).
- **I:** a result of a REGULATED call stored readable. Control: results ≥ CONFIDENTIAL are sealed with tenant field encryption; RLS on `connectors.idempotency_record`.
- **I:** data sent to a vendor that cannot hold it. Control: X-05, X-06, checked before I/O; refusal emits `ResidencyViolationBlocked`.
- **D:** a failing vendor stalls callers. Control: circuit breaker per adapter (PL2-D-33), timeouts and bounded retries in egress, health registry; STORAGE writes fail fast instead of queueing bytes (IPB-DEV-06).
- **E/T:** SSRF through a vendor URL. Control: egress allow-list and no redirects (X-07).
- **Money:** a money call re-sent after an unknown outcome would double-charge or double-refund. Control: unknown outcomes stay pending and go to reconciliation; never re-sent (X-08, P-05).

### 3.9 `@infrabyx/connectors` IDENTITY and AUTHZ (built)

- **S:** a forged, re-signed or other-issuer token. Control: X-16 with ES256 only per issuer; JWKS only from the configured URL through egress; claims mapped to `VerifiedClaims`, unknown principal types refused, roles outside the platform format dropped.
- **S/E:** a user sets their own tenant or type. Control: tenant, type, product scope and external id are admin-only attributes (Keycloak `ADMIN_EDIT`) or admin-set metadata (Zitadel); the kernel context is built only from verified claims (IPB-02-13).
- **E:** a privileged role without MFA. Control: forced enrolment at login (Keycloak required action; Zitadel `forceMfa`), and the API guard refuses a token without an MFA method in `amr` (`IPB-SEC-001`); SMS never counts as MFA.
- **D (a second factor lost between login and token):** Control: each `amr` reference lives for the realm's session lifetime, so a code exchanged seconds after the TOTP step, or a refreshed token, still reports `otp`; a session that never ran the TOTP step carries none (R1-D-16).
- **R/E:** a de-provisioned user keeps working. Control: SCIM deactivation, `revokeSessions`, a role change and back-channel logout write a revocation (hashed subject, RLS, ledgered) before the IdP call; every replica refuses within 15 s (PL2-D-53).
- **D:** IdP outage. Control: JWKS cached 24 h so API calls continue; new logins fail with `IPB-IDN-002`.
- **E:** impersonation without an audited `act`. Control: impersonation tokens are unsupported on both adapters (PL2-D-55, owner); the kernel refuses mutations under `act` (`IPB-SEC-003`). Support access, when first needed, is a platform-issued read-only token on an approved, ticketed request, at most 60 minutes, ledgered and visible to the tenant's `ORG_OWNER`.
- **E:** an AUTHZ allow by mistake. Control: deny by default, PDP failure denies (`IPB-AUTHZ-001`), agents denied before the PDP and in policy (X-14), allow-only cache ≤ 5 s, one decision table proven on both engines.
- **I:** bootstrap secrets. Control: `applyRealm` and `applyInstance` return generated client secrets for the SECRETS port and never log them; they run only in deploy jobs and tests.

### 3.10 `@infrabyx/connectors` STORAGE, QUEUE and WORKFLOW (built)

- **T:** a retained record overwritten or deleted. Control: COMPLIANCE-mode Object Lock; the adapter also refuses a new version, a delete marker or an upload URL while retention applies (`IPB-STOR-003`); break-glass cannot delete a locked version (@IPB-02-AT-13).
- **I:** documents readable across tenants or under the wrong key. Control: keys outside the caller's tenant refused (`IPB-PORT-003`); SSE-KMS with the tenant's own CMK when it has one (C-17), so a tenant purge covers documents.
- **I:** a long-lived or repurposed presigned URL. Control: SigV4, 1–300 s, bound to the method and, for uploads, the content type (IPB-02-15).
- **I:** personal data on the queue or in Temporal's readable fields. Control: queue payloads are flat INTERNAL maps checked before I/O; workflow ids, names and task queues are checked to be identifiers; every Temporal payload and failure is encrypted (C-16) and unencrypted payloads are refused.
- **E:** runtime DDL by the queue. Control: pg-boss's schema is a checked-in migration; its role has DML and EXECUTE only (proven in the contract leg).
- **I:** decrypted workflow failures in worker logs. Control: worker logs go through the OBSERVABILITY scrubber (X-09); failures should carry codes, not personal data.
- **D:** a store outage. Control: writes fail fast (`IPB-STOR-002`) and the caller's outbox retries; reads fail over to the DR replica; queue enqueue failures go to the outbox; Temporal outages pause timers.

- **T (retention shortened, or a recording altered, PR-FBX-27, R1-D-42):** Control: `extendRetention` refuses any date not later than the current one and objects without COMPLIANCE retention; S3 Object Lock itself refuses shortening; `assertImmutable` compares the stored SHA-256 checksum with the hash recorded at write. Residual: a checksum proves the bytes stored match the bytes sent, not what the egress worker captured; the V-CIP manifest (M24) carries the chain from capture.

- **BUREAU and AA_FIU (PR-FBX-28, R1-D-43, ADR-0003), interfaces and fakes only.** **I (personal and financial data leaving or lingering):** requests are REGULATED and `IN`; a pull or a consent request needs the product's consent receipt; raw reports and FI payloads go to the tenant's STORAGE by reference with their SHA-256 and never sit in logs, events or the ledger; results name the subject by the product's reference and carry no PAN and only masked accounts. **S/T (forged callbacks):** both webhooks are parsed only for an id and the state is read back from the vendor. **E (fetching beyond consent):** the AA contract refuses a fetch under a consent that is not ACTIVE, expired, outside its data range or for an FI type outside it or revoked. **R:** every result carries the vendor reference, adapter and format or API version. Residual: no vendor adapter yet, so signature checks on vendor webhooks, the AA's JWS detached signatures and the CICs' transport rules are specified when the owner's sandbox documents arrive; the hard-enquiry footprint is the product's decision (consent and purpose), not the port's.

- **KYC alternative `idfy-kyc` and per-method routing (M25, R1-D-45).** **I (identity data leaving):** only the fields the method needs leave (PAN, name, date of birth; face images by STORAGE reference, checked against their SHA-256 first), over HTTPS to the allow-listed IDfy host from the egress client; results carry no Aadhaar number (a twelve-digit run in a reply is refused) and nothing the vendor returns is stored; the task and group ids carry no personal data. **S (credentials):** the account id and API key come from SECRETS (`secrets/<env>/kyc/idfy/…`). **T (a wrong vendor reached):** `kycMethodRouter` moves to the next adapter only when one is off, unavailable or lacks the method, so a vendor's refusal about the customer is never retried elsewhere. Residual: the request and result shapes are stub-shaped until the owner's IDfy sandbox exists, so the adapter is off and `unproven`; IDfy's webhook signing is not used (no asynchronous methods).

### 3.11 `@infrabyx/connectors` EMAIL, SMS and WHATSAPP (built)

- **S:** forged delivery, bounce or status webhooks. Controls:
  - SES events arrive through SNS: SignatureVersion 2 only, certificate host pinned to ap-south-1/2, one TopicArn, a one-hour timestamp window, and subscription confirmation followed only to an SNS host after verification (C-13).
  - Meta webhooks: `X-Hub-Signature-256` over the raw body; the subscription handshake compares the verify token in constant time.
  - Vendors that do not sign (Brevo, MSG91, Gupshup SMS and WhatsApp) present our C-19 secret, compared in constant time:
    - as a bearer header (Brevo, MSG91);
    - as the `ipb_token` URL parameter when the vendor can only call a URL (Gupshup), which ingress logs must redact;
    - Brevo also needs its published source ranges.
  - Failures answer `IPB-API-018` without logging the body.
- **T:** a replayed webhook processed twice. Control: every event carries a stable vendor event id for the module inbox (@IPB-02-AT-05 scenario 2).
- **I:** CONFIDENTIAL content inline, or documents attached:
  - bodies above INTERNAL are refused before any request;
  - attachments must come from GENERAL or PUBLIC_ASSETS storage, at most 10 files and 10 MiB;
  - anything else goes as a secure link.
- **I:** recipients at a GLOBAL vendor. Control: X-06; Brevo, Gupshup WhatsApp and Meta refuse to start without a DPA reference; Brevo's manual suppression is refused because it would need a contact record (PL2-D-64).
- **I:** credentials in URLs. Control:
  - Gupshup SMS credentials go in a POST body;
  - MSG91's key goes as a header, the balance check included;
  - no API key is put in a query string.
- **T:** non-DLT SMS content. Control: template, header, entity id and variable count are checked before any request; the Gupshup text is rendered from the registered DLT text.
- **E:** marketing sent by mistake. Control: `mkt.meta.enabled` (default false); the template category is read before every send and marketing templates and submissions are refused while it is off (OWN-08).
- **D:** a vendor outage. Control:
  - SES pauses map to `IPB-PORT-002` (reputation block) so the router can fail over;
  - Brevo serves as a failover target only for brands whose domain is authenticated on Brevo;
  - SMS fails over msg91 → gupshup-sms with the same DLT mapping;
  - WhatsApp has no failover between BSPs.

### 3.12 `@infrabyx/connectors` PAYMENTS (built, test mode only)

- **T:** amount tampering or rounding. Control: integer paise in and out, INR only; Cashfree decimals are written as exact text and read back exactly or refused (P-04).
- **S:** a forged webhook or checkout return. Controls (P-09):
  - Razorpay `X-Razorpay-Signature` and Cashfree `x-webhook-signature` are checked over the raw body; Cashfree's timestamp must be within ±5 minutes.
  - A Razorpay checkout return is checked by its `razorpay_signature`; a Cashfree return by fetching the order server-side.
  - Client-side success is never trusted.
- **E:** a refund without approval, or more than was paid. Control:
  - an approved R3 request for exactly the refund's payload is required (`IPB-SEC-006`);
  - the PA's own refund list is read at execution;
  - the cap is the captured amount minus earlier refunds;
  - an agent can only make the request (P-07).
- **T:** a duplicate charge or refund after a timeout. Control: the idempotency record is pending before the call; orders are looked up at the PA by our reference first; refunds and mandates that cannot be resolved go to the human queue and are never retried automatically (P-05, P-07).
- **E:** live money by accident. Control: no live key anywhere in this repository, CI or non-production; the env guard and the adapters refuse live credentials outside prod/dr (P-03); `kill.payments` stops new money operations (P-12).
- **D:** a PA outage. Control: new orders fail over Razorpay → Cashfree; refunds, mandates, captures and checkout sessions stay with the PA that owns them (P-08).
- **I:** payment details beyond what billing needs. Control:
  - only IDs, amounts, statuses, method categories and times leave the adapters (P-10);
  - the customer phone and email reach only Cashfree, which requires them;
  - card data never touches Infrabyx (hosted checkout, SAQ A).

### 3.13 `@infrabyx/rules` and the RULES engine adapters (built, PL3 session 2)

- **T:** a decision that defaults to allow. ### 3.27 `@infrabyx/ui` and `@infrabyx/a11y` (built, PL5 session 2)

The shared components render on the server with no client script. The accessibility kit runs at build and CI time. Its only runtime piece is the client hooks, which read preferences and write to live regions.

- **T/I (XSS):** a component or the accessibility statement renders text supplied by an editor or product. Control: components use React's escaping and never `dangerouslySetInnerHTML`. `renderStatementHtml` escapes every value, and the conformance table comes only from computed status. Components set no inline styles, so the CSP needs no `unsafe-inline`. Click-to-load embeds stay inert inside `<template>` until the person asks, and their URLs are rebuilt for youtube-nocookie or Vimeo with `dnt=1`.
- **T (claims):** someone types "Conforms" into the accessibility statement. Control: the release record schema is strict and has no status field. Status is computed from CI results, AT runs, open defects and the signed checklist, and an open P1 or P2 is reported as `IPB-A11Y-010` (IPB-06-57).
- **T (overlays):** an accessibility overlay is added to a page or the build. Control: `overlay-scan` fails the build and `scanText` blocks a page-config save (`IPB-A11Y-003`). The signature list is stored in parts, so the package does not flag itself.
- **E (gate tooling):** the gate injects axe-core and HTML_CodeSniffer into pages through `page.evaluate`. Control: this happens only in the CI test browser against the site under test, never in a served page. The site's CSP is not relaxed for tests.
- **Supply chain:** `axe-core` 4.14.0 (MPL-2.0) and `html_codesniffer` 2.5.1 (BSD-3-Clause, last released 2020) are used only by the gate, never shipped to visitors. `playwright-core` is an optional peer. `lighthouse` was refused by the trust policy (`puppeteer-core@25.14.0` has no trust evidence; OWNER-QUESTIONS #51) and is not installed.
- **Residual:** `html_codesniffer` is unmaintained; a rule gap there is covered by axe on the same routes. The Lighthouse score is not measured live until #51 is resolved.

### 3.28 `@infrabyx/hlp` and `@infrabyx/brand` (built, PL5 session 3)

`hlp` is build-time tooling plus pure lookups. `brand` adds the `brand` schema (packs, immutable revisions, the host map), logo storage through STORAGE, and the hooks to NOTIFY (email identity) and to the policy set.

- **T (logo upload):** a hostile SVG (script, event attributes, `foreignObject`, external `use`, CSS `@import` or `url()`, entity expansion). Control: an allow-list sanitiser rejects DOCTYPE and malformed XML (`IPB-BRD-001`), removes everything else not listed and reports it, and re-serialises the cleaned tree. Only the sanitised file is stored, tagged and hashed. A revision counts as sanitised only when the stored object carries the tag and its hash matches.
- **S (host spoofing):** a request with a forged `Host` or `X-Forwarded-Host` selects a partner's brand. Control: only published, verified hosts in `brand.host` select a pack. `X-Forwarded-Host` never does, and a mismatch is reported as a security event. Unknown hosts get the default pack with `noindex` (`IPB-BRD-007`). A host belongs to one pack group-wide (primary key; `IPB-BRD-002` at save).
- **E/T (publish):** one person publishing a brand, or changing the legal entity without legal review. Control: the checker and the legal reviewer are each recorded once and never equal the maker (service checks and database constraints). The approver differs from the legal reviewer, the body of a revision never changes (trigger), and a rollback is a new revision under the same rule. Every step writes the audit ledger.
- **T (claims and contrast):** an unreadable brand is published. Control: the contrast guard refuses it (`IPB-BRD-003`), the refusal is ledgered with `ContrastGuardFailed`, and the database refuses a published revision without the guard and sanitiser flags.
- **I:** drafts carry the legal entity and email identity before publication. Control: revisions are INTERNAL and readable through RLS, written only in a platform context. Published values are public by nature (footer, manifest).
- **Residual:** email-domain verification and policy-set publication are hooks; until NOTIFY and `cms` wire them, a deployment must supply them, and the defaults refuse publish. The help registry lint is not yet in `verify` (session 7).

### 3.29 `@infrabyx/cms` core (built, PL5 session 4)

`cms` adds the `cms` schema (content items, immutable revisions, approvals, redirects, media metadata, the Claims Register, preview tokens), media files through STORAGE, the public read API and two workers (scheduler, purge). Content is platform rows: any context reads them, only a platform context writes them.

- **E (Studio access):** a tenant admin with a stolen Studio URL publishes, or an agent publishes. Control: every Studio write needs the platform context (`IPB-UX-011` otherwise) and the refused attempt is ledgered (`cms.access.denied`, `@IPB-04-AT-93`). Agents are refused every transition but draft and submit (`IPB-SEC-004`), and IPB-02-11 keeps them out of the platform scope entirely.
- **E/T (publish):** one person publishes, or a legal page skips counsel. Control: the checker and the legal reviewer are never the maker and never each other (service checks and table constraints on `cms.approval` and `cms.redirect`); legal-review types and lint flags route to `legal_review`, and approve or publish without the legal sign-off is `IPB-CMS-005` (`@IPB-04-AT-03`). Any edit voids the approval; the scheduler publishes only the approved revision, otherwise it skips and ledgers the skip (`@IPB-04-AT-101`).
- **T (stored content):** a revision rewritten after approval. Control: an update trigger refuses any change to `cms.revision`; rollback is a new revision (`@IPB-04-AT-01`).
- **T/I (XSS):** script, event handlers, `javascript:`/`data:` URLs, inline SVG or iframes in rich text or links. Control: rich text is portable-text JSON, never HTML; one allow-list sanitiser runs on import, at save and again at render, and every text node is escaped (`@IPB-04-AT-20`); block links and CTAs accept only site paths, anchors, `https:`, `mailto:` and `tel:`.
- **T (uploads):** a hostile SVG or metadata in images. Control: SVGs go through the brand sanitiser and only the result is stored; JPEG APP1/APP13 and PNG text and EXIF chunks are stripped; files are keyed by SHA-256. Raster re-encoding is off (#43, #53).
- **S/I (preview):** a guessed or leaked preview link. Control: a random 32-byte token stored only as its SHA-256, at most 24 hours (database check), revocable; the page is `noindex` and `no-store` (`@IPB-04-AT-05`).
- **T (claims):** an unsupported figure, certification or category claim reaches the site. Control: the claims lint at submit (`IPB-CMS-010`, `-012`, `-014`, `IPB-TRUST-006`), with failures ledgered and emitted as `ClaimsLintFailed`; only a legal reviewer other than the proposer activates a claim.
- **D/T (public API):** writes or scraping through `/api/public/v1`. Control: GET and HEAD only (405 otherwise, no row changes, `@IPB-04-AT-14`), published revisions only, ETag, a rate-limit hook.
- **T (redirects):** an open redirect or a loop. Control: targets are site paths or `https:` only; loops and chains are refused at save (`IPB-CMS-009`); manual and imported redirects need a checker and the legal reviewer before they are active.
- **I (deletion, OWNER-QUESTIONS #48):** content kept forever, or deleted early. Control: soft delete with a restore window; the purge deletes only rows soft-deleted more than 90 days ago (restrictive policies refuse any other delete), one ledger entry per sweep.
- **E/T (policies, session 5a):** a legal document published by one person, changed after approval, or published with unreviewed text. Control: legal reviewer maker, super admin checker and DPO for privacy-class templates, never the maker (service checks and table constraints); approval snapshots parameters and the rendered hash and a trigger refuses any later edit (`IPB-POL-008`); counsel markers, unresolved parameters, banned wording, stale citations and the notice period block submission and approval (`@IPB-05-AT-03`…`-09`). A MAJOR Terms change takes effect only 30 days after users are notified (the later of the notice published and sent, append-only `cms.policy_notice`, never backdated; #55), so an approval alone cannot start the clock.
- **I/T (resources, forms, pricing; session 5b):** a gated file leaked by URL, form data kept in the CMS, or a typed price. Control: gated files sit in a private bucket and are served by a 300-second presigned URL; downloads keep the CRM lead reference, never field values; form submissions keep only ids, the consent receipt and state, also on failure (`@IPB-04-AT-47`); a honeypot and a rate-limit hook stop scripted submissions; the pricing copy has no price field and figures come only from the catalogue (`@IPB-04-AT-30`).
- **Residual:** the scheduler and the purge run as service principals carrying `PLT_CONTENT_EDITOR`, because IPB-02-11 opens the platform scope only to PLT roles (PL5-D-06); they call only the scheduled publish, unpublish and purge paths. Rate limiting of the public API and of forms is a hook the site must supply. Downloads and form submissions also run as such service principals (PL5-D-08) and only insert their own rows.

### 3.30 `@infrabyx/consent` (built, PL5 session 5c)

`consent` adds the `consent` schema (texts, the append-only consent ledger, acceptances), the CMP components and the first-party controller, the consent endpoint, script gating and the purge with the `svc_consent_sweep` reader.

- **I (tracking before consent, O-2):** a third-party tag or pixel loads before or without consent, or on a sensitive or authenticated route. Control: the server never renders an active third-party tag (inert `text/plain` declarations activated by the first-party controller for consented categories only); marketing tags on the locked sensitive routes or on app routes are dropped and reported (`IPB-WEB-005`); only `none` adapters exist at launch; GPC keeps analytics and marketing off (`@IPB-04-AT-81`, `-83`, `-85`, `-86`).
- **T/R (consent evidence):** a choice rewritten or the wording shown later disputed. Control: records and acceptances are append-only for every role (trigger); each record keeps the exact text and its version and is ledgered; texts are DPO-drafted, legal-approved and immutable once approved.
- **S (cookie forgery):** a forged `ibx_consent` cookie activates scripts. Control: the cookie only reflects the visitor's own choice in their own browser; it is parsed strictly, names a ledger receipt, and a forged value can at most enable scripts for that same visitor; nothing server-side trusts it beyond rendering.
- **I (deletion, #48, #57):** consent evidence kept forever or deleted early. Control: a restrictive delete policy allows deletion only 3 years after a record's replacement or cookie expiry, or after the end of a marketing lead's form consent (24 months after the last interaction, unless the person has an active relationship; `consent/0002`); a legal hold placed by a PLT_LEGAL_REVIEWER stops every deletion for the person; the sweep's reader sees ids, tenants and times only, and every batch is ledgered.
- **Residual:** the end of life of a form consent depends on the product reporting interactions and relationships (`ConsentSubjects`); a product that never reports keeps the 24 months from the consent record itself, which deletes sooner, never later. The controller is hand-written JavaScript without a build step; it is reviewed with the site in session 7 under the nonce CSP.

- **R/T (product-purpose consent, PR-FBX-26, R1-D-38):** a consent claimed for a text the person never saw, or a notice changed after consent. Control: notices are drafted and approved by two different people in the tenant, immutable once approved (trigger), hashed by the database; each grant stores the notice id, version, language and hash; records are append-only and ledgered; agents cannot record consent. **I:** the subject reference is CONFIDENTIAL and never leaves in the event. Residual: no retention rule yet (OWNER-QUESTIONS #95).

### 3.31 `@infrabyx/feedback` (built, PL5 session 6)

`feedback` adds the `feedback` schema (items, their status history), the widget and its first-party controller, the feedback endpoint, the hand-off to OH (SUPPORT, BACKLOG), the OH status consumer and the sweep with the `svc_feedback_sla` reader.

- **I (over-collection, `@IPB-04-AT-91`):** the widget or a crafted request sends page content, form values, screenshots, URLs or personal numbers. Control: a strict allow-list of fields; forbidden or unknown fields, a URL or query string, and any personal number or secret the AI scrubber detects refuse the whole request (`IPB-FB-001`) before anything is stored; there is no column for page content or screenshots; routes are reduced to patterns and user agents to families.
- **D/S (spam):** floods of feedback or scripted submissions. Control: honeypot, the app's per-client limit and 10 items an hour per person (`IPB-FB-002`); no CAPTCHA puzzle (IPB-06-40).
- **I (status link):** guessing another person's status page. Control: the link needs the item id and a 192-bit view key whose hash alone is stored, in the right tenant; signed-in users see only their own items; RLS keeps tenants apart.
- **T/R (SLA evidence):** a missed accessibility timer hidden or reported twice. Control: `sla_breaches` is append-only (trigger), each breach is ledgered and emitted once; the submission itself never changes after it is stored.
- **I (deletion, #48):** items kept forever or deleted early. Control: a restrictive policy allows deletion only 3 years after closure; the history goes with its item only; the sweep's reader sees ids, tenants, states and timers, never a summary or a person.
- **Residual:** OH receives the scanned summary (up to 500 characters) and route pattern. The status consumer trusts the event's tenant; the Ecosystem envelope's signature check belongs to the product's event intake.

### 3.32 `@infrabyx/trust` (built, PL5 session 6)

`trust` adds the `trust` schema (the vendor-assurance mirror, acknowledgements, NDA acceptances, requests, subscriptions), the mirror consumer, the tenant room, the Trust Centre data, `security.txt` and the sweep with the `svc_trust_sweep` reader.

- **T/E (system of record, `@IPB-08-AT-01`):** a product principal, staff included, creates or edits an assurance document. Control: RLS lets only the mirror consumer's principal (`svc_trust_mirror`) write the mirror tables; announced metadata and digests are immutable (trigger), validity can never be extended and versions are never deleted.
- **T (tampered file):** OH's storage serves a file that is not the announced one. Control: a version becomes visible only after its digest matches; a mismatch keeps the previous verified version visible and raises `IPB-TRUST-009`; the daily reconciliation compares the whole publication digest.
- **I (gated documents, `@IPB-08-AT-10`):** a tenant obtains a gated or another tenant's document, or an unwatermarked original. Control: only VISIBLE PUBLIC, TENANT and GATED_NDA versions are listed; NDA-gated ones need an accepted NDA (`IPB-TRUST-002`); every gated download is refused with `IPB-TRUST-012` until watermarking exists (#44), so no unwatermarked gated original is served; AUDITOR documents and per-tenant publications are not exposed in PL5. Tenant rows are under RLS.
- **I (acknowledgement data, IPB-08-38):** names or e-mails in acknowledgements, or personal details in purposes and requests. Control: acknowledgements keep the user id, role and IP and UA classes only; purposes and request descriptions are PII-scanned and refused if they carry personal numbers.
- **R (evidence):** an acknowledgement rewritten. Control: everything except the sync stamp and the legal hold is immutable (trigger); NDA acceptances are append-only; every action is ledgered.
- **I (deletion, #48):** acknowledgements deleted before 10 years after their version ended, or under legal hold. Control: a restrictive delete policy enforces both; only a PLT_LEGAL_REVIEWER sets holds, ledgered in the tenant's chain; the sweep's reader sees ids, tenants, versions and timers only.

### 3.33 MEDIA port and the owner answers #53–#57 (PL5-D-11)

The MEDIA port (`@infrabyx/contracts` `media.ts`) with the `sharp` reference adapter (libvips under the owner's licence exception) and the `passthrough` alternative in `@infrabyx/connectors/media`; renditions in `cms.media.renditions` and PNG favicons from the sanitised logo.

- **T/D (decoder attack surface):** a crafted image or SVG exploits libvips or exhausts memory. Control: the header is parsed and checked against the declared type and a 40-megapixel limit before libvips sees the bytes (`IPB-SEC-013`, `IPB-SEC-014`), libvips enforces the same limit with `failOn: "error"`, its cache is off, only JPEG, PNG, WebP and AVIF are re-encoded (GIF and video are not), and only the brand sanitiser's SVG output is rasterised (DOCTYPE, entities, scripts, event handlers and external references refused, `IPB-SEC-012`); uploads are platform-scope Studio actions only.
- **I (metadata):** EXIF, GPS or author data survive into public files. Control: JPEG and PNG metadata is stripped on upload as before; every rendition is re-encoded without EXIF, XMP, IPTC or the ICC profile (contract case).
- **T (supply chain, licence):** a modified or statically linked LGPL build enters the product. Control: the licence check accepts only `@img/sharp-libvips-*` with exactly `LGPL-3.0-or-later` and refuses any `AND` expression with a disallowed part (the wasm32 builds); `sharp` is pinned, 7 days old, with provenance, and is an optional peer, loaded only by the adapter; `vendor-import` keeps it inside `packages/connectors`.
- **Residual:** libvips runs in the web process, not a separate worker (IPB-01 says "in worker"); a product that re-encodes at volume should run uploads in its worker. Tracked in §6.

### 3.34 `apps/public`, the group site (built, PL5 session 7; PL5-D-13)

The reference group website on Next.js 16 (`@infrabyx/public-site`, private, never published). It reads published content, policies, brand packs, consent texts and the trust mirror in-process through the kernel, and writes only through three endpoints: consent choices, CMS forms and feedback.

- **S/T (script injection):** a CMS body or a crafted path runs script in the visitor's browser. Control: a per-request nonce CSP from `proxy.ts` (`script-src 'nonce-…' 'strict-dynamic'`, `object-src 'none'`, `base-uri 'none'`, `frame-ancestors 'none'`, `form-action 'self'`, no `unsafe-inline`); rich text is the CMS sanitiser's output only; the three first-party controllers are served from the site's own origin under the nonce; the e2e gate asserts the headers.
- **T (forged writes):** a third-party page posts consent, a form or feedback as the visitor. Control: every POST checks `Origin` (or `Referer`) against the site's own origin; forms carry a honeypot; the CMS form and feedback services apply their own limits and minimisation (PL5-D-08, PL5-D-10); consent is written to the ledger with the exact text version.
- **I (tracking before consent):** a page loads anything from another origin before or after a choice. Control: no font CDN, no analytics, no third-party scripts; images and styles are `'self'` only; the gate records every request in Chromium for each consent path and fails on any other origin (`@IPB-04-AT-80`, `@IPB-04-AT-85`).
- **D (database lookups per request):** each request resolves the pack, and each unknown path makes the proxy look up a redirect or tombstone. Control: lookups are indexed reads through the kernel on a bounded pool (10 connections); rate limiting belongs to the edge in front of the site (PL6 deployment).
- **E (fixtures in production):** fixture adapters (fake CRM, HR, OH desk, trust feed) or directory storage accept data in a real environment. Control: `siteEnv()` refuses `APP_FIXTURE_ADAPTERS` and `STORAGE_DIR` outside local, dev, test and preview, so the process exits with code 78; without real adapters each port answers `IPB-PORT-001`. Seeds refuse prod, dr and pre-prod (`SEED_REFUSED_ENVS`).
- **I (unmapped hosts):** a host not mapped to a pack serves the product's default pack under another name. Control: such responses carry `noindex` and the generated files (sitemaps) are empty for them.
- **Residual:** the site has no edge rate limit or WAF of its own yet (PL6 deployment); the fixture CRM and HR keep form data in memory only, so local and test submissions are lost on restart, by design.

### 3.35 `@infrabyx/ui/studio`, the Studio screens (built, PL5 session 8; PL5-D-14)

Server-rendered screens and form handlers over the existing Studio services; no new table or port. Each app mounts them behind its own sign-in and AUTHZ check (`apps/console` in session 9).

- **E (bypassing a rule from the screen):** a screen offers a move the person may not make. Control: screens only show and post; every move, role, maker-checker rule and lint is checked in the service, so a forged post gets the same `IpbError` as any other caller.
- **S/T (forged posts):** another site posts to a Studio action. Control: the app's actions must check the request origin (Next server actions do; a POST route uses the same `sameOrigin` check as the group site); Studio pages are `noindex` and framed by nobody (`frame-ancestors 'none'`).

Control: the route takes own keys of the section's handler map only (`Object.hasOwn`) and answers 404 otherwise; the console e2e test posts four such names (R1-D-14).

Control: React escapes all text; the post-redirect-get result is base64url JSON of short strings, decoded to text only, size-capped, and holds no authority; JSON bodies are parsed and checked by the service, never rendered as HTML.
- **I (preview links):** a preview path is shown in the notice once after it is created; it expires (`cms.preview.ttl_hours`) and can be revoked from the item or the Preview links screen.
- **I (visitor text and consent wording):** the feedback queue holds visitors' words and the consent texts are legal drafts. Control: `FeedbackService.queue` needs PLT_SUPER_ADMIN or PLT_ACCESSIBILITY_LEAD and `ConsentTexts.list` needs PLT_DPO or PLT_LEGAL_REVIEWER, both in the platform context (PL5-D-15); feedback, trust documents and prices are read-only in Studio.

### 3.36 `apps/console`, the reference Studio console (built, PL5 session 9; PL5-D-16)

A private Next.js app that mounts the Studio screens; every change goes through the package services and the kernel.

- **S (who is signed in):** the reference sign-in is a fixture persona cookie. Control: `consoleEnv` refuses fixtures outside local, dev, test and preview (exit 78), so in staging and above no persona is accepted and the AUTHZ port is unconfigured (`IPB-PORT-001`): nothing opens until a product wires its IDENTITY sign-in and AUTHZ adapter. ### 3.37 Container images of the deployables (built, PL6 session 1a; PL6-D-02)

One Dockerfile (`infra/docker/next/Dockerfile`) builds `apps/public` and `apps/console`; the `containers` CI job builds, scans and tests every image and pushes none (OWNER-QUESTIONS #67).

- **T (a tampered base or tool image):** Control: the Node base is pinned by tag and digest (`ipb-check`), and hadolint and Trivy run from Docker Hub images pinned by digest, each published at least 7 days before pinning (PL2-D-32). The lockfile is installed frozen; the build has no registry token (workspace packages are linked, not fetched).

The probes skip the CMS lookup in the proxy and return only status, latency and time (no host, version or error text).

### 3.38 The local Compose stack (built, PL6 session 1b; PL6-D-03)

### 3.39 The shared Helm chart and admission policies (built, PL6 session 2; PL6-D-04)

`infra/helm/infrabyx-app` deploys every product workload; `infra/policy/kyverno` is the cluster's second line. Nothing is deployed from this repository.

- **E (a workload escaping its container):** Control: the chart's security context is not configurable (UID 10001, read-only root, no privilege escalation, every capability dropped, `RuntimeDefault` seccomp, no service-account token); Kyverno refuses pods without it, with host paths or host namespaces, and with tag-only images (`kyverno test`).
- **I (secrets in manifests):** Control: secrets reach pods only through the Secrets Store CSI mount (read-only), required from staging upwards; secret-named plain variables fail rendering there (`IPB-ENV-003`); the migration hook reads its URL from the mount (`--db-file`).

The environment comes from the namespace label, which a pod cannot set, and an unlabelled namespace is enforced.
- **S and I (lateral movement):** Control: a default-deny NetworkPolicy in and out, peers listed per deployment, DNS only by default.
- **Tampering with the environment rules:** Control: a seed profile in prod, dr or pre-prod and a Supabase host from staging up fail rendering (`IPB-ENV-001`, `IPB-ENV-002`; `@IPB-01-AT-12`).
- **Residual:** a cluster administrator who mislabels a staging or production namespace as a lower environment turns enforcement into audit; namespace labels belong to the cluster bootstrap and its review. The chart cannot see the cluster; a product could deploy without Kyverno installed, which the IPB-01 Terraform `kubernetes` module (session 3) is to install. `helm diff` is not run.

### 3.42 `apps/reference` api and worker (built, PL6 session 4a; PL6-D-08)

The reference API (NestJS 11) and its worker on the platform packages; the template products copy. Flows: browser → api (session cookie or bearer) → IDENTITY (code exchange, token verification), AUTHZ (one check per route), the kernel (forced RLS, the ledger and the outbox in one transaction); worker → QUEUE consumers and the same health probes.

- **S (a forged or replayed session):** Control: the authorisation code flow uses PKCE S256 with a state kept in a short-lived HttpOnly cookie and checked at the callback; tokens are verified by the IDENTITY port on every request (Keycloak JWKS, or the fixture's per-process HMAC key, which exists only in local, dev, test and preview); MFA is asserted for the roles that require it (IPB-02-02). Residual: the session cookie lives as long as the access token with no refresh; the fixture IdP has no brute-force protection (Keycloak's own applies with the real adapter).
- **T (cross-site requests on the cookie session):** Control: `SameSite=Lax` and `HttpOnly`, `Secure` on https; every state-changing route is a JSON `POST` or `DELETE` under the authentication guard; CORS is not enabled. Residual: a product that enables CORS for a separate web origin must add a CSRF token or `SameSite=Strict`.
- **R:** Control: every write runs in `kernel.mutate` with its ledger entry and its outbox event in the same transaction; retraction is an R2 request decided by a checker (never the maker, never an agent); deletion ends in the locked verb, refused to agents in the kernel and denied in the Cerbos policy.
- **I (what an error or a probe reveals):** Control: problems carry a code, a title and a safe detail, never SQL, stack traces or hosts; `/health/ready` names ports and adapters only; security headers (`nosniff`, `DENY`, `no-referrer`, `no-store`, a `default-src 'none'` CSP) on every response; `x-powered-by` off.
- **D:** Control: Express's default body limit; list reads capped at 200 rows; health probes time out at 2 s and answer 503 fail-closed. Residual: no rate limit at the API (the ingress or the IdP applies one).
- **E:** Control: the tenant context comes only from verified claims (`TenantContextInterceptor`); AUTHZ decides per route with the principal's roles and the tenant attribute; a sandbox-tenant owner reading a demo greeting gets 404 under RLS (NN-01).
- **Residual:** the fixture personas have fixed ids and roles by design (seed tenants only, IPB-11-26); products must never enable `APP_FIXTURE_ADAPTERS` outside the four fixture environments (the env check refuses it).

### 3.48 The outbox relay as a service reader (built, R1 item 1; R1-D-01)

`OutboxRelay` in `@infrabyx/tenancy` relays module outboxes to the QUEUE as `SVC_OUTBOX_RELAY`, the one service reader that also writes.

- **E (the relay reading or changing more than its outboxes):** Control: its database role starts with no grant; `tenancy.register_outbox()` grants select of the relayed columns and update of `dispatched_at` and `attempts` on one registered `<schema>.outbox`, and `audit/0002` the ledger append; any other table or column is refused by PostgreSQL (`42501`, proven in the integration tests). The kernel admits only `<schema>.outbox.dispatch` for this reader, in a tenant context.
- **T (marking another tenant's events dispatched):** Control: there is no platform-scope update policy; every update runs in the row's own tenant context under the outbox's tenant policy, so a batch can only touch its tenant's rows.
- **R (an unrecorded relay):** Control: the cross-tenant discovery read is ledgered per tenant (`platform.service_read`), and each batch writes `<schema>.outbox.dispatch` in its tenant's ledger in the same transaction.
- **S (registering a table that is not an outbox):** Control: `register_outbox` is executable by `app_migrate` only, validates the schema name, the columns and forced RLS, and grants on that schema's `outbox` table only.
- **Residual:** the event envelope is read by the relay (it must be, to deliver it); envelopes carry no secrets by the IPB-10 event contract.
- **E (the read-only role writing through the relay role; found by Udofin, PR-UDF-016):** `tenancy/0003` granted `svc_outbox_relay` to `app_ro` and `app_rw` with the default INHERIT, so both held its writes (the ledger append, `dispatched_at` and `attempts`) without switching. Control: `tenancy/0004` revokes it from `app_ro` and makes every `svc_*` membership of `app_rw` and `app_ro` INHERIT FALSE, SET TRUE; `app_ro` and `app_rw` are NOINHERIT, so later grants default the same (R1-D-11). The integration test proves a login holding only `app_ro` is refused every write and the switch to `svc_outbox_relay` (42501), and that no role reachable from a read-only or auditor role holds a write privilege.
- **D (events that never leave their table; PR-LDC-35, R1-D-112):** registration was opt-in per module, and none of the 15 platform outboxes was registered, so their events were never relayed. Control: each package's own migration registers its outbox (the same column grants and discovery policy as above, nothing wider); `ipb-check` fails a package that creates an outbox without registering it; the reference API suite checks the registered list equals every outbox table. Rows written before the fix are relayed on the first pass after migration; consumers are idempotent on the event id.

The Studio page editor edits a page's blocks through forms (`@infrabyx/ui/studio` `BlockEditor` and `blockHandlers`, with the block forms and the rich text codec from `@infrabyx/cms` `BLOCK_EDITOR`). It is a new way into the same save: every operation becomes one `CmsStudio.saveDraft` call.

### 3.50 The Ecosystem inbox (built, R1 G2; R1-D-15)

`EcosystemInbox` in `@infrabyx/tenancy` stores inbound Ecosystem events in the consuming module's `eco_inbox` before processing (`tenancy.create_ecosystem_inbox`, migration `tenancy/0006`) and processes them in `seq` order per subject.

- **T and R (a replayed or doubled event acting twice):** Control: the event is stored first, unique by `(tenant, source, id)` and by `(tenant, type, business key)`; a duplicate of either is acknowledged and never handed to the handler; an event at or below the subject's position is skipped; every receive, step, failure, break and repositioning is ledgered in the same transaction.
- **T (out-of-order events applied in the wrong order):** Control: an event ahead of the next `seq` is parked, never processed early; after 15 minutes the product's replay fetches the gap, and a gap still open becomes a break the product raises as `ReconciliationBreakRaised`; only an operator's `setPosition` from the owner's snapshot reopens the subject.
- **S (a sandbox event in production):** Control: an event whose `environment` differs from the inbox's is refused (`IPB-API-005`), as is an envelope that does not validate (consent or legal basis with personal data included).
- **I and E (one tenant's events seen or changed by another):** Control: both tables have forced row-level security by the consuming tenant; `app_rw` may select, insert and update, never delete; the function that creates them is executable by `app_migrate` only and validates the schema name.
- **D (a failing handler blocking a subject):** Control: the handler's transaction rolls back; the attempt is counted in its own transaction; after `maxAttempts` (5) the event is `failed` and the subject waits for an operator instead of retrying without end.
- **Residual:** signature verification of the inbound delivery (Standard Webhooks, RFC 9421) happens before `receive`, in the product's gateway; the detached JWS of regulated messages is G5. Inbox rows are kept until the product decides their retention (no purge is built; retention is the owner's).

### 3.51 JWS for regulated messages (built, R1 G5; R1-D-08, R1-D-17)

`signRegulatedMessage` and `verifyRegulatedMessage` in `@infrabyx/crypto` sign and check the detached JWS that Ecosystem Spec §3.6 stores with each regulated message (`isRegulatedMessage` in `@infrabyx/contracts/events` names them).

- **S and T (a forged or altered regulated message):** Control: ES256 only, through an allow-list that refuses `none`, every `HS*` and every other algorithm; the signature covers the JCS form of the whole CloudEvent; the key is in KMS and named by `kid`; a DER signature, an attached payload or non-canonical base64url is refused.
- **S (algorithm or key confusion through the header):** Control: the protected header must hold exactly `alg`, `kid`, `typ`, `iat` and `jti`; `b64`, `crit`, `jku`, `jwk`, `x5u`, `x5c` and any other member are refused; keys come only from the verifier's own key ring, never from the message, and the ring takes EC P-256 keys only.
- **R and T (a replayed message):** Control: `iat` must lie within five minutes back and one minute ahead, and a `jti` is accepted once (the replay store); a message that fails any other check never claims its `jti`, so a forgery cannot block the real one.
- **D (a key rotation dropping messages):** Control: the key ring holds the current and the previous key, each with its validity window; messages signed during the overlap verify with either.
- **Residual:** `MemoryReplayStore` is per process; a product with several verifier instances backs `ReplayStore` with shared storage, or relies on the Ecosystem inbox's `(source, id)` uniqueness as the durable second line. RFC 9421 transport signatures are the product gateway's.

### 3.52 Scheduled per-tenant jobs (built, PR-UDF-013; R1-D-12)

`TenantSweep` in `@infrabyx/tenancy` lists the tenants for a product's scheduled jobs, and `AuditSweep` in `@infrabyx/audit` runs the IPB-02-51 ledger jobs (weekly verification, daily anchor) for each.

- **I and E (a job seeing more than its tenant):** Control: the list is a `SVC_TENANT_SWEEP` read whose database role selects only `id` and `status` of `tenancy.tenant` (anything else is 42501, tested); each job then runs in its tenant's own context under RLS, as the job's service principal, and sees only that tenant's rows (tested: one tenant visible per run).

- **E (a job holding reader rights or reader limits):** Control: the reader and the job principal are separate; a context holding a service-reader role is read-only in the kernel, so the job runs as `svc_tenant_job` (or the product's own principal), never as the reader; the reader's role is switch-only (R1-D-11).
- **D (one tenant blocking the rest):** Control: a tenant's failure is reported by its error code and the sweep continues.
- **Residual:** scheduling, retries and alerting on `broken` or `failed` are the product worker's (`docs/product-guide.md` §7c).

### 3.53 Customer sign-in: one-time codes and DPoP (built, #84; R1-D-18, R1-D-19)

`CustomerIdentityPort` signs in end users who are not staff, in a customer realm (Keycloak, with the `ipb-customer-otp` extension) or organisation (Zitadel) per product. Codes go out through NOTIFY; sessions are bound to a per-device ES256 key by DPoP and checked by `verifyDpopProof`.

- **S (guessing or brute-forcing a code):** Control: six digits from a CSPRNG, 300 s, 5 tries per code; at most 10 codes per 10 minutes per account, 30 s apart; back-off after 5 consecutive wrong codes and a 15-minute lockout after 10, decided before the IdP is called; Keycloak's brute-force protection behind it. The extension compares in constant time and consumes the challenge on success.
- **S (a stolen access or refresh token):** Control: requests need `Authorization: DPoP` and a proof with `ath` by an active device key of the token's user (and on Keycloak the key in `cnf.jkt`); a refresh needs a proof by the device's key and the current refresh token; a current refresh token with another key revokes the device; a used refresh token is dead (Keycloak rotation without reuse, Zitadel rotation, and the platform's compare-and-set).
- **S and T (forged or replayed proofs):** Control: ES256 only; strict header, key and claim shapes; `htm`, `htu` and `ath` bound; `iat` within 60 s back and 30 s ahead; each `jti` claimed once per key in a replay store shared by replicas (`RedisReplayStore`), only after the proof verifies.
- **D and S (the replay store's own Redis, PR-UDF-032, R1-D-47):** `RedisReplayStore.fromUrl` opens the platform's ioredis connection to the product's Redis or Valkey (`rediss://` with TLS above development; AUTH token from SECRETS, never in the URL there). Control: commands are not queued while disconnected and time out (2 s by default), so an outage makes `claim` throw and the proof is refused, never accepted; keys are the SHA-256 of the `jti` under a prefix, with the proof's TTL. Residual: a Redis outage stops customer sign-in and refresh until it is back; a flushed or failed-over Redis without persistence forgets claims, so a proof captured in the last 60 s could be replayed once (bounded by the `iat` window and `ath`).
- **S and E (taking over an account by changing its login, PR-UDF-034, R1-D-51):** Control: a change needs a signed-in device key, a code sent to the current login (which must be this account's) and one sent to the new login (which must be nobody's); both are six digits from the CSPRNG, kept only as salted SHA-256 digests with the new login's digest, never the codes or the new login; the confirmation must come from the same key, within the code lifetime, under the sign-in guard's attempt limits; a login-change challenge can never be used as a sign-in code. The change and a retirement are ledgered by the account's hash only. Retiring signs every device out and forgets it, disables the account at the IdP and frees the login, so a recycled number reaches a new, empty account. Residual: a DB reader could brute-force a stored digest (10^6 codes) within the code's 5-minute life; the database is CONFIDENTIAL and readable only by the API's roles.
- **S (a code phished to another device):** Control: the code is bound to the key that asked for it; another key's proof at `verifyChallenge` is refused.
- **E (a customer factor satisfying a staff check):** Control: customer realms and organisations are separate from staff realms, with their own issuer and audience; customer tokens carry product roles only (staff roles are refused) and never count as MFA (IPB-02-02); the realm has no `amr` mapper.
- **I (codes or logins leaking):** Control: the IdP keeps only a SHA-256 of `<challenge>:<code>` (Keycloak) or its own hashed code (Zitadel); the code reaches the product API over TLS from the authenticated client call and leaves only through NOTIFY's `sendOneTimeCode`, which stores `[redacted]` and never the address; the platform's tables hold no code, no login (accounts by IdP id, hashed in the guard) and refresh tokens only as SHA-256; ledger entries carry no codes. The extension refuses public clients and clients not marked `ipb.customer.otp`, so only the product API, with its secret, can ask for a code.
- **I and E (one tenant's customers seen by another):** Control: accounts are per tenant (usernames derived from the tenant and the login); `connectors/0004` has forced RLS by tenant, select, insert and update for `app_rw`, and delete only under the retention floors of `connectors/0005`.
- **R:** every guard decision, challenge, attempt, device creation, refresh and revocation is ledgered.
- **I (sign-in state kept longer than needed; owner answer #86, R1-D-23):** Control: a per-tenant job deletes challenges 24 h after expiry, guard rows once their lockout window has ended, and devices 12 months after last use, each period a setting. Unbinding a device or closing the account deletes devices at once. Restrictive delete policies (`connectors/0005`) keep floors below the settings, so no caller can delete a live challenge, an active lock or a device in use. Every deletion is ledgered.
- **D (code flooding or lockout of a victim):** Control: the per-account limits cap SMS cost and annoyance; a lockout is timed (15 minutes), never permanent; the product's edge limits per IP (IPB-02 §02.4.6.2) sit in front.

### 3.54 The `KYC` and `VIDEO_MEET` ports (interfaces and fakes, PR-FBX-01; R1-D-21)

The interfaces and their contract cases, with in-memory fakes. No adapter yet (OWNER-QUESTIONS #87, #88), so no data leaves a product through these ports today.

- **I (identity data leaking through the port):** Control: every KYC request schema is REGULATED; adapters must be `IN`; files move as STORAGE references with SHA-256, never inline; results never carry an Aadhaar number (last four digits only).
- **I (a V-CIP recording kept by the vendor or in a shared bucket):** Control: a CONFIDENTIAL or REGULATED room must declare `providerRetention: "none"` and a recording target (the schema refuses otherwise); `fetchRecording` returns a hash manifest, never media; per-tenant target routing is deferred (#83), so V-CIP stays off.
- **S (a V-CIP call from outside India or from an untrusted network):** Control: `joinToken` refuses (`IPB-SEC-002`) a country outside `participantCountries`, an anonymised origin, an official outside `officialNetworks`, and a participant in another role; the origin comes from the product's GEO check.
- **T and R (a forged vendor event or an altered recording):** Control: webhooks are triggers only; the session or room is read back from the vendor; the manifest lists every artefact by SHA-256 with its own hash, and the product ledgers it.
- **Residual:** the cases prove the contract on the fakes only; each adapter must pass them on its vendor sandbox before routing selects it.

### 3.55 The Digio KYC adapter (`digio-kyc`, built behind a flag; R1-D-24)

- **I (identity documents sent or kept where they should not be):** Control: the adapter is `IN` and REGULATED; files are read from STORAGE and checked against their SHA-256 before upload; downloaded files are written REGULATED under the call's tenant, so a pull without a tenant is refused; nothing goes to Digio while the flag is off.
- **I (the Aadhaar number leaving the vendor):** Control: results carry the last four digits only; a reply carrying a twelve-digit run is refused as a vendor error.
- **S and R (a consent session reused, or used for another customer):** Control: a session is claimed once in a replay store, and only after Digio reports it complete. The product binds the session id to its customer when it creates the KYC request.
- **S (credentials):** Control: HTTP Basic with the client id and secret from SECRETS; egress allows Digio's host only; 401 and 403 surface as credential errors, not retries.

### 3.56 Statutory audit capture (`audit/0003`; PR-FBX-10 item 2, R1-D-25)

PostgreSQL captures every insert, update and delete on registered books-of-account tables, with values and context, in a per-tenant hash chain the daily anchor signs.

- **T and R (a change to the books that leaves no trace):** Control: row triggers enabled ALWAYS on every registered table, TRUNCATE refused, and the capture written by a SECURITY DEFINER function whose owner role nobody holds. Event triggers refuse dropping or disabling any part. The chain, the head and `capture_problems()` are verified daily, and the anchor signs the head.
- **T (the captured history edited):** Control: update, delete and truncate on `audit.capture` are refused always, for every role. A superuser who first disables the guard leaves a chain break and a reported problem.
- **I (captured values are copies of REGULATED data):** Control: `audit.capture` has forced RLS by tenant (read only), its value columns are classed REGULATED, and columns encrypted by field crypto stay ciphertext in the copy. The rows are kept as the ledger is.
- **E (the capture writer misused):** Control: `capture_writer` is NOLOGIN, NOINHERIT and granted to no role; the read-only-role check covers it. The capture function takes no argument and writes only what the trigger sees.
- **D (a capture failure blocks the books):** Control: settings that do not fit a column are recorded as absent rather than refusing the write; a row without `tenant_id` is refused, which registration prevents.
- **Residual:** superuser access to PostgreSQL, as for the ledger; event triggers do not fire in replica mode, so DDL done there is caught by the next daily verification instead.

### 3.57 Branch context (`tenancy/0007`, `audit/0004`; PR-FBX-10 item 1, R1-D-26)

Products scope rows by branch within a tenant through `tenancy.branch_allowed()` and the kernel's branch settings.

- **E (a user reads or writes another branch's rows):** Control: the policy's branch condition denies by default; the branches come only from the verified context, the kernel sets them, and a callback cannot change them. A comma cannot appear in an id, so a list cannot be widened.
- **E (head-office scope granted by accident):** Control: `allBranches` is an explicit flag in the context, never inferred from an empty list (an empty list sees nothing).
- **R (which branch a change was made in):** Control: the ledger entry and the statutory capture record the branch; the ledger chain covers it.
- **T (an exported audit trail that cannot be re-verified):** Control: `REF-EXPORT-1.3` exports `branch_id`, and the offline verifier hashes it only when set, exactly as the ledger chain does.
- **Residual:** branch scoping is as strong as the product's policies; `rls-lint` checks the tenant condition, not the branch one. Tenant isolation is unchanged.

### 3.58 Inbound idempotency (`tenancy/0008`; PR-FBX-10 item 4, R1-D-27)

Product APIs store each POST and PATCH response under the client's key for 24 hours and replay it for an identical retry.

- **T (a replay used to get another request's response):** Control: a replay must match the stored route and the canonical request hash, else 409; keys are per tenant under forced RLS.
- **I (stored responses):** Control: response bodies are classed REGULATED, readable only in their tenant, and deleted after the TTL (only expired rows can be deleted).
- **D (duplicate work under concurrency):** Control: one request per key at a time (advisory lock, 409 IPB-API-011); the key commits with the change.
- **I and S (one principal served another's response; PR-UDF-033 (2), R1-D-48):** every borrower of a product shares its tenant. Control: a key belongs to the principal that first stored it (`tenancy/0015`), and another principal presenting it is refused with 409 (IPB-PORT-004). The interceptor also hashes the route's parameters, so one key cannot replay across two resources of one route (PR-FBX-21 (2)).
- **T and E (joined mutations; PR-UDF-033 (1), PR-FBX-21 (1), R1-D-48):** `kernel.ambient` lets a service's `mutate` run in the handler's transaction. Control: a joined call must have the ambient call's tenant, principal, scope and break-glass grant, and run as the app role. Each runs in a kernel savepoint with its own `app.*` settings and its own ledger check; a failure rolls back only its writes. Joined calls run one at a time, and reads are never joined, so `read` stays read-only. Residual: rows written before `tenancy/0015` have no principal and keep the per-tenant check until they expire (24 hours).
- **Residual:** a client that reuses a key after expiry starts a new request, as IPB-10 intends.

### 3.59 Break-glass visible to the tenant (`tenancy/0009`; PR-FBX-10 item 3, R1-D-28)

Each tenant sees every break-glass grant used on its data, and is notified on first use.

- **R (staff access to a tenant's data unknown to the tenant):** Control: the kernel records each use of a grant in the tenant before the transaction runs, for reads as for writes; the tenant reads the record (who asked, who approved, why, until when, how often); a notice event is raised once per grant.
- **T (the record hidden or altered):** Control: the application role can only read it; writes go through two SECURITY DEFINER functions that act on the transaction's own tenant and an active grant only.
- **I (the grant's reason shown to the tenant):** Control: by design, the reason for touching the tenant's data is the tenant's to see; it is CONFIDENTIAL and readable only in that tenant.
- **Residual:** a use is recorded when the kernel runs; direct database access by a superuser is outside it, as for the ledger.

### 3.60 External read role (`tenancy/0010`; PR-FBX-10 item 5, R1-D-29)

A named external grantee (statutory auditor, inspector) reads one tenant's data under one grant, as the SELECT-only `app_external` role.

- **E (an external grantee reading or changing more than granted):** Control: the role holds SELECT only and belongs to no role (rls-lint `external-read`); the kernel runs its reads read-only, as that role, only for an active grant that is the principal's own and in the tenant; every table it can read has forced RLS and a RESTRICTIVE policy calling `tenancy.external_allows`, which limits rows to the grant's entities, branches and period whatever the table's other policies; columns are the product's explicit grants.
- **S (a grant used by someone else or in another tenant):** Control: the grant row must match the context's grant id, principal and tenant on every transaction (`IPB-TRUST-003`).
- **E (a grant created or widened by one person):** Control: a second ORG_OWNER or ORG_ADMIN approves it (`IPB-TRUST-005` on self-approval); 90 days at most; revocation takes effect on the next transaction.
- **R (an unrecorded read):** Control: the kernel accepts an external principal's transaction only from `ExternalReads`, which ledgers each read (grant, table, row count), empty ones too, before it returns the rows.
- **Residual:** the ledger names the table and row count, not the query text; a product's restrictive policy must cover the right columns (entity, branch, date) for each table it opens, which rls-lint checks for presence, not meaning.

### 3.61 Saved table views and the shell's search (`config/0002`, `ui`; PR-FBX-09, R1-D-32)

People save a table's filters, sort and columns for themselves or share them; the command palette searches what they may open.

- **I (a personal view or layout read by someone else):** Control: forced RLS on `app.actor_id` keeps personal views and table layouts to their owner, in their tenant; `SavedViews` returns a shared view only to its audience (the team ids the product vouches for, the named tenant roles, or the tenant), and a view the caller cannot see answers 404.
- **T (a shared view changed by its audience):** Control: only the owner edits or deletes a view, and an ORG_ADMIN or ORG_OWNER a roles or tenant one, in the service and in the update and delete policies; ownership never moves; updates carry the version read (409 on a stale one); every change, including a replaced default, is ledgered.
- **E (sharing wider than allowed):** Control: roles and tenant views, and the tenant default, need ORG_ADMIN or ORG_OWNER; a team view needs membership; platform, agent and service roles are never an audience; `ux.tables.saved_views_shared` off refuses and hides shared views; agents and platform-scope contexts are refused.
- **I (identifiers in search or stored filters):** Control: `searchRefusal` (`contracts`) refuses Aadhaar (any twelve digits, a Verhoeff VID), Luhn-valid card numbers and PANs in the browser, before any search provider runs, and in every saved filter value and view name; refusals and the palette's analytics event carry the pattern class only; the query goes by POST, never in a URL, and a refused one is not written back into the page.
- **I (search results beyond the caller's rights):** Control: each `SearchProvider` trims at query time; a failing provider's error is dropped (it may echo the query) and only its id is reported.
- **Residual:** shared views are visible to any tenant session at the database level (the audience trim is in `SavedViews`), and team membership is the product's claim; a view's name and filters are CONFIDENTIAL text a person chose, kept until they or an administrator delete it.

### 3.16 Cross-tenant service readers (owner answer #22, PL3-D-21)

Background workers that must find due work across tenants (the workflow timer poller, the NOTIFY dispatcher, the one-click unsubscribe link, the export sweep) read through `ServiceReader` in `@infrabyx/tenancy` as one of the `SVC_` roles in `SERVICE_READER_ROLES` (`contracts/roles`).

- **E:** a background identity reading or changing more than it needs. Control: each role maps to its own database role (`svc_scheduler`, `svc_notify_dispatch`, `svc_notify_unsubscribe`, `svc_export_sweep`, `svc_ai_run_sweep`, `svc_ai_index_sweep`, `svc_vidhi_sched`, `svc_tenant_sweep`, created by the owning package's migration), granted `SELECT` on the named columns of its tables only and nothing else (one table each, except `svc_export_sweep`: jobs, archives and the deletion marker, ids and times only, under platform-scope read policies limited `to` that role; PL3-D-25); the kernel runs a platform-scope read as that role (`SET LOCAL ROLE`), so a query on any other table or column fails with `42501`, and forced RLS still applies.
- **E:** a reader approving, writing or impersonating. Control: the kernel refuses every mutation by a reader except the ledger entry recording its own read, in a tenant context (`IPB-SEC-005`); its context must be a service principal with exactly one reader role, no `PLT_*` role, no `act` and no break-glass; a token claiming a reader role is refused (`contextFromClaims`), so readers exist only in-process.
- **R:** an unrecorded cross-tenant read. Control: the query must select `tenant_id`; each read that returned rows writes one `platform.service_read` ledger entry in every tenant it touched (actor = the reader principal, resource = the table) and calls the operational `onServiceRead` hook with the row count per tenant. An empty read returns no tenant data and writes nothing.
- **Residual:** the platform-scope RLS read policies on these tables still admit PLT\_\* principals (people, under IPB-02-11), as before.
- **E (inherited reader privileges, PR-UDF-016):** until `tenancy/0004` every `svc_*` role was inherited by `app_ro` and `app_rw`, so their column grants and platform-scope policies applied without the kernel switching roles. Control: the memberships are switch-only (INHERIT FALSE, SET TRUE) and the two roles NOINHERIT, so a reader's grants apply only inside the kernel's `SET LOCAL ROLE` (R1-D-11).

- **Residual (device attestation):** until the owner's Google Cloud project and Apple account exist, the adapter is off and products fail closed above test environments. The pinned root was taken from two independent public copies with the same fingerprint (`1cb9823b…c932`); the owner confirms it against apple.com before turning App Attest on.

### 3.66 Chain lanes for the ledger and the capture (`audit/0006`, `0007`; Finbyx PR-FBX-32, ADR-0005, R1-D-58)

Each tenant's ledger and statutory capture are N hash chains (lanes) instead of one, so a tenant's writers no longer queue on one head row. The daily signed anchor seals every lane head.

- **T (an entry edited, removed or inserted):** Control: each lane is the same SHA-256 chain as before (PL1-C-01), and the entry's lane and position are hashed. An edit, a gap, a relinked entry or an entry moved to another lane breaks its lane. Lane heads are written only by the chain owners (`app_migrate`'s trigger, `capture_writer`), and deletes and truncates of them are refused. The verifiers compare each lane's end with its head, so a deleted tail is reported. The format-3 anchor signs every lane head of both chains in KMS and write-once STORAGE.
- **T (history rewritten across lanes after the day's anchor):** Control: the anchor's root over all lane heads no longer matches; formats 1 and 2 still verify.
- **T (a caller steers lanes):** Control: a transaction may pin its lane (`audit.ledger_lane`, `audit.capture_lane`, transaction-local only). That only chooses which lane it waits for: the trigger still locks the lane head and chains the entry.
- **R (ordering across lanes):** Control: no hash links the lanes within a day. Each entry carries its global `seq` and its `occurred_at`, both hashed, and the anchor seals the lanes daily.
- **D (deadlock between two transactions holding a ledger lane and a capture lane in opposite orders):** Control: PostgreSQL aborts one, as with the single heads. Writing the change before its ledger entry keeps the order.
- **D (the upgrade blocks writes):** Control: `audit/0006` locks the two tables for its few statements with a 5 s `lock_timeout`; `audit/0007` builds its indexes concurrently.
- **Residual:** superuser access to PostgreSQL, as for the ledger and the capture (§3.56). Between two anchors, a superuser who rewrites a lane and its head together is caught at the next anchor, not by the head comparison.

### 3.70 CI only on the `ci:run` label (R1-D-64)

- **E (a required check satisfied without running):** pull-request CI starts only when a label is added. A cancelled run does not replace an earlier green or red result on the same commit with a pass.
- **Residual:** a push after the label leaves the PR's checks pending until `ci:run` is removed and added again, which blocks the merge (fail-safe).

- **T (one request provisioned twice):** Control: the inbox stores the event by `(source, id)` and the request id as its business key, so a second event for the request is never processed; the tenant id is the provisional id or one derived from the request id, and `provision` is idempotent per id.

- **Residual:** the payload's field names follow the Spec's wording until the Hub publishes its registry schema (`[VERIFY]`). The request half and `ProvisioningFailed` are §3.74 (Spec v1.3).

### 3.73 Per-tenant templates and delivery reports by vendor reference (PR-FBX-33, PR-LDC-15; R1-D-69)

- **I and T (a message sent under another tenant's sender, DLT entity or template):** Control: the resolver runs at delivery in the delivering tenant's context, `dispatchDue` included (each due delivery is delivered in its own tenant's service context); `null` fails the delivery closed and a template of another channel is refused, so a missing tenant template never falls back silently to someone else's.

### 3.74 Provisioning requested by a product and refused by the Hub (Spec v1.3; PR-040, #105; R1-D-70)

- **S (a forged `ProvisioningFailed` aborts a real sign-up, or a forged `ProvisioningRequested` reaches the Hub):** Control: `ProvisioningFailed` is verified exactly as `TenantProvisioned` is (§3.72: the Hub's pinned key ring, ES256, `kid`, `iat` window, `jti` once); `ProvisioningRequested` is signed with the product's ecosystem key from KMS at delivery, never at write time, so no long-lived JWS sits in the outbox.
- **T (one request ends twice, e.g. a tenant created after a failure was acted on):** Control: `TenantProvisioned` and `ProvisioningFailed` share the request id as business key with `exclusiveWith`, under an advisory transaction lock, so only the first stored of either is processed; the other is acknowledged as `business_duplicate` and ledgered. A request id reused with another payload is refused (`IPB-PORT-004`).
- **I (personal data in the failure, or a provisional tenant's contact data kept after a failure):** Control: `detail` is refused when it carries an email, a mobile number, a PAN or a long number; `ProvisioningRequested` carries business contact data only, with `legalbasis` claimed only when the first-admin email is sent. The product purges the provisional tenant and its first-admin contact data within 30 days of `failed_at` (`purgeBy`), ledgered, unless a retry is open (Spec v1.3 retention rule; DPDP Act 2023 s.8(7)).
- **E (a product acknowledges failures it does not act on):** Control: without an `onFailed` hook the adapter refuses `ProvisioningFailed`, so the Hub keeps resending it rather than it being dropped.
- **Residual:** the personal-data check is a pattern list (a false positive only refuses the event, which the Hub resends without the detail); the purge itself is the product's code, checked by its own tests.

### 3.75 CEL string functions and linear-time patterns (PR-LDC-13, R1-D-71)

- **D (ReDoS: a rule author's pattern makes evaluation super-linear):** Control: `matches` takes only a string literal from a static subset checked when the draft is saved, before publication (no back-references, look-around, atomic or possessive constructs, no quantified group holding a quantifier or an alternation; at most 256 characters). The production engines (`zen`, `json-rules`) search with `re2js` 2.8.8, a pure JavaScript RE2 port, linear by construction; the text is at most 4096 characters, and the evaluation time limit still applies. `evaluateCel`, which runs the CEL library's backtracking RegExp, refuses a non-literal or out-of-subset pattern and any input string over 4096 characters.
- **T (engines disagreeing on a string row):** Control: the subset leaves out every construct whose meaning differs between RE2 and a JavaScript RegExp (`.`, negated classes, `\D`, `\W`, `\s`, `\S`, `\B`, `\x`, `\u`, `\p`); ZEN never sees a pattern (its result is passed in as a boolean input); strings must be well-formed UTF-16. A randomised test over 4,000 patterns checks re2js against RegExp, and a 600-input differential test checks the three engines against each other.
- **Residual:** adjacent ambiguous quantifiers (e.g. `\d+\d+`) are polynomial on a backtracking engine; they run there only in the memory walk (tests and validation) and in `evaluateCel`, both bounded by 4096-character strings. `re2js` (MIT, no dependencies) was already in the lockfile through `unleash-client`.

### 3.76 Platform purpose notices, consent read by principal and the #95 purge (PR-LDC-14, #95; R1-D-72)

- **T and repudiation (an erasure used to rewrite history):** Control: the history's only delete policy admits USER rows of a person who has a `config.setting_erasure` row in the same tenant; that row is written first, in the same transaction as the deletes and the `settings.user.erase` ledger entry (counts and the request reference, never a value); UPDATE stays ungranted; agents, externals and platform contexts are refused; the callers are a service principal, ORG_OWNER or ORG_ADMIN. Residual: an ORG_ADMIN can erase a person's USER preferences with a reason; the ledger keeps who and why.

### 3.96 Setting scopes below ENTITY (`config/0005`; PR-042, PR-LDC-17, R1-D-95)

- **E (a unit loosens a security setting):** Control: UNIT is allowed only for a key that declares `unit_override` (none of the platform's keys does), stays tighten-only against the tenant, the entity and each outer unit, and needs the key's change role with the unit in the caller's own `ctx.unitIds`.
- **S (a forged unit chain):** `ctx.unitIds` comes from the product's own organisation model, set server-side like `entityId`; at most 8 ids of a fixed alphabet. Residual: the platform does not hold the organisation model, so a product that builds the chain from a request body would let a caller pick a unit's values; the guide says to build it from the verified principal only. UNIT rows follow `app.tenant_id` under RLS like ENTITY rows.

### 3.97 Sandbox changes under maker-checker (#115, R1-D-95)

- **E (one administrator takes a production tenant into the sandbox, silencing its mail):** Control: `TenantSandbox.set` is refused; a change is an R3 request by a PLT_SUPER_ADMIN, approved by a different PLT_SUPER_ADMIN or PLT_SECURITY_OFFICER in a platform context only (a tenant's own checkers cannot decide it, and a tenant's `mc.*` settings do not narrow platform checkers), then applied once by a PLT_SUPER_ADMIN through `ApprovalsEngine.consumeIn` in the `tenancy.tenant.sandbox.set` transaction, so the database guard still holds; the ledger keeps the reason and the request id. The request is visible to the tenant's approvers in their own tenant, which is information about their own tenant only.

### 3.98 PDF export (PR-LDC-28, R1-D-95)

Characters outside WinAnsi are refused, never replaced, so amounts and names are never silently altered.

### 3.99 Embedded fonts and the DOCGEN route for Indic PDFs (#117; R1-D-96, R1-D-97)

### 3.100 Purge runs and per-record entries (`consent/0005`; PR-FBX-37, R1-D-97)

The run table is insert-only for the application. The dry run's delete runs under the purge's action inside a savepoint that is always rolled back.

### 3.105 Retiring a statutory-capture registration (`audit/0008`; #122, R1-D-102)

The drop guard admits only the drop of that table and its `ipb_capture*` triggers, only in the retiring transaction and only with the table itself; a deferred check fails the commit if the table survives. Every other drop is refused as before. **R:** the retirement is a chained capture entry in the platform chain and each affected tenant's chain; no capture row is removed; `audit.capture_retirement` and `audit.capture_table` stay append-only except for that one sanctioned delete. **E:** the function is SECURITY DEFINER owned by the database owner; it fails closed where its owner cannot read past row-level security.

### 3.106 The tenant-id rule (`tenancy/0019`; PR-FBX-40, R1-D-103)

- **D (a tenant that cannot use a port) and T (a tenant id that could be read as a path):** a tenant id is `tnt_` then lower-case letters and digits, or a ULID; the database refuses any other at creation, and no id it admits contains a separator a storage key could misread. The migration names, and does not change, existing ids that break the rule.

### 3.107 The DISPATCH, COURT_DATA and ODR ports (ADR-0008 to 0010; R1-D-104)

### 3.111 Scheduled rule-set cut-over (`rules`; PR-LDC-34, R1-D-113)

### 3.113 The AV port and the ClamAV adapter (`contracts`, `connectors/av`; PR-LDC-41, R1-D-117)

- **T (malware reaching a reader; IPB-02-44):** the platform never defined the AV port the upload pipeline needs, so each product scanned on its own. `FileScanPort.scan(ref)` answers `CLEAN`, `INFECTED` or `ERROR`, and `scanDecision` is the one mapping: only `CLEAN` releases a file; `INFECTED` is `IPB-SEC-011`; `ERROR` and anything unknown keep it quarantined (`IPB-SEC-015`). The adapter never throws for a scan that ran and failed, so a caller cannot release a file by catching an exception.
- **T (a scan that did not really happen):** the adapter reads the object from STORAGE and checks its SHA-256 against the reference before scanning (`hash_mismatch` otherwise); a file over `maxBytes` (keep it at or below clamd's `StreamMaxLength`), clamd's size-limit reply, a timeout, an engine error, an unreachable or disabled engine, and a signature set older than 48 hours (IPB-02-44 wants daily updates) are all `ERROR`. Archives are scanned by clamd (the contract leg finds EICAR inside a ZIP).
- **I (file bytes on the wire):** clamd has no TLS, so the adapter connects only when the configured host resolves to loopback, RFC 1918, CGNAT or IPv6 unique-local space; anything else is `ERROR` and nothing is sent. The deployment runs clamd in the same cluster with a network policy that admits only the services that scan. Only the verdict, the threat name and the engine version come back; bytes are never logged. Residency IN, class ceiling REGULATED (KYC images are uploads too).
- **D (engine down or out of date):** uploads stay quarantined, never released, until a scan succeeds; `health()` is `degraded` when signatures are stale. Off behind `int.av.clamav.enabled` (PLATFORM, R4) until a deployment runs clamd with daily `freshclam`. The test image (`clamav/clamav:1.5.4`, pinned by digest) is used from 16 Nov under PL2-D-32; the IPB-01 alternatives need an external account and stay unproven.

### 3.114 Cancelling an approval in the caller's transaction (`tenancy/0022`; PR-LDC-37, R1-D-120)

- **E (withdrawing someone else's request):** `cancelIn` applies `cancel`'s rules unchanged (the maker, ORG_OWNER or PLT_SECURITY_OFFICER; the request must be in the transaction's tenant, which RLS also enforces) and refuses agents. Nothing about approving changes. **R:** the cancellation is ledgered in the same transaction with its reason (digest in the ledger, text on the request); a rolled-back product write rolls back the cancellation, its ledger entry and the inbox closure together. **I:** the reason is CONFIDENTIAL, at most 500 characters, and never in the `ApprovalCancelled` event.

### 3.115 Business ids on ledger entries (`audit/0010`, `audit/0011`; PR-LDC-30, R1-D-125)

- **T (rewriting what an entry concerns):** the ids are inside the entry's hash when present (the trigger builds the canonical form; TypeScript verification matches it), so changing, adding or removing an id breaks the chain at that entry; the ledger stays append-only. Older entries hash exactly as before. **I:** ids only, by pattern (no spaces, at most 128 characters, 16 per entry), never personal data; checked in the sink and by a database check. `history` reads under the ledger's forced RLS, so a tenant sees only its own. **D:** the GIN index is partial and built concurrently, so neither the migration nor the index blocks ledger writes.

### 3.116 Workbook forms (`export` `toXlsx`; PR-LDC-31 writer, R1-D-128)

- **T (formula injection, a workbook that runs something):** validations are built from typed values only (literal list values without commas or quotes, numeric and date bounds, a named range defined in the same call); there is no custom-formula validation and no caller formula text, so the writer's rule that no cell is a formula holds, and text cells are still neutralised. Named ranges are refused if they look like a cell reference, and sheet names in references are always quoted. **T (relying on protection):** sheet protection takes no password and is documented as a UI guard, not a control: a product re-checks every value when a workbook comes back (the bounded reader, M84, has its own entry in wave 14).

### 3.117 The ACCOUNTING sink interface (`contracts`, `testing`; PR-FBX-46, R1-D-122)

- **T (a batch posted twice, or changed after approval):** `post` is idempotent on the journal id and the batch's canonical SHA-256; the same id with a different digest is refused (`IPB-PORT-004`) and an acknowledged batch is never replayed. **T (unbalanced or fractional books):** `assertBalancedBatch` runs before any call: integer paise up to 10^15, at least one debit and one credit, debits equal credits per voucher, voucher references unique in the batch; nothing is half-posted. **E:** agents are refused (`IPB-SEC-004`); a user or the product's service posts. **I:** amounts and narrations are CONFIDENTIAL. Posting records money already moved and moves none. No adapter yet: the TallyPrime adapter's local agent runs on the tenant's own network, outside the cluster, so its transport, authentication and replay window get their own entry with the wave 14 design before the wave 15 build.

### 3.118 The CALENDAR port interface (`contracts`, `testing`; PR-LDC-53, #126, R1-D-126)

- **S (a stolen authorisation code, a forged callback):** the code flow uses PKCE S256 and a state of at least 128 bits bound to the person's session; a state or verifier that does not match is `IPB-SEC-017`; the redirect URI must be the fixed callback path on https (http only on localhost), with no query, fragment or credentials, and providers compare it exactly. **E:** only the person connects and disconnects their own calendar; the product's service may write entries to it, an agent never writes or deletes. **I (case details in a shared calendar):** `calendarPayload` is the only view that reaches the provider: `busy` sends the time only, `title` adds the title, only `full` carries the description and location; the product picks the level per entry. Tokens never leave the adapter (stored with `fieldCryptoForTenant`, never logged or returned) and are revoked at the provider on disconnect; scopes are limited to calendar events (runbook `calendar-oauth-apps.md`). **T:** entries are upserted and deleted by the product's external id and the adapter touches only entries it wrote. **D:** a revoked or failed connection writes nothing (`IPB-PORT-003`) and shows `token_revoked` to the person. The Microsoft 365 and Google adapters (GLOBAL residency; DPA reference required, IPB-DEV-05) stay off and unproven until the owner registers the applications.

### 3.119 The product MFA floor (`contracts`, `connectors/identity`; PR-LDC-55, R1-D-135)

- **E (a product loosening IPB-02-02):** `mfaFloor` only adds roles; `assertMfaForRoles` applies the platform floor on top of whatever floor it is given, so a hand-made floor object cannot drop a platform role. **S (a weak second factor):** for SMS-excluded roles the session must name a non-SMS factor in `amr`; a token that only asserts `mfa` is refused, and `amr` is bounded (16 entries, 32 characters). **D (a user locked out of the step that satisfies the floor):** `assertStepUpReachable` refuses to boot when a callback, sign-in, MFA-enrolment, refresh or sign-out route is behind the floor. **I:** the step-up answer names only the required `acr_values` and whether SMS is excluded; no role list leaves the server. The `acr_values` are checked against RFC 6750's header grammar before they are written into `WWW-Authenticate`.

### 3.120 Ordered approval levels (`tenancy/0023`; PR-LDC-38, #125, R1-D-136)

- **E (a level that loosens maker-checker):** levels only add to the action's rule: level 1's roles must be among the action's checker roles and it needs at least the risk class's checkers; agent roles cannot be a level; a definition outside the limits throws before anything is stored. **E (one person deciding twice):** the decision table's key (request, checker) holds across levels, the maker is refused (`IPB-SEC-007`) and agents are refused (`IPB-SEC-004`). **T (deciding out of order):** a decision is recorded at the level open when it is made, checked against that level's roles, under the request's row lock; a rejection at any level ends the request. **R:** each decision is ledgered with its level. **D:** the delay window starts only when the last level approves, so a later level cannot shorten it.

### 3.121 The TallyPrime agent (design; PR-FBX-46, R1-D-137)

- **S (a rogue agent pulling a tenant's journals):** an agent exists only after a maker-checker enrolment and a one-time code (30 minutes, shown once); it holds its own ES256 key and signs each call (5-minute single-use JWS bound to method, path and body digest); calls are scoped to the agent's tenant under forced RLS; revocation refuses the next call. **T (duplicate or altered vouchers):** `REMOTEID` makes TallyPrime refuse a second create; the agent confirms by export before acknowledging; a mismatch is rejected and never overwritten; a changed batch never leaves the platform (digest rule). **I:** the agent listens on no port and keeps only the job in hand; data class at most CONFIDENTIAL, residency IN. **D:** one batch in flight per agent, bounded size, 7-day expiry, cached trial balance; an offline agent leaves batches pending and the port `degraded`. **E (the agent as a foothold):** it talks only to the platform API and to TallyPrime on localhost; the build ships it with a pinned base image and SBOM like the platform's images. Built in wave 15; this entry is reviewed again with the code.

### 3.122 Projection rule sets (`rules/0004`; PR-LDC-49, R1-D-139)

- **R (decisions without a record):** `project` writes nothing, so it is confined to rule sets created for projection; the purpose is fixed at creation and `evaluate` refuses a projection set, `project` a decision-grade one (`IPB-RULE-003`). A projection result has no decision id, so it cannot be cited as a decision. Publishing a projection set stays an R4 request. **D:** at most 1,000 inputs a call, each under the engine's evaluation timeout. **I:** results return only to the caller in its tenant (RLS on the rule set).

### 3.109 Tenant entitlements (`tenancy/0020`; PR-FBX-43, #123, R1-D-107)

- **E (a tenant licensing itself, or one person licensing a tenant):** a version is written only on the platform's approved path: the insert policy needs a platform context and the action `tenancy.entitlement.change`, the service checks two different platform people (requester PLT_SUPER_ADMIN or PLT_FINANCE; approver a different PLT_SUPER_ADMIN or PLT_SECURITY_OFFICER), refuses services, support roles, tenant users and impersonations, and the table refuses a row whose approver is its requester. R4 (60-minute delay) in production. **R:** versions and notices are insert-only; both steps are ledgered in the tenant. **D (a licence lapsing mid-work):** a lapse or revocation refuses writes only; every record stays readable until the product's detach workflow, and the tenant is told of each grant, revocation and lapse. **I:** the tenant reads only its own licences and notices (forced RLS); of the two SECURITY DEFINER functions, `entitlement_status` reads only the transaction's own tenant and `entitlement_lapses_due` (the sweep's cross-tenant list) returns nothing outside a platform context; both are on the RLS lint's reviewed list.
