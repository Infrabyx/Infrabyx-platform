# Threat model — infrabyx-platform

**Status:** living document (PL2-D-43). Updated by every PR that adds a port, adapter, package or data flow; the PR checklist points here. **Last updated:** 2026-10-27 (PL3 session 4: `@infrabyx/notify`, the PUSH adapters `expo` and `fcm`, C-23 and C-24 in `@infrabyx/crypto`, the suppression and consent flows and the notification dispatcher).

**Method:** STRIDE (Spoofing, Tampering, Repudiation, Information disclosure, Denial of service, Elevation of privilege) per package and per IPB-01 port, against the IPB-02 controls. Each control links to where it is specified (plan section, decision ID) and how it is proven (test tag). "Built" means merged on `main`; "planned" means specified in a phase plan and not yet built.

## 1. Scope, assets and trust boundaries

**In scope:** the `@infrabyx/*` packages, the reference routing files, CI workflows and the test infrastructure in this repository. **Out of scope here:** product code (each product keeps its own model), the cloud accounts themselves (PL6 Terraform and runbooks), and vendor internals (Vendor Assurance Room, IPB-D-09).

**Data classes** (IPB-02 §02.4.3.1): `PUBLIC` < `INTERNAL` < `CONFIDENTIAL` < `REGULATED` < `SECRET`. A class follows the content, not its protection (PL2 plan §6.9). A caller may only raise the class of a port call, never lower it below the port default (PL2-D-03).

| Asset                                                         | Class                   | Where it lives                                              |
| ------------------------------------------------------------- | ----------------------- | ----------------------------------------------------------- |
| Tenant business records                                       | CONFIDENTIAL–REGULATED  | Product schemas (RLS), field-encrypted where REGULATED      |
| REGULATED fields (PAN, Aadhaar, bank account, card last four) | REGULATED               | Field envelope (PL1 C-04), masked everywhere else           |
| Audit ledger                                                  | INTERNAL (digests only) | `audit.ledger`, hash-chained, append-only; signed anchors   |
| Secrets, keys, tokens                                         | SECRET                  | SECRETS / KMS ports only; never env in production           |
| Idempotency results                                           | as the call             | `connectors.idempotency_record`, sealed ≥ CONFIDENTIAL      |
| Telemetry                                                     | INTERNAL (scrubbed)     | OTLP → Collector → Grafana stack, `IN`                      |
| Flag state                                                    | INTERNAL                | Unleash or `config.flag_value`; snapshot in `config`        |
| Seed credentials                                              | SECRET                  | Generated per run, `SEED_CREDENTIALS.md` never committed    |
| Published packages                                            | PUBLIC (to the org)     | GitHub Packages; provenance through `release.yml` on `main` |

**Trust boundaries:**

1. **Caller → kernel.** Every mutation runs in `PgKernel.mutate` with a verified tenant context; RLS is the last line (IPB-02-12).
2. **Kernel → port (router).** The router enforces data class, residency, recipient delivery and idempotency before any I/O (PL2 plan §3.1, §3.5, §3.12).
3. **Adapter → vendor (egress).** HTTPS only, host allow-list, no redirects (IPB-02-43, plan §3.7).
4. **Vendor → platform (webhooks).** Signature verified, de-duplicated, ledgered (IPB-10-27, plan §3.8).
5. **CI and supply chain → `main` → registry.** SHA-pinned actions, 7-day dependency age, publish only from `main` (IPB-02-33, PL2-D-32).

## 3. Packages

### 3.1 `@infrabyx/contracts` (built)

Types, schemas and error codes only; no I/O.

- **T:** a schema too loose lets bad data through every product. Control: Zod strict schemas, payload data-class annotations, and `ipb/port-data-class` lint (an unannotated field fails).
- **I:** an error leaks internal detail. Control: RFC 9457 errors with code and help key; adapters put vendor detail in `meta`, never in `detail` shown to users (IPB-10).

### 3.2 `@infrabyx/crypto` (built)

- **I:** key material logged or serialised. Control: `SecretKey` is opaque (`toJSON`, `toString` and `inspect` print the ID only); material lives in a `WeakMap`.
- **T/S:** wrong algorithm or weak parameters. Control: the algorithm registry and CBOM (PL1), `assertApproved`, and the approved C-items only (plan §9). A new primitive is a stop-and-ask (CLAUDE.md working mode, item 1).
- **I:** joinable pseudonyms across purposes. Control: per-purpose HKDF sub-keys; telemetry hashes use `ipb/telemetry-id/v1` (PL2-D-36).
- **S:** forged or confused tokens. Control: C-11 verifier (X-16); `jose` only as a test devDependency, refused at runtime by `ipb:check`.
- **S:** forged vendor callbacks. Control: C-13 verifiers (X-17); webhook secrets we generate are 32 random bytes (C-19).

### 3.3 `@infrabyx/config` (built)

- **T:** a setting read before registration, or a production secret in env. Control: settings registry, env guard (exit 78) and the `process.env` lint (IPB-01-19).
- **E:** a flag flipped without governance. Control: `FlagAdmin` (kill switches by PLT_RELEASE_MANAGER/PLT_SECURITY_OFFICER, `fut.*` through R3 maker-checker) with a ledger entry (PL1-D-11).
- **D:** flag provider down. Control: last-known-good snapshot ≤ 24 h, then registry defaults; unknown `kill.*` evaluates on (X-10).

### 3.4 `@infrabyx/tenancy` (built)

- **S:** forged tenant or actor. Control: context only from verified claims; RLS insert policies bind `app.tenant_id` and `app.actor_id`.
- **E:** impersonation or break-glass abuse. Control: time-boxed, reason-required, ledgered; impersonated sessions cannot approve (`IPB-SEC-003`).
- **I:** REGULATED fields in plaintext. Control: field envelope encryption with per-tenant keys (PL1 C-04, C-15) and server-side masking; format v2 binds each data key to its tenant and purpose (X-18).
- **T:** a shipped migration edited. Control: checksums in `meta.migration_checksums`; migration-lint `--record-checksums`; CLAUDE.md "never edit a migration that has shipped".

### 3.5 `@infrabyx/audit` (built)

- **R:** an action without a trace. Control: ledger-required commit (X-02); trigger-computed chain so no application path writes an unchained row.
- **T:** history rewritten. Control: append-only for every role (X-03); weekly verifier emits `LedgerChainBroken`; signed daily anchors on write-once storage (PL1 C-03).
- **I:** payloads in the ledger. Control: before/after stored only as canonical digests; IP and user agent as keyed pseudonyms (PL1 C-02).

### 3.6 `@infrabyx/seed` (built)

- **E/I:** seeds or seed credentials in production. Control: refusal first in `prod`, `dr`, `pre-prod` (`SEED_REFUSED_ENVS`, PL1-D-06); generated passwords; `SEED_CREDENTIALS.md` ignored and checked by `ipb:check`; forced rotation and MFA on first production login (IPB-D-04).

### 3.7 `@infrabyx/testing` (built)

- **T (supply chain):** a test image swapped. Control: images pinned by digest from Docker Hub, kept equal to `infra/docker/TEST_IMAGES.md` by a unit test; images from session 2 on were at least 7 days old when pinned (PL2-D-37).
- **I:** sandbox credentials printed. Control: the sandbox-leg gate prints missing variable names only, never values.

### 3.8 `@infrabyx/connectors` core (built)

- **S:** a forged vendor webhook. Control: signature verification before any processing, 401 on failure, inbox de-duplication, ledger entry `connectors.webhook.received` (plan §3.8; C-13 for per-vendor rules, session 3 onwards).
- **T:** a replayed or altered idempotent request. Control: request hash (C-20) compared on replay, mismatch is `IPB-PORT-004`; keys stored as SHA-256 hashes.
- **R:** idempotency outcomes untraceable. Control: each state change is ledgered (PL2-D-35).
- **I:** a result of a REGULATED call stored readable. Control: results ≥ CONFIDENTIAL are sealed with tenant field encryption; RLS on `connectors.idempotency_record`.
- **I:** data sent to a vendor that cannot hold it. Control: X-05, X-06, checked before I/O; refusal emits `ResidencyViolationBlocked`.
- **D:** a failing vendor stalls callers. Control: circuit breaker per adapter (PL2-D-33), timeouts and bounded retries in egress, health registry; STORAGE writes fail fast instead of queueing bytes (IPB-DEV-06).
- **E/T:** SSRF through a vendor URL. Control: egress allow-list and no redirects (X-07).
- **Money:** a money call re-sent after an unknown outcome would double-charge or double-refund. Control: unknown outcomes stay pending and go to reconciliation; never re-sent (X-08, P-05).

### 3.9 `@infrabyx/connectors` IDENTITY and AUTHZ (built)

- **S:** a forged, re-signed or other-issuer token. Control: X-16 with ES256 only per issuer; JWKS only from the configured URL through egress; claims mapped to `VerifiedClaims`, unknown principal types refused, roles outside the platform format dropped.
- **S/E:** a user sets their own tenant or type. Control: tenant, type, product scope and external id are admin-only attributes (Keycloak `ADMIN_EDIT`) or admin-set metadata (Zitadel); the kernel context is built only from verified claims (IPB-02-13).
- **E:** a privileged role without MFA. Control: forced enrolment at login (Keycloak required action; Zitadel `forceMfa`), and the API guard refuses a token without an MFA method in `amr` (`IPB-SEC-001`); SMS never counts as MFA.
- **R/E:** a de-provisioned user keeps working. Control: SCIM deactivation, `revokeSessions`, a role change and back-channel logout write a revocation (hashed subject, RLS, ledgered) before the IdP call; every replica refuses within 15 s (PL2-D-53).
- **D:** IdP outage. Control: JWKS cached 24 h so API calls continue; new logins fail with `IPB-IDN-002`.
- **E:** impersonation without an audited `act`. Control: impersonation tokens are unsupported on both adapters (PL2-D-55, owner); the kernel refuses mutations under `act` (`IPB-SEC-003`). Support access, when first needed, is a platform-issued read-only token on an approved, ticketed request, at most 60 minutes, ledgered and visible to the tenant's `ORG_OWNER`.
- **E:** an AUTHZ allow by mistake. Control: deny by default, PDP failure denies (`IPB-AUTHZ-001`), agents denied before the PDP and in policy (X-14), allow-only cache ≤ 5 s, one decision table proven on both engines.
- **I:** bootstrap secrets. Control: `applyRealm` and `applyInstance` return generated client secrets for the SECRETS port and never log them; they run only in deploy jobs and tests.

### 3.10 `@infrabyx/connectors` STORAGE, QUEUE and WORKFLOW (built)

- **T:** a retained record overwritten or deleted. Control: COMPLIANCE-mode Object Lock; the adapter also refuses a new version, a delete marker or an upload URL while retention applies (`IPB-STOR-003`); break-glass cannot delete a locked version (@IPB-02-AT-13).
- **I:** documents readable across tenants or under the wrong key. Control: keys outside the caller's tenant refused (`IPB-PORT-003`); SSE-KMS with the tenant's own CMK when it has one (C-17), so a tenant purge covers documents.
- **I:** a long-lived or repurposed presigned URL. Control: SigV4, 1–300 s, bound to the method and, for uploads, the content type (IPB-02-15).
- **I:** personal data on the queue or in Temporal's readable fields. Control: queue payloads are flat INTERNAL maps checked before I/O; workflow ids, names and task queues are checked to be identifiers; every Temporal payload and failure is encrypted (C-16) and unencrypted payloads are refused.
- **E:** runtime DDL by the queue. Control: pg-boss's schema is a checked-in migration; its role has DML and EXECUTE only (proven in the contract leg).
- **I:** decrypted workflow failures in worker logs. Control: worker logs go through the OBSERVABILITY scrubber (X-09); failures should carry codes, not personal data.
- **D:** a store outage. Control: writes fail fast (`IPB-STOR-002`) and the caller's outbox retries; reads fail over to the DR replica; queue enqueue failures go to the outbox; Temporal outages pause timers.

### 3.11 `@infrabyx/connectors` EMAIL, SMS and WHATSAPP (built)

- **S:** forged delivery, bounce or status webhooks. Controls:
  - SES events arrive through SNS: SignatureVersion 2 only, certificate host pinned to ap-south-1/2, one TopicArn, a one-hour timestamp window, and subscription confirmation followed only to an SNS host after verification (C-13).
  - Meta webhooks: `X-Hub-Signature-256` over the raw body; the subscription handshake compares the verify token in constant time.
  - Vendors that do not sign (Brevo, MSG91, Gupshup SMS and WhatsApp) present our C-19 secret, compared in constant time:
    - as a bearer header (Brevo, MSG91);
    - as the `ipb_token` URL parameter when the vendor can only call a URL (Gupshup), which ingress logs must redact;
    - Brevo also needs its published source ranges.
  - Failures answer `IPB-API-018` without logging the body.
- **T:** a replayed webhook processed twice. Control: every event carries a stable vendor event id for the module inbox (@IPB-02-AT-05 scenario 2).
- **I:** CONFIDENTIAL content inline, or documents attached:
  - bodies above INTERNAL are refused before any request;
  - attachments must come from GENERAL or PUBLIC_ASSETS storage, at most 10 files and 10 MiB;
  - anything else goes as a secure link.
- **I:** recipients at a GLOBAL vendor. Control: X-06; Brevo, Gupshup WhatsApp and Meta refuse to start without a DPA reference; Brevo's manual suppression is refused because it would need a contact record (PL2-D-64).
- **I:** credentials in URLs. Control:
  - Gupshup SMS credentials go in a POST body;
  - MSG91's key goes as a header, the balance check included;
  - no API key is put in a query string.
- **T:** non-DLT SMS content. Control: template, header, entity id and variable count are checked before any request; the Gupshup text is rendered from the registered DLT text.
- **E:** marketing sent by mistake. Control: `mkt.meta.enabled` (default false); the template category is read before every send and marketing templates and submissions are refused while it is off (OWN-08).
- **D:** a vendor outage. Control:
  - SES pauses map to `IPB-PORT-002` (reputation block) so the router can fail over;
  - Brevo serves as a failover target only for brands whose domain is authenticated on Brevo;
  - SMS fails over msg91 → gupshup-sms with the same DLT mapping;
  - WhatsApp has no failover between BSPs.

### 3.12 `@infrabyx/connectors` PAYMENTS (built, test mode only)

- **T:** amount tampering or rounding. Control: integer paise in and out, INR only; Cashfree decimals are written as exact text and read back exactly or refused (P-04).
- **S:** a forged webhook or checkout return. Controls (P-09):
  - Razorpay `X-Razorpay-Signature` and Cashfree `x-webhook-signature` are checked over the raw body; Cashfree's timestamp must be within ±5 minutes.
  - A Razorpay checkout return is checked by its `razorpay_signature`; a Cashfree return by fetching the order server-side.
  - Client-side success is never trusted.
- **E:** a refund without approval, or more than was paid. Control:
  - an approved R3 request for exactly the refund's payload is required (`IPB-SEC-006`);
  - the PA's own refund list is read at execution;
  - the cap is the captured amount minus earlier refunds;
  - an agent can only make the request (P-07).
- **T:** a duplicate charge or refund after a timeout. Control: the idempotency record is pending before the call; orders are looked up at the PA by our reference first; refunds and mandates that cannot be resolved go to the human queue and are never retried automatically (P-05, P-07).
- **E:** live money by accident. Control: no live key anywhere in this repository, CI or non-production; the env guard and the adapters refuse live credentials outside prod/dr (P-03); `kill.payments` stops new money operations (P-12).
- **D:** a PA outage. Control: new orders fail over Razorpay → Cashfree; refunds, mandates, captures and checkout sessions stay with the PA that owns them (P-08).
- **I:** payment details beyond what billing needs. Control:
  - only IDs, amounts, statuses, method categories and times leave the adapters (P-10);
  - the customer phone and email reach only Cashfree, which requires them;
  - card data never touches Infrabyx (hosted checkout, SAQ A).

### 3.13 `@infrabyx/rules` and the RULES engine adapters (built, PL3 session 2)

- **T:** a decision that defaults to allow. Control: an invalid input (missing, mistyped or undeclared), an engine error, a timeout (`rules.eval.timeout_ms`) or a matched `verify` row that would drive a statutory output is `UNDETERMINED` with empty outputs, logged, and raised to the Work Inbox (`HumanQueue`, `review_undetermined`); there is no default row (IPB-01 RULES).
- **T:** engines disagreeing, or a row meaning something else on another engine. Control: one CEL subset parsed and type-checked by `@marcbachmann/cel-js`, lowered to an IR that every engine compiles; ZEN cells are generated from the IR, never from the row text, so a malformed cell (which ZEN reads as "no match") cannot occur; string literals without quotes, backslashes or control characters; plain-notation numbers; reserved field names refused; a draft must compile on all three engines before it is saved; a differential test proves agreement.
- **T/E:** an edited or unapproved rule set evaluated. Control: the body and digest are immutable once a version leaves `draft` (trigger, for every role); states move only forward; publishing is an R4 maker-checker request bound to `{ ruleSetId, version, digest }` with a 1 h minimum delay, and the executor re-checks the digest; agents cannot make R4 requests or check (`IPB-SEC-004`).
- **E:** a tenant changing a platform rule set. Control: RLS lets every tenant read `tnt_platform` sets but write them only in a platform context; a composite foreign key keeps each version in its rule set's tenant.
- **D:** a costly expression. Control: `rules.cel.max_cost` bounds AST nodes (with fixed depth and list limits), rows are at most 4 KiB, inputs at most 64 KiB, and evaluation runs under the time limit.
- **I:** decision inputs in clear. Control: inputs above INTERNAL are sealed together with FieldCrypto in `decision_log.inputs_enc`; `explain` returns values only for PUBLIC and INTERNAL inputs; the ledger holds digests only; simulation runs store counts and indexes, never inputs; invalid inputs are not stored.
- **R:** an unexplained decision. Control: every decision has a `dcs_` log row and a ledger entry; `explain` reads the log and the version body (`@IPB-07-AT-11`).

### 3.14 `@infrabyx/workflow` and the approvals additions (built, PL3 session 3)

- **E:** a request approved after its time, or a stale approval executed. Control: every request expires (7 days; 72 hours for R4, R5 and financial R3); an overdue or expired request is refused by `decide`, `execute` and `cancel` (`IPB-UX-012`) even before the timer runs; a trigger makes `expired_at` terminal for every role.
- **E:** escalation or a timer deciding. Control: escalation only notifies and raises an inbox item; timers only call the engine's `execute`, `remind`, `escalate` and `expire`, which keep every PL1 rule (checker ≠ maker, agents never check, delay windows); a scheduled action executes only after its window (`IPB-SEC-008`, `IPB-UX-005` by hand).
- **E:** a tenant loosening maker-checker. Control: `mc.checker_roles` can only narrow the action's roles (an empty or foreign list falls back to the platform roles); `mc.dual_checker_above` can only add a checker; the settings validator refuses loosening values (PL3-D-08); every `mc.*` change is itself an R4 request.
- **I:** cross-tenant reads by the timer poller. Control: the poller reads as the dedicated service reader `SVC_SCHEDULER` (owner answer #22, PL3-D-21; see 3.16), never as `PLT_AUDITOR_RO`; it fires each timer in its own tenant's context, where forced RLS applies.
- **E:** an UNDETERMINED rule decision reviewed by the person whose request produced it, or left unreviewed. Control: the inbox task goes to `ORG_CHECKER` (or `ORG_ADMIN` when the tenant has no checker), excludes the requesting principal from listing and resolving it, and escalates once to `ORG_ADMIN` after 48 hours by a timer, as approval requests do (owner answer #21).
- **T:** a lost, duplicated or late timer. Control: timers are rows written in the same transaction as the change that needs them; the poller runs as the reconciler; handlers re-check state, so a duplicate fire is a no-op; failures back off and give up after 5 attempts with a `job_failed` item; Temporal timer ids carry identifiers only (C-16).
- **I:** personal data in the Work Inbox. Control: titles are INTERNAL text built from action names and ids; the checker diff keeps values only for PUBLIC/INTERNAL payloads and field names above; the maker never sees the approval item for their own request.
- **R:** unexplained inbox or schedule changes. Control: every inbox, scheduled-action and timer write carries a ledger entry; `ItemCreated`/`ItemResolved` and `ScheduledAction*` events go to the outbox.

### 3.15 `@infrabyx/notify` and the PUSH adapters (built, PL3 session 4)

- **I:** addresses in NOTIFY's tables, events, queues or logs. Control: callers pass principal references; addresses come from the product's `ContactResolver` at delivery and are never stored; suppression and consent hold C-23 keyed hashes (CONFIDENTIAL, RLS); the ledger holds states and counts only.
- **T:** a held notice (collection, legal, KFS) sent twice. Control: `hold` classes are never resent automatically; an unknown outcome makes the delivery `held` with an inbox task, and a person's `decideHeld` is ledgered; `safe` classes are resent at most once, on the same row, with an attempt-scoped idempotency key.
- **E:** marketing without consent, or on WhatsApp. Control: default deny per address and purpose; a marketing class may use only its purpose's channel; WhatsApp marketing is refused by the catalogue lint while `mkt.meta.enabled` is false; collection and legal notices list `whatsapp` under `never_channels`, and org routing cannot add it.
- **E/D:** one tenant suppressing an address platform-wide. Control: platform rows are limited to hard bounces, complaints and invalid addresses from verified delivery reports (CHECK and service); only a platform context lifts them; tenant lifts are R2 maker-checker.
- **S:** unsubscribe link abuse. Control: random 32-byte tokens, stored as SHA-256, one use, 90 days, revocable; the link only withdraws consent.
- **I:** content in push payloads at a GLOBAL vendor. Control: the adapters refuse anything beyond title, deep link and ≤ 8 INTERNAL data keys (`IPB-NTF-006`); device tokens are sealed with FieldCrypto; the FCM service-account key stays in SECRETS and only `@infrabyx/crypto` signs with it (C-24); the access token is cached in memory only.
- **D:** a channel outage or a runaway sender. Control: `kill.msg.<channel>` refuses the channel before any I/O; quiet hours and the digest bound non-urgent volume.
- **I:** cross-tenant reads by the dispatcher and the unsubscribe link. Control: the service readers `SVC_NOTIFY_DISPATCH` (delivery-queue columns) and `SVC_NOTIFY_UNSUBSCRIBE` (token lookup by hash); every delivery runs in its own tenant's context (owner answer #22, see 3.16).
- **E:** collection or recovery messages outside permitted hours. Control: collection classes go only inside the contact window (the complement of the 21:00–08:00 quiet hours in the recipient's zone, from the product's time-zone hook, default Asia/Kolkata), never bypassed; a product may narrow the window and a wider one is refused, so the send fails closed (owner answer #23).

### 3.18 ESIGN adapters `leegality` and `digio` and C-25 (built, PL3 session 6)

- **S:** a forged webhook that marks a document signed. Control: Leegality's `mac` (HMAC-SHA1 of the document id with the private salt) is verified by C-25 in constant time, with a 5-minute window when a timestamp is sent; Digio documents no signature, so its callback URL carries our C-19 secret (`ipb_token`, ≥ 32 random bytes, redacted by the scrubber); in both cases the adapter reads the envelope back from the vendor and returns only that status, so a webhook is never more than a trigger (`@IPB-10-27`); an unknown document is refused before any read-back.
- **T:** a silent signature-type downgrade. Control: each signer's method is fixed when the envelope is created and kept in the product's `EsignEnvelopeStore`; a method the adapter cannot provide exactly (Leegality without a workflow for it, Digio biometric Aadhaar or account eSign, wet ink anywhere) is refused with `method_unsupported`; Aadhaar and DSC sessions are refused for a signer created with another method.
- **T:** the wrong document signed. Control: documents travel by reference; the adapter reads the PDF from STORAGE and refuses it when its SHA-256 differs from the reference, before any request; the signed PDF is written to STORAGE (`REGULATED`) with its own SHA-256.
- **I:** documents and signers at the ESP. Control: both vendors are India-hosted (`IN`); signer names, e-mail addresses and phone numbers are recipient fields (IPB-DEV-05); credentials (Leegality auth token and salt, Digio client secret) come from SECRETS and never appear in URLs or logs.
- **R:** unverifiable signatures. Control: signature records name the ESP, the vendor document and its audit trail; PAdES validation (`verifySignature`) is `unsupported` on both adapters until a validator is built (PL3-D-23).
- **Residual:** HMAC-SHA1 for Leegality is accepted for verification only (PL3-C-02); move to SHA-256 when Leegality offers it (#55). Digio's callback rests on the URL secret, and its source ranges are unknown (#56).

### 3.17 `@infrabyx/export` and C-22 (built, PL3 session 5)

- **I:** one tenant's data in another tenant's archive. Control: the snapshot runs in the requesting tenant's context with forced RLS and an explicit `tenant_id` filter; archives, jobs and downloads are RLS-scoped; storage keys carry the tenant id and the adapters refuse cross-tenant keys.
- **I:** data that must never leave. Control: map fields that are SECRET, binary, sealed (`*_enc`) or named like Aadhaar or card data are refused (`IPB-EXP-004`); restricted folders are refused (`IPB-EXP-001`); approval payloads and notification variables are not in `REF-EXPORT-1.0` or `-1.1`; file and folder names carry ids only, plus the tenant name in the root folder; job and event payloads describe the job, never its content.
- **T:** an archive changed after export, or a forged one. Control: every file has a SHA-256 in `manifest.json`, which carries a pack hash and is signed with a detached ES256 JWS made by KMS `sign` with the platform export-signing key (C-22); the shipped offline verifier checks hashes, unlisted files, the signature, control totals, CSV headers and the audit chain; the `export.archive` row is insert-only, and each download ledgers `<archive id>:<sha256>`.
- **T:** an archive that silently disagrees with the live system. Control: one REPEATABLE READ snapshot, recounted per table before signing; a difference fails the job (`IPB-EXP-003`).
- **D:** export abuse as a load or exfiltration path. Control: 5 concurrent and 20 a day per principal (`IPB-SEC-019`); only user principals export, never agents: `ORG_OWNER` directly, `ORG_ADMIN` only through an R2 approval that only an `ORG_OWNER` may check (PL3-D-25), and an ORG_ADMIN downloads only the archive of their own approved job; products cannot add roles; presigned URLs last at most 300 s.
- **I:** archives kept longer than needed. Control: each archive is downloadable for 30 days (owner approval, PL3-D-25); `sweep` deletes it from STORAGE and records `export.archive_deletion` and an `export.archive.delete` ledger entry in one transaction; a download past `expires_at` is refused (`IPB-EXP-006`) even before the sweep runs. The sweep reads across tenants as `SVC_EXPORT_SWEEP` (§3.16), which sees ids, tenant and times only, never a storage key.
- **E:** a new destination used to exfiltrate. Control: only download exists; any other destination is refused (`IPB-EXP-002`) until it is built as the delay-window action of IPB-07-27(c).
- **S/R:** downloads that cannot be traced. Control: ledgered request, start, archive creation and each download; the signed `ExportCompleted` JWS is kept with the archive.
- **Residual:** the export-signing key is a single platform key per environment, so its compromise affects every tenant's future archives; it never leaves KMS and is used only for C-22 (R3-06).

### 3.19 `@infrabyx/ai` gateway, registry and routing (built, PL4 session 2)

- **I:** CONFIDENTIAL or REGULATED data sent outside India or to a provider that keeps it. Control: the band is computed from the highest input class and cannot be lowered (`IPB-AI-020`). `in_zero` admits only IN/SELF models with `retention_policy = ZERO` and a training opt-out; SECRET admits only SELF. `trust.privacy.cross_border_ai_allowed` defaults to false, so even INTERNAL data stays IN/SELF. A pin is honoured only when eligible (`IPB-AI-012`). Failover never leaves the band, and with no eligible model the call fails closed (`IPB-AI-021`). An adapter whose observed region differs from its configured one, or whose residency differs from the model record's, is never selected (IPB-03-23).
- **T/E:** a model promoted without evidence, or an unreviewed default change. Control: APPROVED and DEFAULT are R4 approvals checked by `PLT_SECURITY_OFFICER`, never by the maker. A database CHECK refuses an APPROVED or DEFAULT row without retention and training evidence. Eval scores are compared with the current DEFAULT. BLOCKED applies at once, overrides pins and drops the model from the defaults. Registry rows are writable only in platform scope.
- **I:** prompt or completion content in logs, traces, events or the run table. Control: content capture is off by construction (owner decision): `aiTrace` sets only the `SEMCONV` attributes and refuses content-like names, run rows and events have no content columns, and a test asserts that marker strings never reach `ai.run`, the outbox or the ledger.
- **T:** prompt injection through documents or tool results. Control: data blocks are delimited under a fixed "data, never instructions" instruction. Instruction-like phrases, forged markers and non-allow-listed links are removed. A tool call outside the request's allow-list halts the run (`IPB-AI-040`, `GuardrailTriggered`). Classifiers (session 4) add defence in depth.
- **D:** runaway cost, or one provider's outage. Control: tenant daily and feature monthly caps (`IPB-AI-022`), with token caps while prices are unset; per-model breaker; kill switches per adapter, feature, tenant and globally, which turn on at once and turn off only with a checker (`mc_deactivate`); a switch that cannot be read counts as on.
- **R:** an untraceable AI call. Control: one `ai.run` row per call, including refused and blocked calls, with route, candidates considered, principal and outcome, and a ledger entry in the same transaction.
- **Residual:** the breaker is per process (A-05), and the guardrails are rule-based until a classifier provider is approved (A-06).

### 3.20 `@infrabyx/ai` scrubber, guardrails, evals, retrieval and run retention (built, PL4 session 4 and owner answers #27, #30)

- **I:** personal identifiers sent to a model provider. Control: above PUBLIC every outbound text (rendered prompt, messages, data blocks, texts to embed) is scrubbed into `<PII:KIND:n>` tokens before any adapter sees it; the reverse map lives only in the request's memory and is never stored, logged or traced. Detection raises the request's class (an Aadhaar or PAN makes it REGULATED), so it also tightens routing; scrubbing never lowers the class. An invalid `ai.scrub.patterns` fails closed. Token-shaped text in the input is defused, so input cannot forge a token that would expand to another value.
- **T:** prompt injection and jailbreaks in the caller's own text. Control: the rule-based input classifier (English, Hindi, Hinglish) blocks at `ai.guard.input_threshold.<feature>` before routing (`IPB-AI-042`, `GuardrailTriggered(injection, refuse)`); injection inside data blocks is neutralised and recorded (`neutralise`), and the tool allow-list still halts any call it provokes (`@IPB-03-AT-01`).
- **I:** the model reveals hidden context or invents personal data or sources. Control: the output classifier withholds echoed system-prompt sentences and the data instruction, redacts PII the inputs did not carry, drops citations to sources outside the request's data blocks, and replaces reserved advice with a neutral notice; `ai.guard.output_policy.<feature> = refuse` withholds the whole answer (`blocked`).
- **I:** one tenant's documents retrieved for another. Control: `ai.retrieval_index` and `ai.chunk` have RLS forced and every search runs in the caller's context (`@IPB-03-AT-05`: zero cross-tenant results); the product's `authorize` callback removes resources the caller may not read (fail closed); a data-class ceiling per call drops chunks above what the feature may receive. Chunk text is sealed with FieldCrypto; the embedding and the lexical vector are built from scrubbed text, so neither carries identifiers (they are still document content, classed CONFIDENTIAL).
- **T:** a prompt version activated without passing its golden set, or an eval that silently calls a paid model. Control: activation needs an eval pass recorded for the exact content hash; `prompts sync` activates only with a current committed result, and staging and above need a live result; CI runs `ai-prompt-lint` and `ai-eval-gate` on the scripted fake model; `eval --live` refuses to start without an approval reference (O-6).
- **S/E:** the C-24 signer used to mint something other than a Google token. Control: `signServiceAccountAssertion` accepts only the FCM and cloud-platform scopes and only Google's token endpoint as audience (PL4-C-01); the key comes from SECRETS, the token is cached and never logged.
- **R/I:** AI run metadata kept forever, or a run deleted that an approval or statutory output depends on. Control: `RunRetention.sweep` deletes routine runs after 180 days with one ledger entry per run, reading across tenants only through `SVC_AI_RUN_SWEEP` (id, tenant, time; ledgered per tenant); a restrictive PostgreSQL policy refuses deleting any run younger than 180 days or under an active hold.
- **Residual:** the classifiers are rule-based (A-06) and the PII detectors pattern-based, so an unusual shape can pass (R-16); chunks of a deleted resource stay until the owner decides their deletion (#34), filtered meanwhile by the `authorize` callback.

### 3.21 `@infrabyx/ai` IMAGE_GEN, labelling and the publish gate (built, PL4 session 5)

- **T/R:** a generated image passed off as genuine, or published without a label (IT Rules SGI labelling, IPB-03-06). Control: every image is labelled before storage (visible band, XMP, PNG text chunk); an image that cannot be labelled is refused and never stored; `ai.image` records `sgi_label`, and a CHECK forbids approving an unlabelled image; `assertPublishable` re-reads the stored object and checks its hash and XMP before the CMS publishes.
- **E:** publishing without a human. Control: `ai.image.publish` is an R2 approval checked by a content role; the approvals engine refuses the requester and any agent as checker; `assertPublishable` fails with `IPB-AI-032` until it is executed.
- **I/T:** an image of a real person, a customer, a regulator or a court, or a forged document. Control: the use enum and a rule-based subject guard (`IPB-AI-030`); personal data in a prompt is refused; Imagen runs with `personGeneration: dont_allow`. Residual: rules can miss paraphrases (#36, R-16).
- **I:** prompt content stored or logged. Control: only the prompt hash is stored; adapters log no bodies; spans carry no content.
- **D:** an image provider outage. Control: the same routing, breaker, kill switches (`ai.kill.*`, `ai.image.enabled`) and fail-closed behaviour as chat.

### 3.22 `@infrabyx/vidhi` kernel: locked actions, autonomy and tasks (built, PL4 session 6)

- **E:** an agent executes a payment, credit decision, signature, deletion, external share, approval or grant on its own. Control: the frozen kernel locked list (word-matched, additive product lists) sends any such tool to NEEDS_APPROVAL at every level; only a human with the action's role approves; the approvals engine refuses agents and the maker; an agent that insists fails the task, emits `LockedActionAttempted` and is demoted to L2; the kernel's agent-verb guard (IPB-SEC-004) stays as a second layer.
- **E:** autonomy raised without evidence or by the wrong person. Control: L3/L4 only through an R4 approval checked by `ORG_OWNER`, with IPB-03-70 evidence and the cool-down; product ceilings are constants (no product reaches L4; Udofin borrowers L1); scheduled runs are capped at L2/L3.
- **T/R:** a double execution or an execution after a kill switch or a rejection. Control: compare-and-set transitions with a row lock, a trigger that freezes terminal states, `IPB-VID-022` for late or duplicate decisions, the kill-switch sweep, and one ledger entry per transition and tool call.
- **I:** tool arguments (possibly CONFIDENTIAL) stored in clear. Control: they travel only in the approval payload, sealed by FieldCrypto at the skill's class; task rows hold no content.
- **I/T:** reserved advice given as Vidhi's own, or the brand name leaking into audit. Control: the output classifier plus a hand-off card for advice questions; the display name is presentation only, and runs, events and ledger rows say `vidhi`.
- **Residual:** word matching can over-lock a harmless tool (#37); an under-tagged product tool with a novel verb relies on the product's manifest review.

### 3.16 Cross-tenant service readers (owner answer #22, PL3-D-21)

Background workers that must find due work across tenants (the workflow timer poller, the NOTIFY dispatcher, the one-click unsubscribe link, the export sweep) read through `ServiceReader` in `@infrabyx/tenancy` as one of the `SVC_` roles in `SERVICE_READER_ROLES` (`contracts/roles`).

- **E:** a background identity reading or changing more than it needs. Control: each role maps to its own database role (`svc_scheduler`, `svc_notify_dispatch`, `svc_notify_unsubscribe`, `svc_export_sweep`, created by the owning package's migration), granted `SELECT` on the named columns of its tables only and nothing else (one table each, except `svc_export_sweep`: jobs, archives and the deletion marker, ids and times only, under platform-scope read policies limited `to` that role; PL3-D-25); the kernel runs a platform-scope read as that role (`SET LOCAL ROLE`), so a query on any other table or column fails with `42501`, and forced RLS still applies.
- **E:** a reader approving, writing or impersonating. Control: the kernel refuses every mutation by a reader except the ledger entry recording its own read, in a tenant context (`IPB-SEC-005`); its context must be a service principal with exactly one reader role, no `PLT_*` role, no `act` and no break-glass; a token claiming a reader role is refused (`contextFromClaims`), so readers exist only in-process.
- **R:** an unrecorded cross-tenant read. Control: the query must select `tenant_id`; each read that returned rows writes one `platform.service_read` ledger entry in every tenant it touched (actor = the reader principal, resource = the table) and calls the operational `onServiceRead` hook with the row count per tenant. An empty read returns no tenant data and writes nothing.
- **Residual:** the platform-scope RLS read policies on these tables still admit PLT_* principals (people, under IPB-02-11), as before.
