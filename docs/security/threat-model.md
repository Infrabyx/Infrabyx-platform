# Threat model — infrabyx-platform

**Status:** living document (PL2-D-43). Updated by every PR that adds a port, adapter, package or data flow; the PR checklist points here. **Last updated:** 2026-10-27 (PL5 session 5c: `@infrabyx/consent` — the CMP, consent texts, the consent and acceptance ledgers, script gating and the consent purge).

**Method:** STRIDE (Spoofing, Tampering, Repudiation, Information disclosure, Denial of service, Elevation of privilege) per package and per IPB-01 port, against the IPB-02 controls. Each control links to where it is specified (plan section, decision ID) and how it is proven (test tag). "Built" means merged on `main`; "planned" means specified in a phase plan and not yet built.

## 1. Scope, assets and trust boundaries

**In scope:** the `@infrabyx/*` packages, the reference routing files, CI workflows and the test infrastructure in this repository. **Out of scope here:** product code (each product keeps its own model), the cloud accounts themselves (PL6 Terraform and runbooks), and vendor internals (Vendor Assurance Room, IPB-D-09).

**Data classes** (IPB-02 §02.4.3.1): `PUBLIC` < `INTERNAL` < `CONFIDENTIAL` < `REGULATED` < `SECRET`. A class follows the content, not its protection (PL2 plan §6.9). A caller may only raise the class of a port call, never lower it below the port default (PL2-D-03).

| Asset                                                         | Class                   | Where it lives                                              |
| ------------------------------------------------------------- | ----------------------- | ----------------------------------------------------------- |
| Tenant business records                                       | CONFIDENTIAL–REGULATED  | Product schemas (RLS), field-encrypted where REGULATED      |
| REGULATED fields (PAN, Aadhaar, bank account, card last four) | REGULATED               | Field envelope (PL1 C-04), masked everywhere else           |
| Audit ledger                                                  | INTERNAL (digests only) | `audit.ledger`, hash-chained, append-only; signed anchors   |
| Secrets, keys, tokens                                         | SECRET                  | SECRETS / KMS ports only; never env in production           |
| Idempotency results                                           | as the call             | `connectors.idempotency_record`, sealed ≥ CONFIDENTIAL      |
| Telemetry                                                     | INTERNAL (scrubbed)     | OTLP → Collector → Grafana stack, `IN`                      |
| Flag state                                                    | INTERNAL                | Unleash or `config.flag_value`; snapshot in `config`        |
| Seed credentials                                              | SECRET                  | Generated per run, `SEED_CREDENTIALS.md` never committed    |
| Published packages                                            | PUBLIC (to the org)     | GitHub Packages; provenance through `release.yml` on `main` |

**Trust boundaries:**

1. **Caller → kernel.** Every mutation runs in `PgKernel.mutate` with a verified tenant context; RLS is the last line (IPB-02-12).
2. **Kernel → port (router).** The router enforces data class, residency, recipient delivery and idempotency before any I/O (PL2 plan §3.1, §3.5, §3.12).
3. **Adapter → vendor (egress).** HTTPS only, host allow-list, no redirects (IPB-02-43, plan §3.7).
4. **Vendor → platform (webhooks).** Signature verified, de-duplicated, ledgered (IPB-10-27, plan §3.8).
5. **CI and supply chain → `main` → registry.** SHA-pinned actions, 7-day dependency age, publish only from `main` (IPB-02-33, PL2-D-32).

## 3. Packages

### 3.1 `@infrabyx/contracts` (built)

Types, schemas and error codes only; no I/O.

- **T:** a schema too loose lets bad data through every product. Control: Zod strict schemas, payload data-class annotations, and `ipb/port-data-class` lint (an unannotated field fails).
- **I:** an error leaks internal detail. Control: RFC 9457 errors with code and help key; adapters put vendor detail in `meta`, never in `detail` shown to users (IPB-10).

### 3.2 `@infrabyx/crypto` (built)

- **I:** key material logged or serialised. Control: `SecretKey` is opaque (`toJSON`, `toString` and `inspect` print the ID only); material lives in a `WeakMap`.
- **T/S:** wrong algorithm or weak parameters. Control: the algorithm registry and CBOM (PL1), `assertApproved`, and the approved C-items only (plan §9). A new primitive is a stop-and-ask (CLAUDE.md working mode, item 1).
- **I:** joinable pseudonyms across purposes. Control: per-purpose HKDF sub-keys; telemetry hashes use `ipb/telemetry-id/v1` (PL2-D-36).
- **S:** forged or confused tokens. Control: C-11 verifier (X-16); `jose` only as a test devDependency, refused at runtime by `ipb:check`.
- **S:** forged vendor callbacks. Control: C-13 verifiers (X-17); webhook secrets we generate are 32 random bytes (C-19).

### 3.3 `@infrabyx/config` (built)

- **T:** a setting read before registration, or a production secret in env. Control: settings registry, env guard (exit 78) and the `process.env` lint (IPB-01-19).
- **E:** a flag flipped without governance. Control: `FlagAdmin` (kill switches by PLT_RELEASE_MANAGER/PLT_SECURITY_OFFICER, `fut.*` through R3 maker-checker) with a ledger entry (PL1-D-11).
- **D:** flag provider down. Control: last-known-good snapshot ≤ 24 h, then registry defaults; unknown `kill.*` evaluates on (X-10).

### 3.4 `@infrabyx/tenancy` (built)

- **S:** forged tenant or actor. Control: context only from verified claims; RLS insert policies bind `app.tenant_id` and `app.actor_id`.
- **E:** impersonation or break-glass abuse. Control: time-boxed, reason-required, ledgered; impersonated sessions cannot approve (`IPB-SEC-003`).
- **I:** REGULATED fields in plaintext. Control: field envelope encryption with per-tenant keys (PL1 C-04, C-15) and server-side masking; format v2 binds each data key to its tenant and purpose (X-18).
- **T:** a shipped migration edited. Control: checksums in `meta.migration_checksums`; migration-lint `--record-checksums`; CLAUDE.md "never edit a migration that has shipped".

### 3.5 `@infrabyx/audit` (built)

- **R:** an action without a trace. Control: ledger-required commit (X-02); trigger-computed chain so no application path writes an unchained row.
- **T:** history rewritten. Control: append-only for every role (X-03); weekly verifier emits `LedgerChainBroken`; signed daily anchors on write-once storage (PL1 C-03).
- **I:** payloads in the ledger. Control: before/after stored only as canonical digests; IP and user agent as keyed pseudonyms (PL1 C-02).

### 3.6 `@infrabyx/seed` (built)

- **E/I:** seeds or seed credentials in production. Control: refusal first in `prod`, `dr`, `pre-prod` (`SEED_REFUSED_ENVS`, PL1-D-06); generated passwords; `SEED_CREDENTIALS.md` ignored and checked by `ipb:check`; forced rotation and MFA on first production login (IPB-D-04).

### 3.7 `@infrabyx/testing` (built)

- **T (supply chain):** a test image swapped. Control: images pinned by digest from Docker Hub, kept equal to `infra/docker/TEST_IMAGES.md` by a unit test; images from session 2 on were at least 7 days old when pinned (PL2-D-37).
- **I:** sandbox credentials printed. Control: the sandbox-leg gate prints missing variable names only, never values.

### 3.8 `@infrabyx/connectors` core (built)

- **S:** a forged vendor webhook. Control: signature verification before any processing, 401 on failure, inbox de-duplication, ledger entry `connectors.webhook.received` (plan §3.8; C-13 for per-vendor rules, session 3 onwards).
- **T:** a replayed or altered idempotent request. Control: request hash (C-20) compared on replay, mismatch is `IPB-PORT-004`; keys stored as SHA-256 hashes.
- **R:** idempotency outcomes untraceable. Control: each state change is ledgered (PL2-D-35).
- **I:** a result of a REGULATED call stored readable. Control: results ≥ CONFIDENTIAL are sealed with tenant field encryption; RLS on `connectors.idempotency_record`.
- **I:** data sent to a vendor that cannot hold it. Control: X-05, X-06, checked before I/O; refusal emits `ResidencyViolationBlocked`.
- **D:** a failing vendor stalls callers. Control: circuit breaker per adapter (PL2-D-33), timeouts and bounded retries in egress, health registry; STORAGE writes fail fast instead of queueing bytes (IPB-DEV-06).
- **E/T:** SSRF through a vendor URL. Control: egress allow-list and no redirects (X-07).
- **Money:** a money call re-sent after an unknown outcome would double-charge or double-refund. Control: unknown outcomes stay pending and go to reconciliation; never re-sent (X-08, P-05).

### 3.9 `@infrabyx/connectors` IDENTITY and AUTHZ (built)

- **S:** a forged, re-signed or other-issuer token. Control: X-16 with ES256 only per issuer; JWKS only from the configured URL through egress; claims mapped to `VerifiedClaims`, unknown principal types refused, roles outside the platform format dropped.
- **S/E:** a user sets their own tenant or type. Control: tenant, type, product scope and external id are admin-only attributes (Keycloak `ADMIN_EDIT`) or admin-set metadata (Zitadel); the kernel context is built only from verified claims (IPB-02-13).
- **E:** a privileged role without MFA. Control: forced enrolment at login (Keycloak required action; Zitadel `forceMfa`), and the API guard refuses a token without an MFA method in `amr` (`IPB-SEC-001`); SMS never counts as MFA.
- **D (a second factor lost between login and token):** Control: each `amr` reference lives for the realm's session lifetime, so a code exchanged seconds after the TOTP step, or a refreshed token, still reports `otp`; a session that never ran the TOTP step carries none (R1-D-16).
- **R/E:** a de-provisioned user keeps working. Control: SCIM deactivation, `revokeSessions`, a role change and back-channel logout write a revocation (hashed subject, RLS, ledgered) before the IdP call; every replica refuses within 15 s (PL2-D-53).
- **D:** IdP outage. Control: JWKS cached 24 h so API calls continue; new logins fail with `IPB-IDN-002`.
- **E:** impersonation without an audited `act`. Control: impersonation tokens are unsupported on both adapters (PL2-D-55, owner); the kernel refuses mutations under `act` (`IPB-SEC-003`). Support access, when first needed, is a platform-issued read-only token on an approved, ticketed request, at most 60 minutes, ledgered and visible to the tenant's `ORG_OWNER`.
- **E:** an AUTHZ allow by mistake. Control: deny by default, PDP failure denies (`IPB-AUTHZ-001`), agents denied before the PDP and in policy (X-14), allow-only cache ≤ 5 s, one decision table proven on both engines.
- **I:** bootstrap secrets. Control: `applyRealm` and `applyInstance` return generated client secrets for the SECRETS port and never log them; they run only in deploy jobs and tests.

### 3.10 `@infrabyx/connectors` STORAGE, QUEUE and WORKFLOW (built)

- **T:** a retained record overwritten or deleted. Control: COMPLIANCE-mode Object Lock; the adapter also refuses a new version, a delete marker or an upload URL while retention applies (`IPB-STOR-003`); break-glass cannot delete a locked version (@IPB-02-AT-13).
- **I:** documents readable across tenants or under the wrong key. Control: keys outside the caller's tenant refused (`IPB-PORT-003`); SSE-KMS with the tenant's own CMK when it has one (C-17), so a tenant purge covers documents.
- **I:** a long-lived or repurposed presigned URL. Control: SigV4, 1–300 s, bound to the method and, for uploads, the content type (IPB-02-15).
- **I:** personal data on the queue or in Temporal's readable fields. Control: queue payloads are flat INTERNAL maps checked before I/O; workflow ids, names and task queues are checked to be identifiers; every Temporal payload and failure is encrypted (C-16) and unencrypted payloads are refused.
- **E:** runtime DDL by the queue. Control: pg-boss's schema is a checked-in migration; its role has DML and EXECUTE only (proven in the contract leg).
- **I:** decrypted workflow failures in worker logs. Control: worker logs go through the OBSERVABILITY scrubber (X-09); failures should carry codes, not personal data.
- **D:** a store outage. Control: writes fail fast (`IPB-STOR-002`) and the caller's outbox retries; reads fail over to the DR replica; queue enqueue failures go to the outbox; Temporal outages pause timers.

### 3.11 `@infrabyx/connectors` EMAIL, SMS and WHATSAPP (built)

- **S:** forged delivery, bounce or status webhooks. Controls:
  - SES events arrive through SNS: SignatureVersion 2 only, certificate host pinned to ap-south-1/2, one TopicArn, a one-hour timestamp window, and subscription confirmation followed only to an SNS host after verification (C-13).
  - Meta webhooks: `X-Hub-Signature-256` over the raw body; the subscription handshake compares the verify token in constant time.
  - Vendors that do not sign (Brevo, MSG91, Gupshup SMS and WhatsApp) present our C-19 secret, compared in constant time:
    - as a bearer header (Brevo, MSG91);
    - as the `ipb_token` URL parameter when the vendor can only call a URL (Gupshup), which ingress logs must redact;
    - Brevo also needs its published source ranges.
  - Failures answer `IPB-API-018` without logging the body.
- **T:** a replayed webhook processed twice. Control: every event carries a stable vendor event id for the module inbox (@IPB-02-AT-05 scenario 2).
- **I:** CONFIDENTIAL content inline, or documents attached:
  - bodies above INTERNAL are refused before any request;
  - attachments must come from GENERAL or PUBLIC_ASSETS storage, at most 10 files and 10 MiB;
  - anything else goes as a secure link.
- **I:** recipients at a GLOBAL vendor. Control: X-06; Brevo, Gupshup WhatsApp and Meta refuse to start without a DPA reference; Brevo's manual suppression is refused because it would need a contact record (PL2-D-64).
- **I:** credentials in URLs. Control:
  - Gupshup SMS credentials go in a POST body;
  - MSG91's key goes as a header, the balance check included;
  - no API key is put in a query string.
- **T:** non-DLT SMS content. Control: template, header, entity id and variable count are checked before any request; the Gupshup text is rendered from the registered DLT text.
- **E:** marketing sent by mistake. Control: `mkt.meta.enabled` (default false); the template category is read before every send and marketing templates and submissions are refused while it is off (OWN-08).
- **D:** a vendor outage. Control:
  - SES pauses map to `IPB-PORT-002` (reputation block) so the router can fail over;
  - Brevo serves as a failover target only for brands whose domain is authenticated on Brevo;
  - SMS fails over msg91 → gupshup-sms with the same DLT mapping;
  - WhatsApp has no failover between BSPs.

### 3.12 `@infrabyx/connectors` PAYMENTS (built, test mode only)

- **T:** amount tampering or rounding. Control: integer paise in and out, INR only; Cashfree decimals are written as exact text and read back exactly or refused (P-04).
- **S:** a forged webhook or checkout return. Controls (P-09):
  - Razorpay `X-Razorpay-Signature` and Cashfree `x-webhook-signature` are checked over the raw body; Cashfree's timestamp must be within ±5 minutes.
  - A Razorpay checkout return is checked by its `razorpay_signature`; a Cashfree return by fetching the order server-side.
  - Client-side success is never trusted.
- **E:** a refund without approval, or more than was paid. Control:
  - an approved R3 request for exactly the refund's payload is required (`IPB-SEC-006`);
  - the PA's own refund list is read at execution;
  - the cap is the captured amount minus earlier refunds;
  - an agent can only make the request (P-07).
- **T:** a duplicate charge or refund after a timeout. Control: the idempotency record is pending before the call; orders are looked up at the PA by our reference first; refunds and mandates that cannot be resolved go to the human queue and are never retried automatically (P-05, P-07).
- **E:** live money by accident. Control: no live key anywhere in this repository, CI or non-production; the env guard and the adapters refuse live credentials outside prod/dr (P-03); `kill.payments` stops new money operations (P-12).
- **D:** a PA outage. Control: new orders fail over Razorpay → Cashfree; refunds, mandates, captures and checkout sessions stay with the PA that owns them (P-08).
- **I:** payment details beyond what billing needs. Control:
  - only IDs, amounts, statuses, method categories and times leave the adapters (P-10);
  - the customer phone and email reach only Cashfree, which requires them;
  - card data never touches Infrabyx (hosted checkout, SAQ A).

### 3.13 `@infrabyx/rules` and the RULES engine adapters (built, PL3 session 2)

- **T:** a decision that defaults to allow. Control: an invalid input (missing, mistyped or undeclared), an engine error, a timeout (`rules.eval.timeout_ms`) or a matched `verify` row that would drive a statutory output is `UNDETERMINED` with empty outputs, logged, and raised to the Work Inbox (`HumanQueue`, `review_undetermined`); there is no default row (IPB-01 RULES).
- **T:** engines disagreeing, or a row meaning something else on another engine. Control: one CEL subset parsed and type-checked by `@marcbachmann/cel-js`, lowered to an IR that every engine compiles; ZEN cells are generated from the IR, never from the row text, so a malformed cell (which ZEN reads as "no match") cannot occur; string literals without quotes, backslashes or control characters; plain-notation numbers; reserved field names refused; a draft must compile on all three engines before it is saved; a differential test proves agreement.
- **T/E:** an edited or unapproved rule set evaluated. Control: the body and digest are immutable once a version leaves `draft` (trigger, for every role); states move only forward; publishing is an R4 maker-checker request bound to `{ ruleSetId, version, digest }` with a 1 h minimum delay, and the executor re-checks the digest; agents cannot make R4 requests or check (`IPB-SEC-004`).
- **E:** a tenant changing a platform rule set. Control: RLS lets every tenant read `tnt_platform` sets but write them only in a platform context; a composite foreign key keeps each version in its rule set's tenant.
- **D:** a costly expression. Control: `rules.cel.max_cost` bounds AST nodes (with fixed depth and list limits), rows are at most 4 KiB, inputs at most 64 KiB, and evaluation runs under the time limit.
- **I:** decision inputs in clear. Control: inputs above INTERNAL are sealed together with FieldCrypto in `decision_log.inputs_enc`; `explain` returns values only for PUBLIC and INTERNAL inputs; the ledger holds digests only; simulation runs store counts and indexes, never inputs; invalid inputs are not stored.
- **R:** an unexplained decision. Control: every decision has a `dcs_` log row and a ledger entry; `explain` reads the log and the version body (`@IPB-07-AT-11`).

### 3.14 `@infrabyx/workflow` and the approvals additions (built, PL3 session 3)

- **E:** a request approved after its time, or a stale approval executed. Control: every request expires (7 days; 72 hours for R4, R5 and financial R3); an overdue or expired request is refused by `decide`, `execute` and `cancel` (`IPB-UX-012`) even before the timer runs; a trigger makes `expired_at` terminal for every role.
- **E:** escalation or a timer deciding. Control: escalation only notifies and raises an inbox item; timers only call the engine's `execute`, `remind`, `escalate` and `expire`, which keep every PL1 rule (checker ≠ maker, agents never check, delay windows); a scheduled action executes only after its window (`IPB-SEC-008`, `IPB-UX-005` by hand).
- **E:** a tenant loosening maker-checker. Control: `mc.checker_roles` can only narrow the action's roles (an empty or foreign list falls back to the platform roles); `mc.dual_checker_above` can only add a checker; the settings validator refuses loosening values (PL3-D-08); every `mc.*` change is itself an R4 request.
- **I:** cross-tenant reads by the timer poller. Control: the poller reads as the dedicated service reader `SVC_SCHEDULER` (owner answer #22, PL3-D-21; see 3.16), never as `PLT_AUDITOR_RO`; it fires each timer in its own tenant's context, where forced RLS applies.
- **E:** an UNDETERMINED rule decision reviewed by the person whose request produced it, or left unreviewed. Control: the inbox task goes to `ORG_CHECKER` (or `ORG_ADMIN` when the tenant has no checker), excludes the requesting principal from listing and resolving it, and escalates once to `ORG_ADMIN` after 48 hours by a timer, as approval requests do (owner answer #21).
- **T:** a lost, duplicated or late timer. Control: timers are rows written in the same transaction as the change that needs them; the poller runs as the reconciler; handlers re-check state, so a duplicate fire is a no-op; failures back off and give up after 5 attempts with a `job_failed` item; Temporal timer ids carry identifiers only (C-16).
- **I:** personal data in the Work Inbox. Control: titles are INTERNAL text built from action names and ids; the checker diff keeps values only for PUBLIC/INTERNAL payloads and field names above; the maker never sees the approval item for their own request.
- **R:** unexplained inbox or schedule changes. Control: every inbox, scheduled-action and timer write carries a ledger entry; `ItemCreated`/`ItemResolved` and `ScheduledAction*` events go to the outbox.

### 3.15 `@infrabyx/notify` and the PUSH adapters (built, PL3 session 4)

- **I:** addresses in NOTIFY's tables, events, queues or logs. Control: callers pass principal references; addresses come from the product's `ContactResolver` at delivery and are never stored; suppression and consent hold C-23 keyed hashes (CONFIDENTIAL, RLS); the ledger holds states and counts only.
- **T:** a held notice (collection, legal, KFS) sent twice. Control: `hold` classes are never resent automatically; an unknown outcome makes the delivery `held` with an inbox task, and a person's `decideHeld` is ledgered; `safe` classes are resent at most once, on the same row, with an attempt-scoped idempotency key.
- **E:** marketing without consent, or on WhatsApp. Control: default deny per address and purpose; a marketing class may use only its purpose's channel; WhatsApp marketing is refused by the catalogue lint while `mkt.meta.enabled` is false; collection and legal notices list `whatsapp` under `never_channels`, and org routing cannot add it.
- **E/D:** one tenant suppressing an address platform-wide. Control: platform rows are limited to hard bounces, complaints and invalid addresses from verified delivery reports (CHECK and service); only a platform context lifts them; tenant lifts are R2 maker-checker.
- **S:** unsubscribe link abuse. Control: random 32-byte tokens, stored as SHA-256, one use, 90 days, revocable; the link only withdraws consent.
- **I:** content in push payloads at a GLOBAL vendor. Control: the adapters refuse anything beyond title, deep link and ≤ 8 INTERNAL data keys (`IPB-NTF-006`); device tokens are sealed with FieldCrypto; the FCM service-account key stays in SECRETS and only `@infrabyx/crypto` signs with it (C-24); the access token is cached in memory only.
- **D:** a channel outage or a runaway sender. Control: `kill.msg.<channel>` refuses the channel before any I/O; quiet hours and the digest bound non-urgent volume.
- **I:** cross-tenant reads by the dispatcher and the unsubscribe link. Control: the service readers `SVC_NOTIFY_DISPATCH` (delivery-queue columns) and `SVC_NOTIFY_UNSUBSCRIBE` (token lookup by hash); every delivery runs in its own tenant's context (owner answer #22, see 3.16).
- **E:** collection or recovery messages outside permitted hours. Control: collection classes go only inside the contact window (the complement of the 21:00–08:00 quiet hours in the recipient's zone, from the product's time-zone hook, default Asia/Kolkata), never bypassed; a product may narrow the window and a wider one is refused, so the send fails closed (owner answer #23).

### 3.18 ESIGN adapters `leegality` and `digio` and C-25 (built, PL3 session 6)

- **S:** a forged webhook that marks a document signed. Control: Leegality's `mac` (HMAC-SHA1 of the document id with the private salt) is verified by C-25 in constant time, with a 5-minute window when a timestamp is sent; Digio documents no signature, so its callback URL carries our C-19 secret (`ipb_token`, ≥ 32 random bytes, redacted by the scrubber); in both cases the adapter reads the envelope back from the vendor and returns only that status, so a webhook is never more than a trigger (`@IPB-10-27`); an unknown document is refused before any read-back.
- **T:** a silent signature-type downgrade. Control: each signer's method is fixed when the envelope is created and kept in the product's `EsignEnvelopeStore`; a method the adapter cannot provide exactly (Leegality without a workflow for it, Digio biometric Aadhaar or account eSign, wet ink anywhere) is refused with `method_unsupported`; Aadhaar and DSC sessions are refused for a signer created with another method.
- **T:** the wrong document signed. Control: documents travel by reference; the adapter reads the PDF from STORAGE and refuses it when its SHA-256 differs from the reference, before any request; the signed PDF is written to STORAGE (`REGULATED`) with its own SHA-256.
- **I:** documents and signers at the ESP. Control: both vendors are India-hosted (`IN`); signer names, e-mail addresses and phone numbers are recipient fields (IPB-DEV-05); credentials (Leegality auth token and salt, Digio client secret) come from SECRETS and never appear in URLs or logs.
- **R:** unverifiable signatures. Control: signature records name the ESP, the vendor document and its audit trail; PAdES validation (`verifySignature`) is `unsupported` on both adapters until a validator is built (PL3-D-23).
- **Residual:** HMAC-SHA1 for Leegality is accepted for verification only (PL3-C-02); move to SHA-256 when Leegality offers it (#55). Digio's callback rests on the URL secret, and its source ranges are unknown (#56).

### 3.17 `@infrabyx/export` and C-22 (built, PL3 session 5)

- **I:** one tenant's data in another tenant's archive. Control: the snapshot runs in the requesting tenant's context with forced RLS and an explicit `tenant_id` filter; archives, jobs and downloads are RLS-scoped; storage keys carry the tenant id and the adapters refuse cross-tenant keys.
- **I:** data that must never leave. Control: map fields that are SECRET, binary, sealed (`*_enc`) or named like Aadhaar or card data are refused (`IPB-EXP-004`); restricted folders are refused (`IPB-EXP-001`); approval payloads and notification variables are not in `REF-EXPORT-1.0` or `-1.1`; file and folder names carry ids only, plus the tenant name in the root folder; job and event payloads describe the job, never its content.
- **T:** an archive changed after export, or a forged one. Control: every file has a SHA-256 in `manifest.json`, which carries a pack hash and is signed with a detached ES256 JWS made by KMS `sign` with the platform export-signing key (C-22); the shipped offline verifier checks hashes, unlisted files, the signature, control totals, CSV headers and the audit chain; the `export.archive` row is insert-only, and each download ledgers `<archive id>:<sha256>`.

- **D:** export abuse as a load or exfiltration path. - **E:** a new destination used to exfiltrate. Control: only download exists; any other destination is refused (`IPB-EXP-002`) until it is built as the delay-window action of IPB-07-27(c).
- **S/R:** downloads that cannot be traced. Control: ledgered request, start, archive creation and each download; the signed `ExportCompleted` JWS is kept with the archive.

### 3.19 `@infrabyx/ai` gateway, registry and routing (built, PL4 session 2)

### 3.20 `@infrabyx/ai` scrubber, guardrails, evals, retrieval and run retention (built, PL4 session 4 and owner answers #27, #30)

- **I:** personal identifiers sent to a model provider. Control: above PUBLIC every outbound text (rendered prompt, messages, data blocks, texts to embed) is scrubbed into `<PII:KIND:n>` tokens before any adapter sees it; the reverse map lives only in the request's memory and is never stored, logged or traced. Detection raises the request's class (an Aadhaar or PAN makes it REGULATED), so it also tightens routing; scrubbing never lowers the class. An invalid `ai.scrub.patterns` fails closed. Token-shaped text in the input is defused, so input cannot forge a token that would expand to another value.
- **T:** prompt injection and jailbreaks in the caller's own text. Control: the rule-based input classifier (English, Hindi, Hinglish) blocks at `ai.guard.input_threshold.<feature>` before routing (`IPB-AI-042`, `GuardrailTriggered(injection, refuse)`); injection inside data blocks is neutralised and recorded (`neutralise`), and the tool allow-list still halts any call it provokes (`@IPB-03-AT-01`).
- **I:** the model reveals hidden context or invents personal data or sources. Control: the output classifier withholds echoed system-prompt sentences and the data instruction, redacts PII the inputs did not carry, drops citations to sources outside the request's data blocks, and replaces reserved advice with a neutral notice; `ai.guard.output_policy.<feature> = refuse` withholds the whole answer (`blocked`).
- **I:** one tenant's documents retrieved for another. Control: `ai.retrieval_index` and `ai.chunk` have RLS forced and every search runs in the caller's context (`@IPB-03-AT-05`: zero cross-tenant results); the product's `authorize` callback removes resources the caller may not read (fail closed); a data-class ceiling per call drops chunks above what the feature may receive. Chunk text is sealed with FieldCrypto; the embedding and the lexical vector are built from scrubbed text, so neither carries identifiers (they are still document content, classed CONFIDENTIAL).
- **T:** a prompt version activated without passing its golden set, or an eval that silently calls a paid model. Control: activation needs an eval pass recorded for the exact content hash; `prompts sync` activates only with a current committed result, and pre-production, production and DR need a live result (staging accepts the scripted CI result for synthetic data, owner answer #35); CI runs `ai-prompt-lint` and `ai-eval-gate` on the scripted fake model; `eval --live` refuses to start without an approval reference (O-6).
- **S/E:** the C-24 signer used to mint something other than a Google token. Control: `signServiceAccountAssertion` accepts only the FCM and cloud-platform scopes and only Google's token endpoint as audience (PL4-C-01); the key comes from SECRETS, the token is cached and never logged.
- **R/I:** AI run metadata kept forever, or a run deleted that an approval or statutory output depends on. Control: `RunRetention.sweep` deletes routine runs after 180 days with one ledger entry per run, reading across tenants only through `SVC_AI_RUN_SWEEP` (id, tenant, time; ledgered per tenant); a restrictive PostgreSQL policy refuses deleting any run younger than 180 days or under an active hold.
- **Residual:** the classifiers are rule-based (A-06) and the PII detectors pattern-based, so an unusual shape can pass (R-16); a product that does not call `deleteResource` when it deletes a resource leaves its chunks, filtered only by the `authorize` callback (§3.26).

### 3.29 `@infrabyx/cms` core (built, PL5 session 4)

- **T (redirects):** an open redirect or a loop. Control: targets are site paths or `https:` only; loops and chains are refused at save (`IPB-CMS-009`); manual and imported redirects need a checker and the legal reviewer before they are active.
- **I (deletion, OWNER-QUESTIONS #48):** content kept forever, or deleted early. Control: soft delete with a restore window; the purge deletes only rows soft-deleted more than 90 days ago (restrictive policies refuse any other delete), one ledger entry per sweep.
- **E/T (policies, session 5a):** a legal document published by one person, changed after approval, or published with unreviewed text. Control: legal reviewer maker, super admin checker and DPO for privacy-class templates, never the maker (service checks and table constraints); approval snapshots parameters and the rendered hash and a trigger refuses any later edit (`IPB-POL-008`); counsel markers, unresolved parameters, banned wording, stale citations and the notice period block submission and approval (`@IPB-05-AT-03`…`-09`). A MAJOR Terms change takes effect only 30 days after users are notified (the later of the notice published and sent, append-only `cms.policy_notice`, never backdated; #55), so an approval alone cannot start the clock.

Control: gated files sit in a private bucket and are served by a 300-second presigned URL; downloads keep the CRM lead reference, never field values; form submissions keep only ids, the consent receipt and state, also on failure (`@IPB-04-AT-47`); a honeypot and a rate-limit hook stop scripted submissions; the pricing copy has no price field and figures come only from the catalogue (`@IPB-04-AT-30`).
- **Residual:** the scheduler and the purge run as service principals carrying `PLT_CONTENT_EDITOR`, because IPB-02-11 opens the platform scope only to PLT roles (PL5-D-06); they call only the scheduled publish, unpublish and purge paths. Rate limiting of the public API and of forms is a hook the site must supply. Downloads and form submissions also run as such service principals (PL5-D-08) and only insert their own rows.

### 3.30 `@infrabyx/consent` (built, PL5 session 5c)

`consent` adds the `consent` schema (texts, the append-only consent ledger, acceptances), the CMP components and the first-party controller, the consent endpoint, script gating and the purge with the `svc_consent_sweep` reader.

- **I (tracking before consent, O-2):** a third-party tag or pixel loads before or without consent, or on a sensitive or authenticated route. Control: the server never renders an active third-party tag (inert `text/plain` declarations activated by the first-party controller for consented categories only); marketing tags on the locked sensitive routes or on app routes are dropped and reported (`IPB-WEB-005`); only `none` adapters exist at launch; GPC keeps analytics and marketing off (`@IPB-04-AT-81`, `-83`, `-85`, `-86`).

Control: the cookie only reflects the visitor's own choice in their own browser; it is parsed strictly, names a ledger receipt, and a forged value can at most enable scripts for that same visitor; nothing server-side trusts it beyond rendering.

### 3.31 `@infrabyx/feedback` (built, PL5 session 6)

Control: a strict allow-list of fields; forbidden or unknown fields, a URL or query string, and any personal number or secret the AI scrubber detects refuse the whole request (`IPB-FB-001`) before anything is stored; there is no column for page content or screenshots; routes are reduced to patterns and user agents to families.

### 3.33 MEDIA port and the owner answers #53–#57 (PL5-D-11)

### 3.34 `apps/public`, the group site (built, PL5 session 7; PL5-D-13)

The reference group website on Next.js 16 (`@infrabyx/public-site`, private, never published). It reads published content, policies, brand packs, consent texts and the trust mirror in-process through the kernel, and writes only through three endpoints: consent choices, CMS forms and feedback.

- **S/T (script injection):** a CMS body or a crafted path runs script in the visitor's browser. Control: a per-request nonce CSP from `proxy.ts` (`script-src 'nonce-…' 'strict-dynamic'`, `object-src 'none'`, `base-uri 'none'`, `frame-ancestors 'none'`, `form-action 'self'`, no `unsafe-inline`); rich text is the CMS sanitiser's output only; the three first-party controllers are served from the site's own origin under the nonce; the e2e gate asserts the headers.
- **T (forged writes):** a third-party page posts consent, a form or feedback as the visitor. Control: every POST checks `Origin` (or `Referer`) against the site's own origin; forms carry a honeypot; the CMS form and feedback services apply their own limits and minimisation (PL5-D-08, PL5-D-10); consent is written to the ledger with the exact text version.
- **I (tracking before consent):** a page loads anything from another origin before or after a choice. Control: no font CDN, no analytics, no third-party scripts; images and styles are `'self'` only; the gate records every request in Chromium for each consent path and fails on any other origin (`@IPB-04-AT-80`, `@IPB-04-AT-85`).
- **D (database lookups per request):** each request resolves the pack, and each unknown path makes the proxy look up a redirect or tombstone. Control: lookups are indexed reads through the kernel on a bounded pool (10 connections); rate limiting belongs to the edge in front of the site (PL6 deployment).
- **E (fixtures in production):** fixture adapters (fake CRM, HR, OH desk, trust feed) or directory storage accept data in a real environment. Control: `siteEnv()` refuses `APP_FIXTURE_ADAPTERS` and `STORAGE_DIR` outside local, dev, test and preview, so the process exits with code 78; without real adapters each port answers `IPB-PORT-001`. Seeds refuse prod, dr and pre-prod (`SEED_REFUSED_ENVS`).
- **I (unmapped hosts):** a host not mapped to a pack serves the product's default pack under another name. Control: such responses carry `noindex` and the generated files (sitemaps) are empty for them.
- **Residual:** the site has no edge rate limit or WAF of its own yet (PL6 deployment); the fixture CRM and HR keep form data in memory only, so local and test submissions are lost on restart, by design.

### 3.42 `apps/reference` api and worker (built, PL6 session 4a; PL6-D-08)

The reference API (NestJS 11) and its worker on the platform packages; the template products copy. - **E:** Control: the tenant context comes only from verified claims (`TenantContextInterceptor`); AUTHZ decides per route with the principal's roles and the tenant attribute; a sandbox-tenant owner reading a demo greeting gets 404 under RLS (NN-01).
- **Residual:** the fixture personas have fixed ids and roles by design (seed tenants only, IPB-11-26); products must never enable `APP_FIXTURE_ADAPTERS` outside the four fixture environments (the env check refuses it).

Residual: local only; the in-memory seed vault keeps no hash list between runs.

Residual: traffic between the containers and the services is plain on the loopback interface of the developer's machine or the CI runner.

Residual: the platform role lets the relay read every tenant's row in the platform-scope tables that admit `PLT_*` readers, more than the tenant list it needs; a reader role for product outboxes (#74) would narrow it.

### 3.48 The outbox relay as a service reader (built, R1 item 1; R1-D-01)

`OutboxRelay` in `@infrabyx/tenancy` relays module outboxes to the QUEUE as `SVC_OUTBOX_RELAY`, the one service reader that also writes.

- **E (the relay reading or changing more than its outboxes):** Control: its database role starts with no grant; `tenancy.register_outbox()` grants select of the relayed columns and update of `dispatched_at` and `attempts` on one registered `<schema>.outbox`, and `audit/0002` the ledger append; any other table or column is refused by PostgreSQL (`42501`, proven in the integration tests). The kernel admits only `<schema>.outbox.dispatch` for this reader, in a tenant context.
- **T (marking another tenant's events dispatched):** Control: there is no platform-scope update policy; every update runs in the row's own tenant context under the outbox's tenant policy, so a batch can only touch its tenant's rows.
- **R (an unrecorded relay):** Control: the cross-tenant discovery read is ledgered per tenant (`platform.service_read`), and each batch writes `<schema>.outbox.dispatch` in its tenant's ledger in the same transaction.
- **S (registering a table that is not an outbox):** Control: `register_outbox` is executable by `app_migrate` only, validates the schema name, the columns and forced RLS, and grants on that schema's `outbox` table only.
- **Residual:** the event envelope is read by the relay (it must be, to deliver it); envelopes carry no secrets by the IPB-10 event contract.
- **E (the read-only role writing through the relay role; found by Udofin, PR-UDF-016):** `tenancy/0003` granted `svc_outbox_relay` to `app_ro` and `app_rw` with the default INHERIT, so both held its writes (the ledger append, `dispatched_at` and `attempts`) without switching. Control: `tenancy/0004` revokes it from `app_ro` and makes every `svc_*` membership of `app_rw` and `app_ro` INHERIT FALSE, SET TRUE; `app_ro` and `app_rw` are NOINHERIT, so later grants default the same (R1-D-11). The integration test proves a login holding only `app_ro` is refused every write and the switch to `svc_outbox_relay` (42501), and that no role reachable from a read-only or auditor role holds a write privilege.

### 3.49 The visual block editor (built, R1 item 2; PR-038, R1-D-02)

The Studio page editor edits a page's blocks through forms (`@infrabyx/ui/studio` `BlockEditor` and `blockHandlers`, with the block forms and the rich text codec from `@infrabyx/cms` `BLOCK_EDITOR`). It is a new way into the same save: every operation becomes one `CmsStudio.saveDraft` call.

- **T (markup or script through rich text):** Control: the editor's text is turned into portable text, never HTML, and `sanitisePortableText` runs on the result, then again at save and at render (IPB-04-15); link targets go through `safeHref`, so a `javascript:` or other non-allow-listed link is dropped (unit-tested). - **E (editing without the right role, or on a deleted item):** Control: the handler only calls the CMS service, which checks the editor roles and platform scope on every save; the console's AUTHZ gate covers the new action like the section's other actions; a deleted item shows no editor.

### 3.50 The Ecosystem inbox (built, R1 G2; R1-D-15)

`EcosystemInbox` in `@infrabyx/tenancy` stores inbound Ecosystem events in the consuming module's `eco_inbox` before processing (`tenancy.create_ecosystem_inbox`, migration `tenancy/0006`) and processes them in `seq` order per subject.

- **T and R (a replayed or doubled event acting twice):** Control: the event is stored first, unique by `(tenant, source, id)` and by `(tenant, type, business key)`; a duplicate of either is acknowledged and never handed to the handler; an event at or below the subject's position is skipped; every receive, step, failure, break and repositioning is ledgered in the same transaction.
- **T (out-of-order events applied in the wrong order):** Control: an event ahead of the next `seq` is parked, never processed early; after 15 minutes the product's replay fetches the gap, and a gap still open becomes a break the product raises as `ReconciliationBreakRaised`; only an operator's `setPosition` from the owner's snapshot reopens the subject.
- **S (a sandbox event in production):** Control: an event whose `environment` differs from the inbox's is refused (`IPB-API-005`), as is an envelope that does not validate (consent or legal basis with personal data included).
- **I and E (one tenant's events seen or changed by another):** Control: both tables have forced row-level security by the consuming tenant; `app_rw` may select, insert and update, never delete; the function that creates them is executable by `app_migrate` only and validates the schema name.
- **D (a failing handler blocking a subject):** Control: the handler's transaction rolls back; the attempt is counted in its own transaction; after `maxAttempts` (5) the event is `failed` and the subject waits for an operator instead of retrying without end.
- **Residual:** signature verification of the inbound delivery (Standard Webhooks, RFC 9421) happens before `receive`, in the product's gateway; the detached JWS of regulated messages is G5. Inbox rows are kept until the product decides their retention (no purge is built; retention is the owner's).

### 3.51 JWS for regulated messages (built, R1 G5; R1-D-08, R1-D-17)

`signRegulatedMessage` and `verifyRegulatedMessage` in `@infrabyx/crypto` sign and check the detached JWS that Ecosystem Spec §3.6 stores with each regulated message (`isRegulatedMessage` in `@infrabyx/contracts/events` names them).

- **S and T (a forged or altered regulated message):** Control: ES256 only, through an allow-list that refuses `none`, every `HS*` and every other algorithm; the signature covers the JCS form of the whole CloudEvent; the key is in KMS and named by `kid`; a DER signature, an attached payload or non-canonical base64url is refused.
- **S (algorithm or key confusion through the header):** Control: the protected header must hold exactly `alg`, `kid`, `typ`, `iat` and `jti`; `b64`, `crit`, `jku`, `jwk`, `x5u`, `x5c` and any other member are refused; keys come only from the verifier's own key ring, never from the message, and the ring takes EC P-256 keys only.
- **R and T (a replayed message):** Control: `iat` must lie within five minutes back and one minute ahead, and a `jti` is accepted once (the replay store); a message that fails any other check never claims its `jti`, so a forgery cannot block the real one.
- **D (a key rotation dropping messages):** Control: the key ring holds the current and the previous key, each with its validity window; messages signed during the overlap verify with either.
- **Residual:** `MemoryReplayStore` is per process; a product with several verifier instances backs `ReplayStore` with shared storage, or relies on the Ecosystem inbox's `(source, id)` uniqueness as the durable second line. RFC 9421 transport signatures are the product gateway's.

### 3.52 Scheduled per-tenant jobs (built, PR-UDF-013; R1-D-12)

`TenantSweep` in `@infrabyx/tenancy` lists the tenants for a product's scheduled jobs, and `AuditSweep` in `@infrabyx/audit` runs the IPB-02-51 ledger jobs (weekly verification, daily anchor) for each.

- **I and E (a job seeing more than its tenant):** Control: the list is a `SVC_TENANT_SWEEP` read whose database role selects only `id` and `status` of `tenancy.tenant` (anything else is 42501, tested); each job then runs in its tenant's own context under RLS, as the job's service principal, and sees only that tenant's rows (tested: one tenant visible per run).
- **R (an unrecorded sweep):** Control: the list read is ledgered in every tenant it lists (`platform.service_read`); the job's own writes are ledgered under its principal; a break found by verification is ledgered and raises `LedgerChainBroken`, as for one tenant.
- **E (a job holding reader rights or reader limits):** Control: the reader and the job principal are separate; a context holding a service-reader role is read-only in the kernel, so the job runs as `svc_tenant_job` (or the product's own principal), never as the reader; the reader's role is switch-only (R1-D-11).
- **D (one tenant blocking the rest):** Control: a tenant's failure is reported by its error code and the sweep continues.
- **Residual:** scheduling, retries and alerting on `broken` or `failed` are the product worker's (`docs/product-guide.md` §7c).

### 3.53 Customer sign-in: one-time codes and DPoP (built, #84; R1-D-18, R1-D-19)

`CustomerIdentityPort` signs in end users who are not staff, in a customer realm (Keycloak, with the `ipb-customer-otp` extension) or organisation (Zitadel) per product. Codes go out through NOTIFY; sessions are bound to a per-device ES256 key by DPoP and checked by `verifyDpopProof`.

- **S (guessing or brute-forcing a code):** Control: six digits from a CSPRNG, 300 s, 5 tries per code; at most 10 codes per 10 minutes per account, 30 s apart; back-off after 5 consecutive wrong codes and a 15-minute lockout after 10, decided before the IdP is called; Keycloak's brute-force protection behind it. The extension compares in constant time and consumes the challenge on success.
- **S (a stolen access or refresh token):** Control: requests need `Authorization: DPoP` and a proof with `ath` by an active device key of the token's user (and on Keycloak the key in `cnf.jkt`); a refresh needs a proof by the device's key and the current refresh token; a current refresh token with another key revokes the device; a used refresh token is dead (Keycloak rotation without reuse, Zitadel rotation, and the platform's compare-and-set).
- **S and T (forged or replayed proofs):** Control: ES256 only; strict header, key and claim shapes; `htm`, `htu` and `ath` bound; `iat` within 60 s back and 30 s ahead; each `jti` claimed once per key in a replay store shared by replicas (`RedisReplayStore`), only after the proof verifies.
- **S (a code phished to another device):** Control: the code is bound to the key that asked for it; another key's proof at `verifyChallenge` is refused.
- **E (a customer factor satisfying a staff check):** Control: customer realms and organisations are separate from staff realms, with their own issuer and audience; customer tokens carry product roles only (staff roles are refused) and never count as MFA (IPB-02-02); the realm has no `amr` mapper.
- **I (codes or logins leaking):** Control: the IdP keeps only a SHA-256 of `<challenge>:<code>` (Keycloak) or its own hashed code (Zitadel); the code reaches the product API over TLS from the authenticated client call and leaves only through NOTIFY's `sendOneTimeCode`, which stores `[redacted]` and never the address; the platform's tables hold no code, no login (accounts by IdP id, hashed in the guard) and refresh tokens only as SHA-256; ledger entries carry no codes. The extension refuses public clients and clients not marked `ipb.customer.otp`, so only the product API, with its secret, can ask for a code.
- **I and E (one tenant's customers seen by another):** Control: accounts are per tenant (usernames derived from the tenant and the login); `connectors/0004` has forced RLS by tenant, select, insert and update for `app_rw`, and delete only under the retention floors of `connectors/0005`.
- **R:** every guard decision, challenge, attempt, device creation, refresh and revocation is ledgered.
- **I (sign-in state kept longer than needed; owner answer #86, R1-D-23):** Control: a per-tenant job deletes challenges 24 h after expiry, guard rows once their lockout window has ended, and devices 12 months after last use, each period a setting. Unbinding a device or closing the account deletes devices at once. Restrictive delete policies (`connectors/0005`) keep floors below the settings, so no caller can delete a live challenge, an active lock or a device in use. Every deletion is ledgered.
- **D (code flooding or lockout of a victim):** Control: the per-account limits cap SMS cost and annoyance; a lockout is timed (15 minutes), never permanent; the product's edge limits per IP (IPB-02 §02.4.6.2) sit in front.
- **Residual:** Zitadel does not bind tokens to the key, so a Zitadel access token is bearer at the IdP until it expires (300 s) and its refresh token survives the platform's sign-out at the IdP; both are refused by the platform. Keycloak's 1-second quick-login check can lock a customer for 60 s after two very fast tries. The upstream Keycloak 26.8.1 base carries findings waived until 6 Nov 2026 (`infra/docker/trivyignore.yaml`); the pin moves when the rebuilt base clears the 7-day policy. Retention of the sign-in tables is the owner's (OWNER-QUESTIONS #86).

### 3.54 The `KYC` and `VIDEO_MEET` ports (interfaces and fakes, PR-FBX-01; R1-D-21)

The interfaces and their contract cases, with in-memory fakes. No adapter yet (OWNER-QUESTIONS #87, #88), so no data leaves a product through these ports today.

- **I (identity data leaking through the port):** Control: every KYC request schema is REGULATED; adapters must be `IN`; files move as STORAGE references with SHA-256, never inline; results never carry an Aadhaar number (last four digits only).
- **I (a V-CIP recording kept by the vendor or in a shared bucket):** Control: a CONFIDENTIAL or REGULATED room must declare `providerRetention: "none"` and a recording target (the schema refuses otherwise); `fetchRecording` returns a hash manifest, never media; per-tenant target routing is deferred (#83), so V-CIP stays off.
- **S (a V-CIP call from outside India or from an untrusted network):** Control: `joinToken` refuses (`IPB-SEC-002`) a country outside `participantCountries`, an anonymised origin, an official outside `officialNetworks`, and a participant in another role; the origin comes from the product's GEO check.
- **T and R (a forged vendor event or an altered recording):** Control: webhooks are triggers only; the session or room is read back from the vendor; the manifest lists every artefact by SHA-256 with its own hash, and the product ledgers it.

### 3.55 The Digio KYC adapter (`digio-kyc`, built behind a flag; R1-D-24)

### 3.56 Statutory audit capture (`audit/0003`; PR-FBX-10 item 2, R1-D-25)

PostgreSQL captures every insert, update and delete on registered books-of-account tables, with values and context, in a per-tenant hash chain the daily anchor signs.

- **T and R (a change to the books that leaves no trace):** Control: row triggers enabled ALWAYS on every registered table, TRUNCATE refused, and the capture written by a SECURITY DEFINER function whose owner role nobody holds. Event triggers refuse dropping or disabling any part. The chain, the head and `capture_problems()` are verified daily, and the anchor signs the head.
- **T (the captured history edited):** Control: update, delete and truncate on `audit.capture` are refused always, for every role. A superuser who first disables the guard leaves a chain break and a reported problem.
- **I (captured values are copies of REGULATED data):** Control: `audit.capture` has forced RLS by tenant (read only), its value columns are classed REGULATED, and columns encrypted by field crypto stay ciphertext in the copy. The rows are kept as the ledger is.
- **E (the capture writer misused):** Control: `capture_writer` is NOLOGIN, NOINHERIT and granted to no role; the read-only-role check covers it. The capture function takes no argument and writes only what the trigger sees.
- **D (a capture failure blocks the books):** Control: settings that do not fit a column are recorded as absent rather than refusing the write; a row without `tenant_id` is refused, which registration prevents.
- **Residual:** superuser access to PostgreSQL, as for the ledger; event triggers do not fire in replica mode, so DDL done there is caught by the next daily verification instead.

### 3.57 Branch context (`tenancy/0007`, `audit/0004`; PR-FBX-10 item 1, R1-D-26)

Products scope rows by branch within a tenant through `tenancy.branch_allowed()` and the kernel's branch settings.

- **E (a user reads or writes another branch's rows):** Control: the policy's branch condition denies by default; the branches come only from the verified context, the kernel sets them, and a callback cannot change them. A comma cannot appear in an id, so a list cannot be widened.
- **E (head-office scope granted by accident):** Control: `allBranches` is an explicit flag in the context, never inferred from an empty list (an empty list sees nothing).
- **R (which branch a change was made in):** Control: the ledger entry and the statutory capture record the branch; the ledger chain covers it.
- **T (an exported audit trail that cannot be re-verified):** Control: `REF-EXPORT-1.3` exports `branch_id`, and the offline verifier hashes it only when set, exactly as the ledger chain does.
- **Residual:** branch scoping is as strong as the product's policies; `rls-lint` checks the tenant condition, not the branch one. Tenant isolation is unchanged.

### 3.58 Inbound idempotency (`tenancy/0008`; PR-FBX-10 item 4, R1-D-27)

Product APIs store each POST and PATCH response under the client's key for 24 hours and replay it for an identical retry.

- **T (a replay used to get another request's response):** Control: a replay must match the stored route and the canonical request hash, else 409; keys are per tenant under forced RLS.
- **I (stored responses):** Control: response bodies are classed REGULATED, readable only in their tenant, and deleted after the TTL (only expired rows can be deleted).
- **D (duplicate work under concurrency):** Control: one request per key at a time (advisory lock, 409 IPB-API-011); the key commits with the change.
- **Residual:** a client that reuses a key after expiry starts a new request, as IPB-10 intends.

### 3.59 Break-glass visible to the tenant (`tenancy/0009`; PR-FBX-10 item 3, R1-D-28)

Each tenant sees every break-glass grant used on its data, and is notified on first use.

- **R (staff access to a tenant's data unknown to the tenant):** Control: the kernel records each use of a grant in the tenant before the transaction runs, for reads as for writes; the tenant reads the record (who asked, who approved, why, until when, how often); a notice event is raised once per grant.
- **T (the record hidden or altered):** Control: the application role can only read it; writes go through two SECURITY DEFINER functions that act on the transaction's own tenant and an active grant only.
- **I (the grant's reason shown to the tenant):** Control: by design, the reason for touching the tenant's data is the tenant's to see; it is CONFIDENTIAL and readable only in that tenant.
- **Residual:** a use is recorded when the kernel runs; direct database access by a superuser is outside it, as for the ledger.

### 3.16 Cross-tenant service readers (owner answer #22, PL3-D-21)

Background workers that must find due work across tenants (the workflow timer poller, the NOTIFY dispatcher, the one-click unsubscribe link, the export sweep) read through `ServiceReader` in `@infrabyx/tenancy` as one of the `SVC_` roles in `SERVICE_READER_ROLES` (`contracts/roles`).

- **E:** a background identity reading or changing more than it needs. Control: each role maps to its own database role (`svc_scheduler`, `svc_notify_dispatch`, `svc_notify_unsubscribe`, `svc_export_sweep`, `svc_ai_run_sweep`, `svc_ai_index_sweep`, `svc_vidhi_sched`, `svc_tenant_sweep`, created by the owning package's migration), granted `SELECT` on the named columns of its tables only and nothing else (one table each, except `svc_export_sweep`: jobs, archives and the deletion marker, ids and times only, under platform-scope read policies limited `to` that role; PL3-D-25); the kernel runs a platform-scope read as that role (`SET LOCAL ROLE`), so a query on any other table or column fails with `42501`, and forced RLS still applies.
- **E:** a reader approving, writing or impersonating. Control: the kernel refuses every mutation by a reader except the ledger entry recording its own read, in a tenant context (`IPB-SEC-005`); its context must be a service principal with exactly one reader role, no `PLT_*` role, no `act` and no break-glass; a token claiming a reader role is refused (`contextFromClaims`), so readers exist only in-process.
- **R:** an unrecorded cross-tenant read. Control: the query must select `tenant_id`; each read that returned rows writes one `platform.service_read` ledger entry in every tenant it touched (actor = the reader principal, resource = the table) and calls the operational `onServiceRead` hook with the row count per tenant. An empty read returns no tenant data and writes nothing.
- **Residual:** the platform-scope RLS read policies on these tables still admit PLT_* principals (people, under IPB-02-11), as before.
- **E (inherited reader privileges, PR-UDF-016):** until `tenancy/0004` every `svc_*` role was inherited by `app_ro` and `app_rw`, so their column grants and platform-scope policies applied without the kernel switching roles. ## 5. CI and supply chain

- **T:** a compromised action or dependency. Controls: X-12; Renovate as the single updater; `ipb:check` refuses regressions; dependency and image ages recorded in DECISIONS (PL2-D-32, PL2-D-37).
- **E:** over-privileged release token. Open risk R-01 below; the GitHub App token replaces `NPM_PUBLISH_TOKEN` before production (PL1-D-21, PL2-D-42).
- **T (a substituted release artefact):** Control: the release job signs the BOM with cosign keyless (the release workflow's GitHub OIDC identity, Fulcio, Rekor) and verifies it before publishing, then attests each published tarball as the registry serves it with the BOM as CycloneDX predicate, verifies it and attaches the bundles to the package's release (owner answer #67(1), IPB-02-35, `@IPB-01-AT-18`); cosign is installed from the Go module proxy at a pinned version, checked by Go's checksum database.
- **I (what signing discloses):** every signature writes the repository, workflow and ref to the public Rekor log, permanently. Accepted for this public repository; `docs/product-guide.md` §6 tells private product repositories to sign with a KMS key if their names and release cadence must not be public.
- **I:** secrets in commits. Controls: gitleaks in CI with a reviewed baseline, the pre-commit env and credential guard, generated test tokens (no literal tokens in tests).
- **T:** a published package that a product cannot load (the 0.1.0 `@temporalio/proto` import). Control: `consumer-smoke` installs the packed tarballs with plain npm and imports every export with plain Node, in CI and before every publish (PL3-D-02).
- **T:** a third-party package published minutes before a release running its install scripts in the release job, beside its signing identity (found 29 Oct 2026: release run 130 resolved `@types/estree` two minutes after it was published). Control: `consumer-smoke` resolves with npm `--before` set 7 days back, the same rule pnpm's `minimumReleaseAge` applies to the workspace (PL2-D-32, R1-D-30).
- **D:** CI minutes exhausted on GitHub Free. Control: CI budget (PL2-D-41, PL2-D-44); weekly full matrix, changed-ports nightly.
